# Структура развития проекта (черновик v0.1)

> Это снимок мыслей по развитию программы из мозгового штурма. Идей ещё много — документ живой, дополняем по мере появления новых мыслей. Здесь зафиксирован общий язык (словарь) и архитектурный каркас, который не даёт «комбинаторике режимов» взорвать голову.

---

## A. Словарь — чтобы говорить одинаково

- **Engine** — то, что *исполняет* граф нод (ffmpeg / AE / Moho / ИИ). Без UI.
- **Shell** — интерфейс пользователя (колонки, нодовый редактор, настройки). Сам ничего не исполняет.
- **Capability** — способность («ffmpeg есть», «AE установлен», «ИИ-грант от сайта»). Нода видна, если её требования ⊆ доступных capability.
- **Workspace backend** — откуда файлы и где обработка: `local` или `cloud`. Прячет разницу путей/темпов.
- **folderConfig** — настройки одной папки (граф, авто-обработка, права, версии). Центральный синхронизируемый объект.
- **Job / Queue** — задача обработки и очередь к engine.
- **Event-stream** — поток engine→shell (прогресс, пауза-ручного-режима, готово, уведомления).

---

## B. Пространство состояний — 3 независимых оси (а не «куча режимов»)

| Ось | Значения | Чем управляет |
|-----|----------|---------------|
| **Identity** | anonymous / authenticated | какие capability открыты; есть ли облако |
| **Role** | user / admin | UI-поверхность: число колонок, кнопка плагинов, глубина настроек, право редактировать |
| **Backend** | local / cloud | где файлы, где обработка, схема путей, темпы |

Единственная связь: `cloud ⇒ authenticated`. Остальное ортогонально. Достижимых состояний ~6, и они **не строятся по отдельности** — выпадают из трёх свитчей.

## C. 4 абстракции, которые гасят всю «комбинаторику»

1. **Capability resolver** — `доступные = probeLocal() ∪ grantedBySite()`. Видимость нод = чистая функция от этого. Сюда же ложится «создание плагинов» (capability `dev.esbuild`, только в admin/dev-сборке) и «нет AE → нет AE-нод», «нет сайта → нет ИИ-нод».
2. **Workspace backend** — один интерфейс, две реализации. Разница путей (`project/_process` локально vs `$localFolder/$main/$project/$findTime` в облаке) живёт только в `resolvePaths()`. UI не знает.
3. **Engine / Shell + один API на двух транспортах** — `commands.*` (specta) вызываются хоть через Tauri IPC (локал), хоть через WS (сервер). Сервер = тот же engine-крейт + тонкий сетевой вход, **не переписывание**. Облачный протокол первичен, локал = его частный случай (engine на localhost).
4. **Event-stream** — один поток engine→shell. Прогресс, вкладки ручного режима и пуш-уведомления — это **три потребителя одного механизма**, а не три системы.

---

## D. folderConfig — центральный объект

Все операции «кнопка обработать», «выключить папку», «редактор нод», «кто может менять», «откатить» — это операции над одним объектом:

```
folderConfig = {
  graph / settings,        // что и как обрабатывать
  autoProcess: bool,       // тумблер "убрать из обработки"
  editPolicy: locked | user-editable,   // кто может менять
  version: N,              // текущая версия
  history: [ {v, author, when, snapshot} ]  // откат
}
```

**Правила по редактированию и версиям:**

- По умолчанию папки настраивает admin, и они `locked`. Это базовый сценарий.
- Редактирование пользователем — opt-in на папку (`editPolicy: user-editable`), не глобально. Свобода раздаётся точечно.
- Версионирование — только у folderConfig, не у всего подряд. Append-only снимки (`v`, кто, когда, snapshot), откат = записать старый снимок как новую версию. Без git-стиля с диффами на старте.
- Изменение пользователем = новая версия → admin всегда видит, что поменялось, и может откатить.

Это **не новая подсистема**, а два поля (`editPolicy`, `version/history`) у объекта, который и так синхронизируется.

## E. Осознанно откладываем (open questions — не решаем сейчас)

- **Пуш-уведомления** — отложено. Когда дойдём — потребитель event-stream, не новая система. (Программа работает на автомате → юзеру шлём, что происходит на сервере; admin видит не только свои папки, но и остальные.)
- **Что такое «сервер» физически** — пока: реальная машина(ы) с установленным AE/Moho + очередь задач (AE не мультитенантен → одна задача за раз). Эластичное облако с лицензиями AE — не сейчас.
- **Стоимость обработки** (`fromSite` суммируется с возвратом сайта) — повесить на job/event-stream позже.
- **Нода loop в ручном режиме** (группа вкладок) — UI-вопрос, после протокола паузы.
- **Конфликты синхронизации** — на старте last-write-wins, одно устройство.
- **Какие настройки скрыть у user** — позже, после фазы 1.
- **Авторизация: пароль vs сайт** — локальный пароль это UX-замок (косметика), не защита. Реальные права (оплаченный ИИ) живут на сервере в токене/грантах. Не писать свою криптографию — argon2/bcrypt.

## F. Дорожная карта (порядок имеет значение)

- **Фаза 0** — фундамент, юзер не замечает: Capability resolver + интерфейс Workspace backend (`local` = текущее поведение). Чистый рефактор. Без него фазы 3–5 запутываются.
- **Фаза 1** — admin/user + пароль (только UI, всё локально). Сюда же `editPolicy` + версии folderConfig.
- **Фаза 2** — вкладка «облако плагинов» (admin, чистое чтение/агрегация): кликаешь плагины → остаются проекты, где они есть; мультиселект; клик на папку → переход или открыть настройки нод.
- **Фаза 3** — авторизация + capability-гранты с сайта (identity онлайн, backend ещё локальный).
- **Фаза 4** — cloud backend: sync хранилища (IN/OUT) + очередь + удалённое исполнение через WS. Большой кусок. Триггер обработки на сервере (кнопка на папке / редактор) + тумблер autoProcess.
- **Фаза 5** — интерактивные вкладки ручного режима (на протоколе паузы): процесс доходит до `interactive`-ноды → пауза → отдаёт промежуточное состояние как вкладку → юзер правит/подтверждает → продолжение.

---

## Принцип, который снимает страх «двух программ»

Не «локальная программа» и «онлайн программа», а **один движок + одна оболочка + один API на двух транспортах**. Облачный протокол первичен, локал = его частный случай с engine на localhost. Сервер запускает тот же engine-крейт в роли `engine` (с установленными AE/Moho), пользователь — тот же код в роли `shell`. Один codebase, возможно два build-таргета, общий движок.
