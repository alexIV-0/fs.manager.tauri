# plugins-dev — исходники плагинов

`plugins-dev/<id>/` — исходник. `distr-plugins/<id>@<version>/` — esbuild-бандл, который реально загружает приложение.

**Правка в `plugins-dev/` не действует, пока не пересобрано:**

```bash
npm run plug:build <id>     # один плагин (аргумент = имя папки)
npm run plug:build:all      # все
npm run plug:watch          # вотчер на время работы
```

Не редактировать `distr-plugins/` — это артефакт.

## Доставка пользователю — отдельный канал

`distr-plugins/` работает **только в dev**: Rust-менеджер ищет там плагины, когда `is_dev` (`../src-tauri/src/commands/plugin_commands.rs:105`). В собранном приложении путь другой — `app_data/plugins`.

Из этого следствия, которые легко забыть:

- `distr-plugins` в `.gitignore`, а `release.yml` **не вызывает** `plug:build` — то есть **релиз приложения плагины не несёт вообще**. Правка плагина, влитая в `main`, до пользователя с обновлением не доедет.
- Доставка отдельная: `npm run plug:pack <id>` (или `plug:pack:all`) собирает zip, пользователь ставит его в `app_data/plugins`.
- Версия в `plugin.json` живёт своей жизнью и **не** бампится CI (тот трогает только версию приложения). Меняешь поведение плагина — версию поднимаешь руками, иначе папка `<id>@<version>` не изменится и обновление будет неотличимо от старого.

## Состав плагина

| файл | роль |
|---|---|
| `plugin.json` | манифест: `id`, `name`, `version`, `apiVersion`, `type[]`, `main` (имя **скомпилированного** `.js`), `ui`, `external[]`, `cost`/`costUnit` |
| `<main>.ts` | код: экспортирует одну async-функцию `<name>Func(_item, _description)` |
| `ui.json` | целиковое определение ноды: `type`, `width`/`height`, `data.label`, `data.colorType`, `data.properties[]` |

Образец и хелперы — в `_template/` (`tauri.ts`, `plugin.md`, `ui.md`).

## Контракт: host-сервисы приходят в ctx

Третий аргумент точки входа — `ctx`. Из него берутся `fs`, `http`, `ffmpeg`, `exec`, `ae`, `paths`, `system`, `fonts`, `sendToMW`, `log`, `signal`. Импортировать их откуда-либо **не нужно и нельзя** — единственная живая копия живёт в `src/PluginAPI/host.ts`, плагин её не бандлит:

```ts
import type { PluginContext } from '../../src/PluginAPI/host';

export async function copyFileFunc(_item: any, _description: any, ctx: PluginContext): Promise<string[]> {
	const { fs, sendToMW } = ctx;
	…
}
```

Импорт `PluginContext` — **только типовой**, при сборке он стирается: в бандл не попадает ничего, а взамен есть автодополнение и проверка типов.

**`onLoad` больше не экспортируется.** Его наличие — признак старого стиля, и загрузчик по нему определяет, что у плагина есть module-local состояние, поэтому **отказывается кэшировать модуль** и пересоздаёт его на каждый вызов. Это была утечка: ES-модули из динамического импорта нельзя выгрузить, и прогон 500 файлов через 5 нод оставлял 2500 копий бандла в памяти.

Если сервис нужен функции-хелперу (в том же файле или в соседнем), передавай его параметром — `fs: PluginContext['fs']` или целиком `ctx: PluginContext`. Обязательный параметр обязан идти **до** необязательных, иначе TypeScript откажется компилировать.

## Ловушка: ровно одна экспортированная функция

Раннер резолвит вызываемое через `resolveCallable` (`src/PROCESSING/processItem.ts:635`): `default` → сам модуль → **первая попавшаяся функция**, кроме `onLoad`/`onUnload`/`default`.

Значит вспомогательная функция, экспортированная рядом с основной, может тихо стать точкой входа (порядок = порядок объявления). Хелперы **не экспортировать**.

## Что доступно внутри плагина

- Импорт из `../../src/**` — можно, esbuild забандлит (`createPathForFileByPattern`, `formatNameByPattern` и т.п.).
- `node:*` / `path` / `fs` остаются **external** и переписываются на полифилы `src/PluginAPI/*` через importmap из `vite.config.ts` и Rust-handler протокола `plugin://`. Поэтому `import path from 'path'` работает, но это не Node.
- Сторонние npm-пакеты — только через `"external": ["pkg"]` в манифесте: сборщик положит их в плагин отдельными node_modules.
- Побочные эффекты и IPC — только через сервисы из `ctx` (см. «Контракт» выше). Прямой `window.tauriAPI` в плагине — ошибка: обходит единственную точку IPC.

## Аргументы

- `_item` — параметры ноды. Встроенные свойства лежат по `id` из `ui.json`; входы (`isInput`) приходят под `_item.import.<id>` уже разрешёнными в массивы; динамические свойства (добавленные через «+» с `editLabel`) лежат **по лейблу**, а не по id.
- `_description` — контекст проекта. Относительный путь из `pathNavigator` резолвить от `_description.projectPathGD` (GD-папка проекта), **не** от `mainWorkFolder`.
- Возврат — `string[]` (пути результатов).

## Маски

Маски имён (`$clearName`, `$random(3)` и пр.) — общий движок `src/Utils/masks.ts`, применяется через `formatNameByPattern` / `createPathForFileByPattern`. **Свои маски в плагине заводить нельзя**: список дублирован в Rust (`apply_vars`) и в документации, расхождение молча ломает пути.

## Модель доверия: плагин = полное доверие

Зафиксировано явно, потому что из кода это не видно, а решения об этом принимаются часто.

**Плагин исполняется с правами приложения.** Он получает `ctx` с `fs`, `exec`, `http` — то есть чтение и запись любого файла, запуск любого процесса, любые сетевые запросы. Песочницы нет и она не планируется: плагин по своей природе занимается ровно этим (гоняет ffmpeg, пишет рядом с исходником, постит в соцсеть). Ограничивать его смысла нет — он бы просто перестал работать.

Следствия, которые из этого вытекают и о которых нужно помнить:

- **Установка плагина = запуск чужого кода.** Единственная граница — момент установки: архив из недоверенного источника ставить нельзя. Поэтому распаковка проверяет имена записей (`sanitize_relative` — общая с протоколом `plugin://`) и держит потолки (`ArchiveLimits`): это защита от **испорченного** архива, а не от вредоносного плагина. Второе технически невозможно.
- **`apiVersion` — не механизм безопасности,** а совместимость контракта.
- Что имеет смысл усиливать: **границы вокруг** плагинов (потолки, таймауты, редакция секретов в логах), а не права самих плагинов.

Права **окон** — другая история и там сужение осмысленно, см. `../src-tauri/CLAUDE.md` → «Права окон».

## Статус архитектуры

Полноценный host-API (contribution points, `ctx`) спроектирован, но **отложен осознанно** — см. `../ideasAndTest/PLUGIN_HOST_API_PLAN.md`. Новую функциональность писать в ядро (`src/`), плагин оставлять тонким гейтом; код держать seam-ready по правилам из плана.
