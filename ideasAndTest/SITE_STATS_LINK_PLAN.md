# План: связать архив статистики с базой сайта

**Статус:** не реализовано. Правка на стороне программы маленькая, но без неё вся
дальнейшая сшивка держится на эвристике.

Сторона сайта — `innovation-hub/docs/PIPELINE.md`, части §14–15.
Схема архива — [`+STATS_SCHEMA_PLAN.md`](./+STATS_SCHEMA_PLAN.md) (v1, заморожена).
Модель очереди — [`DISTRIBUTED_QUEUE_PLAN.md`](./DISTRIBUTED_QUEUE_PLAN.md).

---

## Зачем

Сайт стал оркестратором: он находит файл в `IN`, собирает объект для обработки и
создаёт **задачу** со своим id. Машина эту задачу берёт, обрабатывает и по
завершении пишет строку в `options/_stats/$YYYY.$MM.jsonl` — с **другим** id,
который сгенерировала сама.

Получаются две несвязанные идентичности одного и того же события. «Эта задача
завершилась вот такой записью» становится догадкой по совпадению «проект + имя
файла + время», а не связью.

Хуже того, текущий id **непереносим между машинами**:

```rust
// settings_commands.rs:473 — db_register_found
let id = if !path_for_delete.is_empty() && !find_time.is_empty() {
    format!("{}:{}", path_for_delete, find_time)
} else if !path_for_delete.is_empty() {
    path_for_delete.to_string()
} else {
    format!("{}-{}", chrono::Utc::now().timestamp_millis(), uuid…)
};
```

`pathForDelete` — **локальный** путь. Один и тот же файл, обработанный на двух
машинах, получит два разных `itemId`. Для склейки архивов нескольких машин в одну
базу это прямая проблема: одна работа будет выглядеть как две.

## Решение

Идентификатор задаёт сайт, программа его принимает и передаёт дальше как есть.

Поле для этого **уже существует**: `sendFindItemToRegistrationProcessDatabase`
пишет результат регистрации в `_item.description.dbItemId`. Достаточно научиться
читать его на входе, а не только писать на выходе.

```
Сайт: создаёт задачу         →  task.id = "a1b2c3…"
      кладёт в объект        →  description.dbItemId = "a1b2c3…"
Машина: db_register_found    →  видит dbItemId → использует его, НЕ генерирует
        write_local_archive  →  "itemId": "a1b2c3…"
Сайт: импортирует _stats     →  processing_stats.item_id = "a1b2c3…" = tasks.id
```

Фолбэк остаётся: если `dbItemId` не пришёл (локальный прогон без сайта, старый
объект) — работает текущая логика. Обратная совместимость полная, поведение
одиночной машины не меняется.

## Правки

### A. Rust — принять переданный id

`src-tauri/src/commands/settings_commands.rs`, `db_register_found` (~строка 462).
Перед текущей цепочкой вычисления `id` добавить приоритетную ветку:

```rust
// Идентификатор, назначенный сайтом, если задача пришла из конвейера.
// Приоритет над локальным: pathForDelete — локальный путь, он разный на
// каждой машине, и склейка архивов нескольких машин по нему невозможна.
let site_id = desc.get("dbItemId").and_then(|v| v.as_str()).unwrap_or("").trim();

let id = if !site_id.is_empty() {
    site_id.to_string()
} else if !path_for_delete.is_empty() && !find_time.is_empty() {
    format!("{}:{}", path_for_delete, find_time)
} else if !path_for_delete.is_empty() {
    path_for_delete.to_string()
} else {
    format!("{}-{}", chrono::Utc::now().timestamp_millis(), uuid…)
};
```

Дальше ничего не меняется: `id` уже уезжает в `DbItemRecord.item_id`, а
`write_local_archive` пишет его в поле `itemId`. Схему v1 **не трогаем** —
`schemaVersion` остаётся 1, состав полей тот же, меняется только происхождение
значения.

### B. Frontend — прокинуть id в payload регистрации

`src/PROCESSING/utils/sendFindItemToRegistrationProcessDatabase.ts`. Сейчас
`payload.description` собирается из фиксированного списка полей, и `dbItemId`
в него не попадает — до Rust он не доезжает вообще:

```ts
const payload = {
    description: {
        curItem: d.curItem ?? '',
        …
        // Добавить: id задачи, если объект пришёл от сайта.
        dbItemId: String(d.dbItemId ?? ''),
    },
    plugins,
};
```

Строка `_item.description.dbItemId = itemId` после вызова остаётся как есть: при
пришедшем id она просто перезапишет его тем же значением.

### C. Сайт — положить id в объект

Сторона `innovation-hub`, `lib/pipeline/build-task.ts`: в `description` добавляется
`dbItemId: task.id`. Задача создаётся до сборки payload, поэтому id уже известен.

⚠️ Порядок важен: сейчас `buildTaskPayload` вызывается **до** `insertTask`, то есть
id ещё не существует. Придётся либо генерировать `id` заранее (`randomUUID()` перед
сборкой), либо собирать payload в два шага. Первое проще и не меняет форму.

## Чего в этом плане НЕТ

- **`database-sync` / пуш на URL.** `storage.onlineDb` в настройках так и остаётся
  заглушкой без Rust-обработчика. Базовый путь доставки статистики — сайт сам читает
  `_stats` из объектного хранилища: файлы уже пишутся, схема заморожена, в программе
  менять нечего, и они остаются резервной копией у пользователя. Пуш добавляется
  позже как ускорение, приёмник у него тот же.
- **Изменения схемы v1.** `plugins[]` и `srcSec` по-прежнему отложены в v2.
- **Отправка прогресса на сайт.** Это экшены `taskProgress` / `taskDone` машинного
  API — отдельная работа, описанная в `PIPELINE.md` §11. Здесь только идентичность.

## Почему именно так, а не иначе

**Почему не сшивать по «проект + файл + время».** Время находки и время старта
обработки различаются (это отдельная грабля, зафиксированная в
`+STATS_SCHEMA_PLAN.md`), имена файлов повторяются между проектами и прогонами, а
один файл можно обработать дважды осознанно. Любая такая сшивка ошибётся молча.

**Почему id назначает сайт, а не машина.** Задача возникает на сайте раньше, чем
машина о ней узнаёт, и живёт дольше: её могут переретраить на другой машине после
протухшей аренды. Идентичность должна принадлежать тому, кто владеет жизненным
циклом.

**Почему не новое поле, а `dbItemId`.** Поле уже есть в объекте обработки и уже
означает ровно это — «id этой работы в базе». Новое поле было бы вторым именем для
той же сущности.

## Проверка

1. Локальный прогон без сайта: `itemId` в `_stats` как раньше
   (`<pathForDelete>:<findTime>`), поведение не изменилось.
2. Прогон задачи из конвейера: `itemId` в `_stats` равен `tasks.id` на сайте.
3. Две машины обрабатывают задачи одного проекта: в `_stats` два файла
   (`2026.08.<host-a>.jsonl`, `2026.08.<host-b>.jsonl`), после импорта на сайте —
   строки из обоих, без дублей, `item_id` совпадают с задачами.
4. Повторный импорт того же файла не создаёт ничего нового
   (`ON CONFLICT (item_id) DO NOTHING` + курсор `lines_imported`).
5. `cargo test` и `npx tsc --noEmit` зелёные.
