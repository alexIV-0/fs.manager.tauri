# Ключи внешних сервисов и отчёт о потреблении — контракт с сайтом

**Статус:** 📖 контракт. По §1–4 **сторона сайта готова** (2026-08-28, миграция не
применена); **локальная сторона программы сделана и проверена вживую 2026-09-02** —
учётка заводится в ноде, ключ лежит в хранилище учётных данных ОС, плагин
`AIcomfyUI_v2` отработал на настоящем сервере. Серверная ветка выдачи ключей вживую
НЕ проверена: у сайта не применена миграция сейфа. По §6 (учётки, чей ключ) работа нужна с обеих
сторон: схема сайта разных учёток под одним сервисом пока не знает. План и обоснования:
`../innovation-hub/docs/VENDOR_SERVICES_PLAN.md`, запрос к сайту —
`../innovation-hub/docs/VENDOR_KEYS_CLIENT_REQUESTS.md`.

Закрывает две вещи разом:

1. **Ключи вендоров переезжают на сайт.** Программа перестаёт хранить их у себя и
   спрашивает перед задачей. Это `SECRETS_VAULT_SITE_PLAN.md`, модель B, но только для
   **сервисных** ключей — про аккаунты площадок ниже, §5.
2. **Плагины перестают присылать деньги** и присылают потребление. Это отменяет
   `BILLING_NODE_CONTRACT_PLAN.md` §3 «валюта себестоимости»: объявлять валюту незачем,
   если числа в валюте больше не уходят.

## 1. Ключи: две поверхности, один контракт

Токен у вас уже есть, второй заводить не надо — **машина и есть устройство**:

| Кто ходит | Куда | Как |
|---|---|---|
| Десктоп (`mch_…`) | `POST /api/storage/v1/vault` | `{ "action": "keys", … }` |
| Воркер парка (`rc_…`) | `POST /api/v1` | `{ "action": "vendorKeys", "props": { … }, "token": "rc_…" }` |

**Запрос — перед задачей и только по нужным ей сервисам:**

```jsonc
{
  "action": "keys",
  "services": ["eleven-labs"],        // слаги, до 50. Весь сейф не просить
  "known": { "eleven-labs": 6 }       // версии, которые уже лежат у вас
}
```

**Ответ:**

```jsonc
{
  "keys": [
    { "slug": "eleven-labs", "version": 7, "secret": "sk_…", "ttlSec": 21600 }
  ],
  "fresh": [],           // по этим версия актуальная — ключ по сети не поехал
  "unavailable": [],     // нет такого, на паузе, отозван или помечен proxy
  "vaultRevision": 42
}
```

Три правила, которые следуют прямо из формы ответа:

- **`known` — не оптимизация, а основной режим.** Совпала версия — секрет вообще не
  достаётся из базы и не пишется в журнал. Обычная работа выглядит как «спросил,
  получил `fresh`, взял из своего сейфа».
- **`unavailable` — не пустяк, но и не безусловный стоп.** Сервис на паузе или отозван:
  задачу с ним начинать не надо, вендор всё равно откажет, а деньги за попытку спишутся у
  него. Исключение — учётка, заведённая только локально (§6.5): про неё сайт не знает
  ничего, и `unavailable` по ней ожидаем. Стоп — когда ключа нет ни там, ни там.
- **`ttlSec` — потолок жизни копии**, а не рекомендация. Истёк — спрашиваем заново.

## 2. Отзыв: `vaultRevision` в heartbeat

Ответ на `heartbeat` теперь несёт `vaultRevision` — версию сейфа целиком, растущую на
любую правку секретов, паузу, смену TTL и отзыв.

```
heartbeat → { "ok": true, "vaultRevision": 43 }   // у нас было 42
          → спросить ключи заново
```

Это и есть механизм отзыва. Без него единственной защитой был бы `ttlSec`, и ключ,
отозванный на сайте, оставался бы рабочим на машине до конца срока. С ним — полминуты.

## 3. Сейф на машине

Шов у вас уже готов, и это самая приятная часть: плагины зовут IPC
(`account_get_token`), файла не читают, а в `account_commands.rs` прямо заложено «бэкенд
подменяемый (позже RemoteTokenStore/сайт)». Меняется бэкенд, не плагины.

Что должен уметь сейф:

| | Почему именно так |
|---|---|
| **Срок и версия у записи** | Кэш без срока — вечная копия, и тогда отзыв на сайте не отзывает ничего. А отзыв — единственное, ради чего ключи вообще переехали на сайт |
| **Шифрование на диске** (Keychain / DPAPI) | Сейчас `accounts/*.json` лежит открытым текстом. От этого и уходим |
| **Спрашивать свежесть, а не наличие** | Один дешёвый запрос перед задачей с `known`, а не запрос ключа на каждый вызов |
| **Только нужные сервисы** | Одна скомпрометированная машина не должна означать весь сейф |
| **Ключ не пишется в логи** | Логи уезжают на сайт. Окажись ключ в дампе запроса — он утечёт в наше же хранилище логов, и вычистить его оттуда нечем |
| **Офлайн: кэш жив — работаем, протух — внятная ошибка** | Ровно как в `SECRETS_VAULT_SITE_PLAN.md`, «Локальный кэш (вариант B2)» |

## 4. Потребление вместо `costUsd`

**Шлём сразу после ответа вендора, не дожидаясь `taskDone`.** Вендор уже получил свои
деньги; упади машина следом — расход всё равно должен быть учтён.

```jsonc
{
  "action": "usage",                      // или action: "vendorUsage" на /api/v1
  "taskId": "0f5c…",                      // тот же, что из claimTask
  "entries": [
    { "service": "eleven-labs", "unit": "char", "units": 8140 }
  ]
}
```

`unit`: `token` · `char` · `sec` · `image` · `run`.

```jsonc
{ "recorded": 1, "duplicate": 0, "unknown": [], "unpriced": [], "noRate": [] }
```

⚠️ **Ответ надо разбирать.** `unpriced` (цена меры не назначена) и `noRate` (нет курса
валюты) означают, что строка **не записана** — расход потерян, и её надо прислать позже.
`duplicate` — норма: повтор по той же тройке (задача, сервис, мера) расход не удваивает,
это держит уникальный индекс, так что переигрывать отчёт безопасно.

### Почему единицы, а не деньги

Цена живёт на сайте, у сервиса, с датой начала действия. Прайс, зашитый в плагин,
размножается по парку и разъезжается при первом же изменении цен у вендора — а проверить
присланное число нечем. Единицы же вендор подтверждает в ответе на вызов.

Побочный выигрыш: **смена тарифа у вендора перестаёт быть переустановкой плагинов.**

### Что делать с `totalCost`

Пока ничего: сайт берёт строки потребления, если они есть, и падает на `total_cost` из
архива, если их нет. Парк переходит не одномоментно. Когда плагины начнут слать `usage`,
`accumulatedCost` можно выключить — но не раньше, чем на сайте появится прайс сервиса,
иначе обработка станет бесплатной молча.

## 5. Чего этот контракт НЕ закрывает

**Аккаунты площадок (VK, YouTube, Telegram).** Там владелец секрета — конкретный
пользователь, а не мы, и нужна привязка «чей это токен» плюс device-enrollment из
`SECRETS_VAULT_SITE_PLAN.md` §1. Сейф на сайте к этому готов: колонка `owner_user_id`
заведена с первого дня, чтобы не пришлось потом сводить два хранилища и две процедуры
отзыва. Но эндпоинтов для аккаунтов пока нет — это отдельная работа, план сайта:
`../innovation-hub/docs/SOCIAL_POSTING_PLAN.md` §4.

**Прокси-вызовы.** У сервиса есть поле `delivery`, и значение `proxy` означает «ключ не
выпускается с сервера». Такие сервисы приходят в `unavailable`, и звать их должна была бы
сторона сайта — но этого пути пока нет. Пока все сервисы заводятся как `keys`.

## 6. Учётка, а не сервис: чей ключ и кто платит

Разобрано 2026-09-01. Закрывает две вещи, которые §1–4 обходили стороной: тестовые ключи
рядом с боевыми и ключ, который приносит сам клиент.

### 6.1 Сервис — каталог, учётка — секрет

`11labs-main` и `11labs-test` — **не два сервиса**. Два сервиса означают два прайса на
один и тот же ElevenLabs, и они разъедутся при первом изменении цен: обновят один,
забудут второй, и себестоимость тестов начнёт врать молча.

| | что это | что внутри |
|---|---|---|
| **Сервис** | каталог | адаптер, единицы, прайс, валюта, `delivery` |
| **Учётка** | именованный секрет под сервисом | метка, поля секрета, владелец, версия |

Прайс остаётся у сервиса: цена вендора не зависит от того, чьим ключом позвали.

⚠️ **Схема сайта этого пока не умеет** — `vendor_service_secrets` хранит версии одного
секрета, то есть ротацию, а не разные учётки. Это главный пункт запроса
(`innovation-hub/docs/VENDOR_KEYS_CLIENT_REQUESTS.md` §1). Требование приходит с двух
независимых сторон разом — «не смешивать тест с продом» и «клиент приносит свой ключ», —
поэтому просить его надо один раз и целиком.

### 6.2 В ноде — метка, не секрет

В `options.json` уезжает **имя учётки**. Иначе ключ окажется в файле проекта, в зеркале
на каждой машине и в хранилище сайта — мимо всего сейфа, ради которого §1–3 затевались.

Контрол уже существует, переизобретать не надо: `ddm`, в `options` динамический токен,
разделитель, внизу «добавить» — ровно как `#vkAccounts` в `plugins-dev/autoPostVK/ui.json`
(резолв — `useResolveOptions.ts`, он общий для любого `#`-токена). Новый источник —
`#services:<слаг>`; слаг живёт в `controlProps` этого же поля, **не в манифесте** —
`plugin.json` менять не нужно.

Форма добавления учётки — одна на все сервисы, поля берутся из описания сервиса в
каталоге. Двадцать вендоров не должны означать двадцать окон. VK и YouTube остаются со
своими окнами: там не поля, а процедура (webview, системный браузер, PKCE).

### 6.3 Галочка «показать на сайте» = политика, кто платит

Отдельного поля «чей ключ» не заводим. Его роль играет `exposedToSite` — он уже есть на
свойстве и уже уезжает в `options.json` (`src/NODE_WIN/definitions/types.ts`).

| галочка | значение поля | чей ключ | чьи деньги |
|---|---|---|---|
| снята | метка нашей учётки | наш | наши |
| стоит | заполняет клиент в настройках проекта на сайте | клиента | клиента |

Два правила, без которых это разъедется:

- **Включение галочки очищает значение.** Иначе забытый `11labs-test` останется лежать в
  `options.json`, и рано или поздно его прочтут как фолбэк — клиент поедет на нашей
  тестовой учётке. Дополнительно сайт при сборке предупреждает, если поле с галочкой всё
  же ссылается на нашу учётку.
- **Галочка действует только на задачи, собранные сайтом.** Локально она инертна: при
  настройке флоу я тестирую своими или нашими ключами независимо от неё.

### 6.4 Каталог слагов — пятый словарь

Руками слаг не пишем: опечатка даёт молчаливый `unknown` в отчёте потребления. Каталог
сервисов приезжает тем же каналом, что и общие словари (`src/Utils/settingsSync.ts`,
`SYNC_DOMAINS`), но **односторонним**: сервисы заводятся на сайте, мы их только читаем,
трёхстороннее слияние здесь ни к чему.

Одна локальная копия обслуживает трёх потребителей сразу: дропдаун в pluginBuilder при
написании ноды, резолв `#services:<слаг>` в самой ноде и гейт, собирающий список нужных
сервисов перед прогоном.

**Слаг неизменяем.** Переименование = новый сервис: старый слаг уже лежит в `ui.json`
собранных плагинов и в `options.json` чужих проектов.

### 6.5 Выдача — на задачу, а не на машину

Машина просит ключи **под конкретную задачу** (`taskId` в запросе), а чья это учётка,
решает сайт по владельцу задачи (`ownerEmail` едет и в самой задаче, и в `description`).

Фильтровать учётки на машине не надо и лучше сознательно не делать: отсеивание означает,
что на машине лежат ключи нескольких пользователей — ровно то, от чего защищает правило
«выдаём только нужное» из §3.

Отсюда же граница кэша: **метки — всегда, секреты — по нужде.** Список учёток безобиден и
должен приезжать целиком, иначе дропдаун при настройке пустой. Сами ключи — только тех
сервисов, которые нужны запускаемому флоу.

**Форма запроса (сайт реализовал 2026-09-02, форма ломающая — прежняя нигде не работала):**

```jsonc
{ "action": "keys",
  "services": ["eleven-labs"],
  "known":    { "eleven-labs": { "account": "main", "version": 7 } },  // ПАРА, не версия
  "accounts": { "eleven-labs": "main" },   // метка, если нода её знает из поля проекта
  "taskId":   "0f5c…" }                    // чью учётку выдать — решает сайт
```

Три следствия, каждое выстрадано:

- **`known` — пара «учётка + версия».** Нумерация у каждой учётки своя: `v3` у `main`
  совпал бы с `v3` у `test` и подтвердил бы машине чужой ключ как актуальный.
- **`keys[].fields` — объект**, а не строка `secret`: первый же вендор с парой полей
  (ключ + секрет подписи, OAuth-набор) сломал бы строковую схему.
- **`ambiguous[]`** — учёток несколько, а метка не названа. Сайт не выбирает за ноду:
  `main` вместо `test` заметили бы по счёту вендора. У нас это отдельная причина отказа
  в гейте, с текстом «выбери метку», а не общее «поле не заполнено».

Плюс `services[]` (`slug`, `baseUrl`, `account`, `hasSecret`) приезжает **всегда**, даже
когда секрет не менялся: адрес нужен на каждый вызов, а секрет — только при устаревшей
версии. Мы его пока не используем (адрес живёт в плагине), но он есть.

### 6.6 Гейт: нет ключа — задача не собирается

- **Проверка при сборке, не при `claim`.** Заведомо неисполнимая задача в очереди будет
  взята и возвращена каждой машиной по очереди, пока `attempts` не упрётся в
  `maxAttempts` — и умрёт как «превышены попытки», хотя причина была известна заранее.
  Правильный исход: проект на паузу, жёлтый треугольник на карточке с причиной.
- **Клиентская проверка всё равно нужна**: ключ могли отозвать между сборкой и
  выполнением. Нужен третий исход помимо `failed` (тратит попытку) и `release`
  (возвращает молча, и задача уедет на следующую машину с тем же итогом) — «ключа нет,
  другие тоже не смогут, гасите проект».
- **Причина — код и слаг сервиса, не текст.** Состояние проектов показываем и мы у себя;
  разбирать чужую строку ради значка — гарантированный источник расхождений.
- **На своих проектах** гейт целиком наш и срабатывает до старта витка: недоделанный
  наполовину ролик хуже невзятой задачи.
- **Задача на локальном ключе в парк не уезжает** — локальный ключ есть только на моей
  машине по определению.
- **Отзыв посреди работы текущую задачу не рвёт.** Доделываем, следующую не берём.

### 6.7 Локальный прогон нашим ключом

Стоимости на сайте не появляется — обработка локальная, продавать нечего. Но у вендора
деньги списались, и суточная сверка (остаток вчера − остаток сегодня ≈ сумма потребления)
увидит расход без строк. Это ровно тот сигнал «ключом пользуется кто-то ещё», ради
которого сверка и заведена: каждый локальный тест будет давать ложную тревогу, пока на
неё не перестанут смотреть.

Поэтому `usage` с локальных прогонов **шлём тоже, но без `taskId`**: в биллинг такие
строки не идут, в сверку идут.

### 6.8 Рефреш и сроки

Момент обновления токена отдельно помнить не надо — он уже выражен версией секрета: сайт
обновил → версия выросла → `vaultRevision` в heartbeat → машины перезапросили.

Помнить надо **два разных срока**, их легко перепутать: `ttlSec` — сколько нам разрешено
держать копию (это про отзыв), `exp` самого токена — когда он умрёт у вендора. Идти за
новым по меньшему из двух.

Рефрешер — **ровно один, и это сайт**: часть вендоров инвалидирует старый refresh при
использовании, и десять машин начнут выбивать друг друга. Следствие приятное:
`refresh_token` на машину не выдаётся вовсе, машине едет только короткий access. То, что
нельзя потерять, у нас на диске не лежит.

⚠️ Наш YouTube под это правило **не попадает**: там `refresh_token` принадлежит
пользователю по модели BYO и рефрешим мы сами (`youtube_auth_commands.rs`). Это аккаунты
площадок, §5, другая ветка — не смешивать.

### 6.9 Инциденты

Ошибки и предупреждения этого контура (ключ протух в момент вызова, вендор отказал, у
клиента кончились деньги, задача возвращена без ключа) идут в журнал на сайте — не потоком
логов, а узким API «инцидент». Иначе половина картины окажется в логах, половина в
журнале, а треугольник будет знать только то, что заметил сайт.

Предпроверка баланса перед постановкой задачи полезна, но **опциональна**: остаток по API
отдают не все вендоры, проверка — снимок (может пройти и кончиться на третьем ролике,
путь ошибки всё равно нужен), и звать её надо раз в период на ключ с кэшем, а не на
каждый ролик.
