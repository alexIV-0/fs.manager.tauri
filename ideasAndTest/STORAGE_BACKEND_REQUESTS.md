## 0. Как мы поняли разделение — просьба подтвердить

| | Бэкенд | Локальный клиент |
|---|---|---|
| Каталог, журнал, курсоры | **да** | держит локальную копию |
| Права, ключи R2, подписи, раскладка ключей | **да** | не имеет ключей вообще |
| **Передача байтов** | нет | **да, напрямую в R2 по presigned** |
| Что лежит на диске машины, кэш, вытеснение | нет | **да** |

Это следует из вашей же строки «Bytes go directly to/from R2, not through the API» и из устройства
`/presign`. Сервер физически не может залить файл, которого у него нет, — файл лежит на диске
машины. Если это понимание неверно, надо обсудить до начала работ.

**Ключи бакета (`S3_KEY_ID` / `S3_SECRET_KEY`) нам не нужны и мы их не используем.** Работать ими
напрямую означало бы писать в R2 мимо каталога: строк в Postgres нет, журнал не пополнен, сайт файлов
не видит до ручного `/reindex`. Вместо них нужен **machine token с `projectId: null`**.

## 1. Блокеры и просьбы — по приоритету

### ✅ 1.0. Список проектов по machine token — СДЕЛАНО

`/tree` и `/delta` требуют `projectId`. **А узнать, какие проекты существуют, программе неоткуда:**
`GET /api/projects` авторизуется через `requireUserApi` — только сессия, machine token не пустят.

Получается замкнутый круг: дерево проекта получить умеем, а список проектов — нет. Ни колонку с
главными папками, ни список проектов наполнить нечем.

**Просьба:** эндпоинт со `requireStorageApi`.

```
GET /api/storage/v1/projects
→ { "clients":  [ { "id": "…", "displayName": "Мегафон" } ],
    "projects": [
      { "id": "…", "name": "Реклама Q3", "clientId": "…",
        "groupName": "personal", "isActive": true, "isPaused": false,
        "updatedAt": "…" }
    ] }
```

Для токена с `projectId != null` — отдавать только этот проект. Для ADMIN — все (или с фильтром по
владельцу).

**Это самый первый по срочности пункт: без него программа не сделает ни одного полезного запроса.**

### ✅ 1.0.1. Клиентский уровень — СДЕЛАНО

В нашей программе интерфейс трёхуровневый, и это же нужно онлайн:

```
клиент  →  проект  →  IN / OUT / options / свои папки
```

В бэкенде сейчас два уровня: плоский список проектов на пользователя. `group_name` для этого не
годится — это фиксированный enum `personal | shared | tools | archive`, категория интерфейса сайта,
а не «папка под клиента».

**Ключевое: раскладку в бакете менять НЕ надо.** Раз `writeRename` не трогает `s3Key`, иерархия,
которую видит человек, вообще не обязана совпадать с путями. Клиентский уровень — это связь в БД:

```sql
CREATE TABLE clients (
    id           TEXT PRIMARY KEY,
    user_id      TEXT NOT NULL REFERENCES users(id),
    display_name TEXT NOT NULL,        -- меняется свободно
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

ALTER TABLE projects ADD COLUMN client_id TEXT REFERENCES clients(id);
```

Ключи остаются как есть: `innohub/projects/{userId}/{projectId}/{folderPath}/…`

Что получается:

| Уровень | Где имя | Цена переименования |
|---|---|---|
| Клиент | `clients.display_name` | `UPDATE` одной строки, **0 операций в R2** |
| Проект | `projects.name` | `UPDATE` одной строки, **0 операций в R2** |
| Папки внутри проекта | `project_files.name` / `folder_path` | `writeRename`, **0 операций в R2** |

**Почему клиента не стоит класть в путь.** Вариант `innohub/{clientId}/{projectId}/…` выглядит
логично, но делает **переезд проекта к другому клиенту** перекладыванием всех объектов проекта. При
связи в БД это `UPDATE projects SET client_id` — одна строка. Плюс менять раскладку сейчас означает
миграцию уже написанного, а выигрыша нет: бакет всё равно нечитаем глазами, там UUID.

**Просьба:** таблица `clients`, `projects.client_id`, и отдавать `clientId` + список клиентов в
эндпоинте из 1.0. Если решите, что клиентский уровень пока не нужен — скажите, начнём с плоского
списка проектов и добавим позже, это не блокер.

### ✅ 1.1. `rename` под `/api/storage/v1` — СДЕЛАНО

Логика **уже написана**: `writeRename` в `lib/storage/write-path.ts:426`. Она делает ровно то, что
нужно, и делает хорошо — `s3Key` не трогается, файл это `UPDATE name, folder_path`, папка это один
`UPDATE` со `substr` по всем потомкам. Переименование папки с 500 ГБ внутри = один SQL-запрос.

Проблема только в доступе: `writeRename` выставлен на legacy-роутах
(`app/api/projects/[id]/files/route.ts`, `app/api/projects/[id]/drive/files/[fileId]/route.ts`), а они
авторизуются через `requireUserApi` — **только сессия, machine token туда не пустят**.

**Просьба:** тонкий роут `POST /api/storage/v1/rename` с `requireStorageApi` +
`requireOwnedProjectAccess`, вызывающий существующий `writeRename`.

```
POST /api/storage/v1/rename
{ "projectId": "…", "fileId": "…", "name": "new.mov", "folderPath": "OUT", "eventId": "…" }
→ 200 { "file": ProjectFile }
```

Переименование и перенос — ежедневные операции у нас. Сейчас они недоступны.

### ⬜ 1.2. `copy` — файла и папки, в том числе между проектами

Отсутствует полностью. `writeRename` **переносит**, а не копирует.

Наш реальный сценарий: есть папка `music` в одном проекте, надо получить её копию в другом. Файлы
должны стать **независимыми** — удаление в одном проекте не должно затрагивать другой.

В R2 это серверный `CopyObject` (байты через нашу машину не идут) + новые строки в `project_files` +
события в журнал. Между проектами меняется префикс ключа.

```
POST /api/storage/v1/copy
{ "projectId": "…", "fileId": "…", "toProjectId": "…", "toFolderPath": "music", "eventId": "…" }
→ 200 { "files": ProjectFile[] }   // для папки — все созданные потомки
```

Оговорка про лимит: `CopyObject` не принимает объекты больше 5 ГиБ, для крупных нужен
`UploadPartCopy`. У нас файлы обычно меньше, но заложить обработку стоит.

### ⬜ 1.3. Multipart-загрузка — не срочно, но потолок жёсткий

`/presign` отдаёт **один** PUT-URL. Одиночный `PUT` в S3/R2 ограничен **5 ГиБ** и не возобновляется:
оборвалось на 4 ГБ из 4.5 — начинаем с нуля.

Наши файлы обычно меньше 5 ГБ, поэтому **сейчас это не блокер**. Но потолок физический, и на
нестабильной сети докачка нужна начиная примерно с гигабайта.

```
POST /api/storage/v1/multipart/create        { projectId, folderPath, fileName, contentType }
                                             → { uploadId, s3Key }
POST /api/storage/v1/multipart/presign-part  { projectId, uploadId, s3Key, partNumber }
                                             → { url }
POST /api/storage/v1/multipart/complete      { projectId, uploadId, s3Key, parts: [{partNumber, etag}] }
                                             → { file: ProjectFile }     // сам делает upsert + журнал
POST /api/storage/v1/multipart/abort         { projectId, uploadId, s3Key }
```

`complete` заменяет `/notify` — объект уже подтверждён операцией завершения.

**Отдельно, про гигиену бакета:** брошенные multipart-загрузки оставляют залитые части, которые
занимают место и **не видны в листинге объектов**. Нужно lifecycle-правило
«abort incomplete multipart uploads через 7 дней». Это настройка бакета, то есть ваша сторона.

### ✅ 1.4. `origin_mtime` — СДЕЛАНО (принимается в `/notify`)

Колонка `project_files.origin_mtime` в миграции есть, но в теле `/notify` поля для неё нет — значит
она всегда `NULL`.

Практическое следствие: «когда файл изменён» превращается в `updated_at`, то есть «когда бэкенд
зарегистрировал заливку», а не когда файл реально создан на машине. Для показа в интерфейсе это
разные вещи.

**Просьба:** принимать `originMtime` (unix seconds) в `/notify` и в `multipart/complete`.

### ✅ 1.5. `content_hash` — СДЕЛАНО (принимается в `/notify`)

Колонка есть, в примерах ответов `null`.

Он нужен нам для надёжного ответа «моя локальная копия устарела или нет». Сейчас сравниваем по
`etag`, и это работает — **но только пока нет multipart**: у multipart-объектов `etag` перестаёт быть
хэшем содержимого (составное значение с суффиксом `-N`).

**Просьба:** либо считать `content_hash` на стороне бэкенда, либо принимать его от клиента (мы можем
посчитать sha256 при заливке и прислать в `/notify` — нам это почти бесплатно, файл всё равно
читается).

### ✅ 1.6. Эндпоинт capabilities — СДЕЛАНО

Пока часть операций отсутствует, клиент гасит соответствующие пункты интерфейса по флагам. Сейчас
флаги придётся прописать константами, а потом не забыть снять.

```
GET /api/storage/v1/capabilities
→ { "multipart": false, "rename": true, "copy": false, "sharing": false, "apiVersion": 1 }
```

Дешёво, а снимает целый класс рассинхрона между вашим релизом и нашим.

### ⬜ 1.7. Глобальная `/delta` без `projectId` — удобство

Сейчас `/delta` требует `projectId`, то есть при десяти открытых проектах — десять поллингов.
Индекс `storage_changes_seq_idx` для этого уже есть.

```
GET /api/storage/v1/delta?since=…        // без projectId: все доступные пользователю проекты
```

Не блокер, просто экономия запросов.

### 🔴 1.11. `/projects` не отдаёт `userId`

`serializeProject` (`app/api/storage/v1/projects/route.ts:57`) собирает ответ без `userId`, хотя
объект проекта его содержит — рядом, в ветке scoped-токена, бэкенд им же проверяет доступ.

Первый уровень зеркала — **владелец** (`projects/{userId}/{projectId}/…`), и группировать больше
не по чему: `client_id` в живых данных не заполнен ни у одного проекта. Без поля все проекты (под
ADMIN-токеном — проекты всех пользователей) сваливаются в одну папку.

Просим: `userId: project.userId` в `serializeProject` плюс массив `users: [{ id, displayName }]` —
тем же видом, что уже сделан для `clients`. Имя нужно только для подписи папки.

До фикса владелец добывается из ключа: сначала из индекса (бесплатно), а если ключей нет — из
ответа **`/presign` на PUT**, который бэкенд строит из владельца, не создавая объекта. Один запрос,
ноль байт, работает и у пустого проекта. Поле из ответа имеет приоритет, поэтому после правки
обходной путь перестанет вызываться сам.

### 🔴 1.8. Переименование не попадает в журнал

`writeRename` (`lib/storage/write-path.ts:443`) журналит только внутри `if (oldKey !== newKey)`
(`:509`), а ключи берутся из `s3_key` (`:494`), который при переименовании не меняется.

- **файл:** `oldKey === newKey` → ни одного события, `last_seq` не двигается. `/delta` о
  переименовании не расскажет никогда;
- **папка:** `folder_path` потомков правится одним `UPDATE` (`:472`), событие пишется только на саму
  папку.

Для нас это не косметика: из логического пути строится путь на диске, поэтому чужое переименование
означает «файл исчез из проекта», а обработка получает путь к несуществующему файлу.

Просим: журналить `put` для переименованной строки всегда (и по потомкам для папки) — как уже
сделано в каскаде `writeFileDelete` (`:312`), — **либо** ввести `op: "rename"` с `from`/`to`, тогда
переименование папки это одно событие, а префикс мы перепишем у себя (`file_id` стабилен, качать
ничего не нужно).

До фикса: свои мутации применяем в индекс сами, чужие видим только после полного `/tree`.

### 🔴 1.9. `/reindex` удаляет строки под `options/`

В `reindexProject` (`:634`) ключи с `/options/` исключены из `remoteKeys` (`:660`), а финальный проход
(`:741`) удаляет **все** строки, которых нет в `remoteKeys`, с журнальным `op: "delete"`.

Строки под `options/` появляются от обычной заливки (`/presign` → PUT → `/notify` создаёт строку),
а у нас туда пишется статистика обработки — `options/__stat/<год>.<месяц>.jsonl`. Первый же
`/reindex` объявит её удалённой, хотя объект в R2 останется.

Просим: пропускать `options`-строки в проходе удаления (функция `isOptionsKey` уже есть —
`lib/storage/keys.ts:47`), либо не исключать `options/` из листинга.

### 🟡 1.10. `/reindex` пишет физическое имя

`const name = key.slice(key.lastIndexOf("/") + 1)` (`:688`) — то есть `{uuid}-{имя}`. `/notify` при
этом пишет логическое имя, которое присылает клиент. Один и тот же файл называется по-разному в
зависимости от того, каким путём попал в каталог; это имя видим и мы (из него строится имя на диске),
и сайт.

Не блокер, пока реиндекс не запускают. Но зовут его как раз тогда, когда «что-то разошлось».

## 3. Что мы гарантируем со своей стороны

Чтобы каталог не расходился с бакетом:

1. **Никогда не пишем в R2 иначе, чем по presigned URL, полученному от вас.** Ключей бакета у нас нет.
2. **Всегда вызываем `/notify` после успешного PUT** (или `multipart/complete`). Без подтверждения не
   считаем файл залитым.
3. **Присылаем точный `contentType`**, где он известен (`video/mp4`, `video/quicktime`), а не
   `application/octet-stream` по умолчанию — чтобы сайт понимал, что можно проиграть в браузере.
4. **Запрашиваем presign в момент старта передачи**, а не пачкой заранее: TTL по умолчанию час, и
   пачка ссылок на большую очередь протухнет.
5. **Курсор храним на проект**, `truncated` обрабатываем полным `/tree`.
6. **`eventId` присылаем** во все мутирующие вызовы для идемпотентности (у вас `storage_changes.event_id`
   уникальный — используем это).
7. **Не полагаемся на роль ADMIN как на данность.** 403 показываем пользователю как «нет прав», а не
   как сетевую ошибку.

## 5. Расшаривание — на будущее, нас не блокирует

Мы увидели, что расшаривания сейчас нет: `findProjectForUser` — алиас на `findOwnedProject`
(`WHERE id = $1 AND user_id = $2`), таблицы участников нет. То есть второй пользователь получит 404
на `/tree`.

Нам это **не мешает**: `role === "ADMIN"` пробивает оба guard'а, программа ходит под непривязанным
админским токеном.

Но шов у вас оставлен аккуратно, и это стоит отметить: читающие эндпоинты (`/tree`, `/delta`,
`/presign` GET, `/sidecars` GET) уже зовут `requireProjectAccess`, пишущие —
`requireOwnedProjectAccess`. Значит для расшаривания достаточно: **(1)** таблица участников,
**(2)** переписать `findProjectForUser` — чтение для гостя включится само, **(3)** для записи
заменить бинарное «владелец / не владелец» на проверку роли.

Наши наработки по ролям (`viewer` / `downloader` / `editor` / `uploader` / `owner`, разрешение
конфликтов по самому длинному совпавшему scope, ссылки наружу через токен в БД вместо presigned)
лежат в [`R2_SHARING_PLAN.md`](./R2_SHARING_PLAN.md) — берите, если пригодится.
