# Синхронизация настроек с сайтом — план для программы

Словари, которые до сих пор жили только здесь, но нужны и сайту: типы файлов с
расширениями, цвета типов нод и типов данных, пользовательские маски путей.

Контракт и обоснование архитектуры — в `innovation-hub/docs/SETTINGS_SYNC.md`.
Этот документ описывает только сторону программы.

**Статусы:** ✅ работает · 🔧 частично · ⬜ не сделано

> **Сверено с кодом сайта 2026-08-14: серверная сторона готова целиком.** Есть таблица,
> репозиторий `lib/repositories/automation-settings.ts`, все три поверхности
> (`GET`/`PUT /api/storage/v1/settings` под нашим `mch_`-токеном, `getSettings`/`putSettings`
> на `POST /api/v1`, `/api/admin/settings`), и `settingsRevision` уже приходит в ответе
> `delta`. Блокер теперь только на нашей стороне.

---

## 1. Что меняется по сути

Сегодня словари — единоличная собственность программы. Становятся: **сервер главный,
локальные файлы — рабочая копия**, которая продолжает полностью работать без сети.

Ключевое, чего нельзя потерять при реализации: программа остаётся самодостаточной.
Не подключена к серверу — ведёт себя ровно как сейчас, ни одного запроса не делает.

## 2. Состояний связи три, а не два

| состояние | признак | поведение |
|---|---|---|
| **не подключен** | `StorageConfig::is_configured()` == false | всё как сейчас, ни тянем, ни шлём |
| **подключен, связь есть** | последний запрос успешен | правка → `PUT /settings` → применяем ответ |
| **подключен, связи нет** | сконфигурирован, но запрос не прошёл | правки копятся с флагом `dirty`; при возврате связи **сначала отдаём**, потом применяем |

Разница между первым и третьим — **настройка, а не доступность сервера**. Если их не
различать и на любом восстановлении связи тянуть с сервера, правки, сделанные пока
лежала сеть, затрутся молча. `is_configured()` в
[storage/client.rs](../src-tauri/src/storage/client.rs) уже даёт ровно этот признак.

## 3. Что синхронизируем, а что нет

Четыре домена из [pathPattern_store.ts](../src/Store/MainWin/pathPattern_store.ts):

| стор | домен | синхронизируется | не синхронизируется |
|---|---|---|---|
| `typeOfFile_store` | `fileType` | `name`, `path` (расширения), `color` | `id`, `inactivePath` |
| `typeOfNodes_store` | `nodeType` | `name`, `color` | `id`, `path`, `inactivePath` |
| `typeOfdata_store` | `dataType` | `name`, `color` | `id`, `path` (пуст) |
| `pathPattern_store` | `pathPattern` | `name`, `path` (сегменты масок) | `id` |
| `programPathPattern_store` | — | **ничего** | весь стор |
| `folderPath_store` | — | **ничего** | весь стор |

Две последние строки критичны: там пути к ffmpeg и After Effects, они машинно-локальные.
Стор `programPathPattern_store` устроен так же и лежит в том же файловом механизме, что
`typeOfFile_store`, — его легко зацепить заодно.

`path` у `nodeType` не синхронизируется по той же причине: там имена **установленных**
плагинов, наполняется событиями `PLUGIN_ENABLED`/`PLUGIN_DISABLED`, у каждой машины
свой набор. Синхронизируется только цвет.

**Оговорка по `pathPattern`:** это единственный домен без `optionsOnly` в UI
([TabPaths.tsx](../src/MAIN_WIN/options/tabs/TabPaths.tsx)) — в сегменты можно вписать
не только маску (`$localFolder`), но и абсолютный путь через «Custom Folder…». Такой
сегмент машинно-зависим. Синхронизируем как есть, но в UI помечаем предупреждением.

## 4. Ключ — `name`, не `id` ⬜

`id` на сервер не уходит вовсе. У дефолтов он человекочитаемый (`video`), у
пользовательских — nanoid, то есть на второй машине будет другой.

Идентичность по имени — не новое ограничение, а то, что уже есть: графы ссылаются на
тип по имени (`searchType: "video"`), `getFileTypeByExt` ключует по имени, слияние
дефолтов идёт по имени (`defaultNamesSet` в `createPathPatternStore`). Переименование
типа ломает графы уже сегодня.

При приёме с сервера локальный `id` сохраняется для существующих записей (иначе
переедут React-ключи и dnd), новым генерится `nanoid()`.

**Порядок значим.** `getFileTypeByExt` возвращает первое совпадение: одно расширение в
двух типах — победит верхний. Порядок массива синхронизируется вместе с содержимым.

## 5. Что сделать

### 5.1 Заглушить петлю записи ⬜

Сейчас любой сеттер стора сразу пишет вниз (`tauriSave` / `saveToLocalStorage`).
Изменения, **пришедшие с сервера**, повторно уходить наверх не должны.

Нужен путь `applyRemote(domain, elements)`, который:

1. кладёт состояние в стор и в локальное хранилище;
2. обновляет базу (§5.3) той же операцией;
3. не поднимает `dirty`.

Без этого первая же входящая правка улетит обратно как исходящая.

### 5.2 Три домена живут только в localStorage 🔧

`typeOfFile_store` и `programPathPattern_store` уже лежат файлами в `app_data_dir`
(`fileTypes.json`, `programPaths.json` — [settings_commands.rs](../src-tauri/src/commands/settings_commands.rs)).
А `typeOfNodes`, `typeOfData`, `pathPattern` — только `localStorage`.

Для синхронизации это не блокер (слияние живёт в renderer), но localStorage у webview
чистится вместе с кэшем, и тогда пользовательские маски путей пропадут молча. Рекомендую
перевести три домена на файлы по образцу `file_types_get/set` — отдельным шагом, до
включения синхронизации.

### 5.3 База для трёхстороннего слияния ⬜

Файл `app_data_dir/settingsSyncBase.json`: снимок документа на момент последней
успешной синхронизации + `revision`.

Слияние по каждой записи (ключ — `name`) и каждому полю:

| ситуация | результат |
|---|---|
| локально == база | берём серверное |
| на сервере == база | берём локальное |
| разошлись, поле `path` | объединение множеств |
| разошлись, поле `color` | серверное |
| добавлено с одной стороны | добавляем |
| удалено с одной, с другой не менялось | удаляем |
| удалено с одной, изменено с другой | **оставляем**, пишем в лог |

Объединение для `path` работает честно потому, что реальная операция пользователя —
«добавить расширение в тип». Добавление в множество коммутативно и идемпотентно.
Неоднозначны только удаления, и их прикрывает `isDefault`: дефолтный тип удалить нельзя.

**Грабля: сравнивать надо нормализованное.** Сервер приводит значения к своему виду
(`normalizeColor` в `automation-settings.ts`): `#0a84feff` → `#0a84fe`, `rgb(99, 214, 81)` →
hex, расширения в нижний регистр без ведущей точки, дубли схлопываются. База — это снимок
серверного документа, а локальный стор держит сырой формат. Сравнишь как есть — **каждая**
запись будет выглядеть изменённой с обеих сторон, и по правилу «цвет — серверный» реальные
правки пользователя начнут молча теряться. Значит порт нормализации на нашу сторону — часть
слияния, а не деталь оформления.

### 5.4 HTTP-команды ⬜

Токен и адрес живут в Rust ([storage/config.rs](../src-tauri/src/storage/config.rs)),
поэтому запросы идут оттуда, а не из renderer. В
[storage_commands.rs](../src-tauri/src/commands/storage_commands.rs) добавить пару
поверх `StorageApi`:

- `storage_settings_get(domains: Option<Vec<String>>) -> { revision, domains }`
- `storage_settings_put(base_revision, domains) -> Ok{revision,domains} | Conflict{revision,domains}`

`409` — не ошибка транспорта, а нормальный ответ: его надо донести до renderer
отличимым от сетевого сбоя, иначе слияние не запустится.

### 5.5 Триггер «словарь изменился» ⬜

Отдельный поллинг не нужен. Демон и так зовёт `GET /delta` каждые 3 секунды
([daemon.rs](../src-tauri/src/storage/daemon.rs), `PULSE`). Сайт добавляет в ответ
`settingsRevision` — счётчик глобальный, от проекта не зависит.

Отличается от локального — Rust эмитит событие `settings-revision-changed`, renderer
тянет `storage_settings_get`. Плюс безусловное чтение при подключении: если проектов
нет, `delta` не вызывается и словарь иначе не приедет.

### 5.6 UI ⬜

В [TabTypes.tsx](../src/MAIN_WIN/options/tabs/TabTypes.tsx) и
[TabPaths.tsx](../src/MAIN_WIN/options/tabs/TabPaths.tsx) — строка состояния:
«не подключено» / «синхронизировано, ревизия N» / «нет связи, N локальных правок» и
кнопка ручной синхронизации.

Секции `programmPathPattern` и `folderPathStore` в `TabPaths` помечаются как локальные
явно, иначе неочевидно, почему одни настройки едут на сервер, а соседние — нет.

## 6. Отдельно: снимок словаря типов в `options.json` ⬜

Не относится к синхронизации, но блокирует конвейер уже сейчас
(`innovation-hub/docs/PIPELINE.md` §6): сайт пропускает проект с причиной
`no-search-exts`.

Узел `mainSearch` хранит `searchType` («video»), а расширения к нему — в
`typeOfFile_store`, которого у сайта нет.

**Решение: при сохранении графа кладём в `options.json` весь словарь типов** — соседним
ключом рядом с `nodes`/`edges`:

```jsonc
{ "nodes": [...], "edges": [...], "fileTypes": { "video": ["mp4","mov",…], "audio": ["mp3","wav"], … } }
```

### Почему словарь целиком, а не `searchExts` у одной ноды

Решено 2026-08-14. Расширения нужны не только `mainSearch`: граф уходит в другую папку
проекта за аудио, потом за текстом или скриптом. `getFileFromFolder` уже сегодня читает
**весь словарь** — `_description.typeOfFile?.[searchType]`. Проставить одно поле у
`mainSearch` значило бы закрыть дырку для сборщика задач и оставить её для всех остальных
нод.

Объект в нужной форме уже собирается — [findFilesForSingleFolder.ts:94](../src/PROCESSING/findFilesForSingleFolder.ts):
`Object.fromEntries(typeOfFileRaw.map(t => [t.name, t.path]))`. Вынести в общую функцию и
звать из обоих мест, иначе снимок и исполнение разъедутся молча.

### Три решения по реализации

**Читать в NODE_WIN через `commands.fileTypesGet()`, а не из стора.** Окна — разные
JS-realm'ы, `loadFromTauri` зовётся из `AppMain` в MAIN_WIN. Файл `fileTypes.json` и есть
SSOT; так не нужен ни broadcast между окнами, ни открытое главное окно.

**Соседний ключ, а не свойство ноды.** Сайт читает свойства через `nodeProps` (только
`data.properties[].controlProps.value`), но класть туда вычисляемый снимок — значит завести
скрытые свойства, которых в модели нет, и новую ветку в
[validation.ts](../src/NODE_WIN/utils/validation.ts): незнакомый `controlType` возвращает
`false` и делает ноду невалидной навсегда. Ключ верхнего уровня редактор при загрузке просто
игнорирует, а `structSig` в `SaveButton` смотрит только ноды и рёбра — лишнего «dirty» не
будет.

**Единая точка сохранения.** Мест два и они дублируют друг друга —
[SaveButton.tsx:105-117](../src/NODE_WIN/layout/SaveButton.tsx) и
[TopPanel.tsx:38-42](../src/NODE_WIN/layout/TopPanel.tsx). Вынести `saveFlow(path, flow)`;
снимок ставится **до** записи, иначе поле будет появляться при сохранении одной кнопкой и не
появляться другой.

### Роли снимка и словаря

| | снимок в `options.json` | словарь на сервере |
|---|---|---|
| отвечает на вопрос | чем этот проект **исполнялся** | какие типы **бывают сейчас** |
| кто читает | сборщик задач, машина | редактор нод, дефолты машин |
| когда меняется | пересохранением графа | правкой настроек |

Снимок делает папку самодостаточной: проект + `options.json` = полная инструкция, без
обращения к настройкам конкретной машины. На этом стоит распределённая модель.

**Приоритет: словарь первым, снимок — страховка** (решено 2026-08-14). Сайт резолвит
`searchType` по своему синхронизированному словарю, а к снимку обращается, когда типа в
словаре нет или проект живёт вне синхронизации.

Обратный порядок (снимок главный) означал бы, что правка настроек не доезжает до уже
нарисованных проектов, пока каждый не пересохранишь. Лечится это либо ручной кнопкой
«применить ко всем», либо массовой перезаписью `options.json` — а перезапись нельзя:
каждая запись журналируется в `storage_changes` и тянет заливку в R2, то есть правка одного
цвета обернулась бы сотнями облачных операций. Кнопку решили не заводить, значит главным
остаётся словарь.

Снимок при этом не лишний: он держит проект работоспособным, когда синхронизации нет вовсе,
и когда тип из словаря удалили, а граф на него ссылается.

### `typeOfFile` перестаёт быть машинно-локальным

В `build-task.ts` на сайте записано, что `typeOfFile` вместе с `programmPath`, `folderPath`,
`pathAliases` машинно-локален и заполняется машиной. После синхронизации это неверно:
`typeOfFile` — единственный из четырёх, который является **общей конвенцией**, а не
свойством машины; у всех машин он обязан совпадать, в том и смысл. Пути к ffmpeg и After
Effects остаются за машиной, а типы файлов сайт теперь кладёт в задачу сам — из снимка
проекта.

## 7. Порядок

| # | шаг | блокирует |
|---|---|---|
| 1 | снимок `fileTypes` при сохранении графа (§6) | конвейер на сайте — делать первым |
| 2 | три домена на файлы (§5.2) | нет, но лучше до синхронизации |
| 3 | `applyRemote` без петли (§5.1) | всё остальное |
| 4 | база + слияние (§5.3) | работу в офлайне |
| 5 | команды `storage_settings_*` (§5.4) | — |
| 6 | событие из `delta` (§5.5) | — |
| 7 | UI состояния (§5.6) | — |

Шаг 1 самостоятелен, от синхронизации не зависит и разблокирует конвейер сразу.

Грабля порядка на шаге 2: `nodeType.path` наполняется событиями `PLUGIN_ENABLED` при
старте программы. `loadFromTauri` обязан отработать **раньше** этих событий, иначе файл
затрёт список установленных плагинов.

## 8. Что синхронизация НЕ меняет

Правило «ничего машинно-локального в задаче» (`PIPELINE.md` §5) остаётся в силе.
`typeOfFile`, `programmPath`, `folderPath`, `pathAliases` машина по-прежнему
подставляет сама в момент исполнения задачи — см.
[findFilesForSingleFolder.ts:94-107](../src/PROCESSING/findFilesForSingleFolder.ts).
Синхронизируются *настройки*, а не содержимое задачи.
