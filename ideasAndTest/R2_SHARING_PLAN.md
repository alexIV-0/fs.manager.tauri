<a name="граница"></a>

## 1. Правило границы: производные данные против авторских

> **Каталог можно `TRUNCATE` в любой момент. Права — нельзя восстановить никогда.**

| | Каталог (`objects`, `changes`, `projects`) | Права (`users`, `grants`, `share_links`) |
|---|---|---|
| Природа | **производные** данные | **авторские** данные |
| Восстановимость | полным обходом бакета, в любой момент | **никогда** |
| Кто создал | R2 | человек |

**Если повесить `shared_with` колонкой на таблицу `projects`, то штатная операция обслуживания
«пересобрать каталог с нуля» уничтожит все расшаривания.** Это не стилистика, это потеря данных.

**Зависимость строго односторонняя:** права ссылаются на каталог, каталог про права не знает ничего.

### Где физически

| Данные | Где |
|---|---|
Каталог (`objects`, `changes`, `projects`, `project_plugins`) | Cloudflare D1 — проекция бакета |
| Права (`users`, `grants`, `share_links`, аудит) | **основная БД сайта** (там же аккаунты, авторизация, подписки) |

Почему не в той же D1: **Time Travel в D1 восстанавливает базу целиком.** Захотел откатить каталог
после сбоя consumer-Worker'а — откатил заодно и права. Разные жизненные циклы должны лежать в разных
базах.

JOIN между двумя базами не нужен: запрос прав вернёт 10–100 идентификаторов проектов, дальше
`WHERE project_id IN (…)` в каталог.

<a name="user-id"></a>

## 3. Идентичность пользователя: почему в путь идёт `user_id`, а не почта

Естественная мысль — назвать корневую папку пользователя его почтой:

```
alexey@mail.com/my_project/OUT/final.mov
```

**Так делать нельзя, и это та же ошибка, что «имя проекта = его идентичность», только масштабом
больше.**

Смена почты меняет корневой префикс → меняются префиксы **всех** проектов этого пользователя →
физический перенос **всего его хранилища**: тысячи объектов, N×(copy + delete), для мастеров крупнее
5 ГБ ещё и multipart-copy, операция неатомарная, идёт минутами-часами, и всё это время хранилище
пользователя в состоянии `moving`.

**Правильно:**

```
u_9fk2mq7x/my_project/OUT/final.mov
└────┬────┘
  user_id — навсегда;   users.email = "alexey@mail.com" — меняется свободно
```

Смена почты = `UPDATE users.email`. **Ноль операций в R2.**

Четыре независимых довода:

1. **Масштаб.** Смена почты не должна перекладывать терабайты. А почты меняются: ребрендинг, человек
   сменил компанию, опечатка при регистрации.
2. **Регистр.** Почты на практике регистро-нечувствительны, ключи в R2 — чувствительны.
   `Alex@Mail.com` и `alex@mail.com` создадут **две разные папки**. Та же ловушка, из-за которой
   `project_id` взят из строчного алфавита.
3. **Символ `+`.** Gmail-алиасы (`alex+work@mail.com`) требуют URL-кодирования в presigned-ссылках —
   источник тонких, не сразу заметных багов.
4. **Почта — персональные данные.** Ключи объектов попадают в логи Worker'а, в аналитику Cloudflare,
   потенциально в URL внешних ссылок. Складывать почты в ключи = разносить PII туда, где ты этим не
   управляешь.

**Генерация `user_id`:** как и `project_id` — `nanoid`, только строчные буквы и цифры, 12 символов.
Префикс `u_` для читаемости при отладке.

Читаемость бакета теряется только на верхнем уровне: в программе и на сайте всегда показывается
почта, `u_9fk2mq7x` увидишь только если полезешь в бакет через rclone.

### Итоговая раскладка ключей

Вариант А **принят 2026-08-05**: и юзер, и проект адресуются своими id.

```
u_9fk2mq7x/                          ← user_id (навсегда), display = users.email
  k7m2xq9vb4te/                      ← project_id (навсегда), display = .keep/display_name
    .keep                            ← { role, project_id, display_name, created_at }
                                       + метаданные x-amz-meta-project-id
    options/
      folderState.json               ← project_id, enabled, lastActivity
      options.json
    IN/  .keep
    OUT/ .keep
         final.mov                   ← мастер, приватный
         _web/final.mp4              ← веб-прокси для просмотра
```

Ни один сегмент пути не меняется при переименовании: `display_name` живёт в `.keep` и в БД.

<a name="расшаривание"></a>

## 4. Расшаривание проекта другому пользователю

**Хорошая новость: в R2 нет «хранилища пользователя».** Есть один бакет и плоское пространство
ключей, а «проект принадлежит пользователю 1» — соглашение о префиксе. Поэтому «у пользователя 2
этой папки в хранилище нет» получается само собой: копировать нечего, симлинки не нужны,
перекрёстная ссылка стоит одну строку в БД.

```sql
CREATE TABLE users (
    user_id    TEXT PRIMARY KEY,     -- 'u_9fk2mq7x', в путях
    email      TEXT NOT NULL UNIQUE, -- отображаемое, меняется свободно
    created_at INTEGER NOT NULL
);

CREATE TABLE grants (
    id                INTEGER PRIMARY KEY,
    project_id        TEXT    NOT NULL,   -- ← НЕ prefix! переживает переезд и переименование
    subject_type      TEXT    NOT NULL,   -- 'user' | 'group'
    subject_id        TEXT    NOT NULL,
    role              TEXT    NOT NULL,   -- см. таблицу ролей
    scope             TEXT,               -- NULL = весь проект; иначе путь ОТНОСИТЕЛЬНО проекта
    granted_by        TEXT    NOT NULL,
    granted_at        INTEGER NOT NULL,
    expires_at        INTEGER,            -- NULL = бессрочно
    last_known_prefix TEXT                -- снимок пути для процедуры починки (раздел 6)
);
CREATE INDEX idx_grants_subject ON grants (subject_type, subject_id);
CREATE INDEX idx_grants_project ON grants (project_id);
```

### Роли

| Роль | Дерево | Смотреть `_web/` | Скачивать мастера | Загружать | Управлять правами |
|---|---|---|---|---|---|
| `viewer` | ✓ | ✓ | — | — | — |
| `downloader` | ✓ | ✓ | ✓ | — | — |
| `editor` | ✓ | ✓ | ✓ | ✓ | — |
| `uploader` | **только `IN/`** | — | — | ✓ | — |
| `owner` | ✓ | ✓ | ✓ | ✓ | ✓ |

**`uploader` — это ответ на вопрос «как клиенты сдают материал»:** кладёт файлы в `IN/`, не видя
ничего остального.

### Разрешение конфликтов

**Побеждает самый длинный совпавший scope** (как в файловых ACL), а не самое широкое право. Иначе
понижение прав на подпапку не сработает: широкий `editor` на проект перебьёт узкий `viewer` на
`OUT/`, и ограничение окажется бессмысленным.

### Переписыватель пути

Пользователю 2 **нельзя показывать** `u_9fk2mq7x/my_project/` — это утечка структуры пользователя 1.
В его кабинете проект отображается как «Доступные мне / <display_name>». Сайт обязан отдавать
переписанный путь, а не реальный префикс.

### Как выдаются байты

**Это место, где модель «сайт выписывает presigned URL» становится обязательной, а не опциональной.**

| Кто | Как получает файл |
|---|---|
| Наша программа (мы владельцы) | ключи R2 в keychain, подписывает сама |
| Внешний пользователь через сайт | **только** presigned URL на один конкретный объект, выписанный Worker'ом **после** проверки grant, TTL минуты |

Внешнему пользователю нельзя дать ни ключей, ни широкой ссылки. Никогда.

## 5. Внешние ссылки: доступ без аккаунта

### Presigned URL нельзя отдавать людям

| Свойство | Presigned URL (S3 SigV4) |
|---|---|
| Максимальный TTL | **7 суток**, жёстко в протоколе |
| Отзыв конкретной ссылки | **невозможен** |
| Единственный способ погасить досрочно | ротация ключа доступа → умирают **все** ссылки этого ключа |
| Пароль, лимит скачиваний, лог обращений | нет |

Presigned URL — **неотзываемый bearer-токен с фиксированным сроком жизни**. Для машина→R2 идеально
(TTL 5–15 минут, используется сразу, нигде не хранится). Для ссылки, которую человек отправит в
мессенджер, перешлёт дальше и скриншотнет — категорически нет.

> **И отдельно: НИКОГДА не делать бакет публичным через `r2.dev` или домен «на весь бакет».**
> Одна галочка, после которой открыто всё.

### Правильная схема: ссылка ведёт на наш Worker

```
https://files.example.com/s/<token>
                │
                ▼
        Worker: нашёл токен в БД
                ├── отозван? истёк? лимит скачиваний? пароль? → 403
                ├── записал обращение в лог
                └── отдал файл (проксируя с Range) либо 302 на presigned с TTL 60–300 с
```

Отзываемость появляется именно здесь: погасили строку в БД — ссылка умерла мгновенно, ключи доступа
не тронуты.

```sql
CREATE TABLE share_links (
    token_hash        TEXT    PRIMARY KEY,  -- ХЭШ токена, не сам токен
    token_prefix      TEXT    NOT NULL,     -- первые 6 симв., чтобы показать в списке
    project_id        TEXT    NOT NULL,     -- ← не префикс
    scope_kind        TEXT    NOT NULL,     -- 'file' | 'prefix'
    scope             TEXT    NOT NULL,     -- путь ОТНОСИТЕЛЬНО корня проекта
    mode              TEXT    NOT NULL,     -- 'view' | 'download' | 'upload'
    password_hash     TEXT,
    expires_at        INTEGER,
    max_downloads     INTEGER,
    n_downloads       INTEGER NOT NULL DEFAULT 0,
    revoked_at        INTEGER,
    created_by        TEXT    NOT NULL,
    created_at        INTEGER NOT NULL,
    last_known_prefix TEXT,
    note              TEXT
);

CREATE TABLE share_access_log (
    id         INTEGER PRIMARY KEY,
    token_hash TEXT NOT NULL,
    key        TEXT, ip TEXT, ua TEXT, country TEXT,
    at         INTEGER NOT NULL, bytes INTEGER
);
```

Три неочевидные вещи в этой схеме:

1. **В БД лежит хэш токена, а не токен.** Утечка базы тогда не даёт рабочих ссылок — тот же принцип,
   что с паролями. Сам токен ≥128 бит энтропии (22 символа base62), показывается один раз при
   создании; в списке видно только `token_prefix`.
2. **Scope относительно проекта, а не абсолютным префиксом.** Иначе физический перенос проекта порвёт
   все ссылки.
3. **Клиент никогда не выбирает ключ.** Для `mode='upload'` Worker сам формирует
   `IN/<uuid>_<очищенное-имя>`. Иначе получаем перезапись существующих файлов и выход за пределы
   префикса через `../`.

### Безопасные дефолты

- **Срок жизни обязателен**, по умолчанию 7 суток. «Бессрочно» — только явным выбором и с отметкой в
  списке ссылок.
- **По умолчанию `view`, а не `download`.** Самая полезная защита: большинство ссылок нужны в смысле
  «посмотри», а не «забери 5 ГБ мастера».
- Лог обращений всегда включён.
- Rate limiting Cloudflare на маршрут Worker'а: egress бесплатен, но утёкшая ссылка не должна
  превращаться в раздачу.
- **Глобальный тумблер «внешние ссылки запрещены»** на аккаунт — если решим наружу не отдавать ничего.

### Почему `_web/` не делаем публичным

Соблазн: отдать префикс `_web/` (веб-прокси) через свой домен публично — постоянные ссылки и
edge-кэш. Но публично = кто угодно со ссылкой, а проекты приватные и с разными правами.

Решение: `_web/` отдаёт тот же Worker после проверки токена, **а edge-кэш сохраняется** — ответ
кэшируется по URL, то есть **по токену**. Одна ссылка, разосланная десяти людям, обслуживается из
кэша; разные ссылки не смешиваются. Публичный домен остаётся только для действительно публичного
контента (шоурил, отданный навсегда).

### Проксировать или редиректить

| | Проксировать через Worker | 302 на presigned |
|---|---|---|
| Range-запросы (перемотка видео) | нужно реализовать самому | R2 делает сам |
| Лог и лимиты на каждый запрос | да | только на первый |
| Ссылка «утекает» наружу | нет | да, на время TTL |
| Длинное видео | стабильно | presigned может истечь посреди просмотра → 403 |

**Рекомендация:** `_web/` проигрывать проксированием через Worker (с поддержкой `Range`), целые файлы
на скачивание отдавать через 302 на presigned с TTL 5 минут — байты идут напрямую из R2, Worker не
становится горлышком.

## 6. Что ломается и как это чинится

Каталог производный — он всегда прав. Ломается **авторское**, если оно сослалось на путь.

| Событие | Что с правами и ссылками |
|---|---|
| Переименование проекта (`display_name`) | ничего, они на `project_id` |
| Смена почты пользователя | ничего, префикс на `user_id` |
| Физический перенос проекта | ничего, `projects.prefix` обновился в одной строке |
| Переименование подпапки внутри проекта | **`share_links.scope` надо перенести** в том же job'е |
| Переименование файла | ссылка `scope_kind='file'` **умирает** — у файлов нет стабильного id |
| Удаление `folderState.json` руками | `project_id` восстанавливается из метаданных маркера |
| Удаление и файла, и маркера | **проект потерял идентичность** → процедура ниже |

### Процедура починки: поломка должна быть заметной, а не молчаливой

Задача не «сделать неломаемым», а «сделать починяемым».

1. **Никогда не генерировать новый `project_id` для папки, похожей на существующий проект.** Нет id
   ни в файле, ни в метаданных → `needs_review`, а не свежий id. Молчаливая перегенерация превращает
   восстановимую ситуацию в безвозвратную потерю.
2. **`grants` и `share_links` хранят `last_known_prefix`.** Тогда сайт предлагает: «три права
   указывали на `u_9fk2mq7x/my_project/`, у этой папки больше нет id — это тот же проект?» Одна
   кнопка вместо «сломалось навсегда».
3. **Каталог не удаляет строку проекта, потерявшую префикс** — переводит в `orphaned` и держит.
   Права остаются валидными, просто временно ни на что не указывают.
4. **Экран «проекты, потерявшие связь»** — без него правила 1–3 некому предъявить.

### Предупреждения в UI

- Переименование или удаление файла, у которого есть активные внешние ссылки → предупредить, показать
  сколько ссылок затронуто.
- Ссылки на **папку** (`scope_kind='prefix'`) переживают переименование файлов внутри → для «покажи
  клиенту готовые материалы» шарить папку `OUT/`, а не отдельный файл. Сделать это дефолтом в UI.
