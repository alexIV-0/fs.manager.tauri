# План: что нужно от программы для биллинга на сайте

**Статус:** 🎯 спроектировано, кода нет. Сверено с кодом 2026-08-27.

Сайт вводит оплату обработки с баланса пользователя. Общий план — на их стороне:
`../innovation-hub/docs/BILLING_AND_TRIAL_PLAN.md`. Здесь **только наша часть**: что
дописать, где и почему.

Работы мало и она вся мелкая. Это не совпадение: половина механики у нас уже есть
(`cost`, `costUnit`, `fromSite`, `outSec`), и план на сайте построен так, чтобы её
использовать, а не дублировать.

Связанное: [`+STATS_SCHEMA_PLAN.md`](./+STATS_SCHEMA_PLAN.md) (схема v1, заморожена),
[`SITE_STATS_LINK_PLAN.md`](./SITE_STATS_LINK_PLAN.md) (сквозной `itemId`),
[`DISTRIBUTED_QUEUE_PLAN.md`](./DISTRIBUTED_QUEUE_PLAN.md) (режим воркера).

---

## Граница, из которой всё следует

Договорённость с сайтом, зафиксированная в их плане:

> **Машина считает, во что работа обошлась нам. Сайт считает, что выставить клиенту.**

```
машина  →  totalCost = внешние сервисы (fromSite) + фиксированные сборы плагинов (run)
сайт    →  списание  = единица × ставка сайта  +  totalCost × (1 + маржа)
```

Отсюда прямо получается и то, что мы делаем, и то, чего мы **не** делаем (§3).

## 1. Две обязательные оси тарификации в ноде `description` 🎯

### Зачем

Сайт должен знать, **за что списывать средства в этом проекте**. Знает об этом только
автор графа: он проектирует выход и заранее понимает, что получится, что бы ни пришло на
вход.

Раскладывается на две независимые оси:

```
от чего отталкиваемся  ×  в чём считаем
      payBase                payMeter
```

| `payBase` | | `payMeter` | |
|---|---|---|---|
| `output` | финальный результат | `sec` | секунды |
| `source` | исходник на входе | `count` | штуки |
| `render` | время обработки | `bytes` | объём |
| `fixed` | за сам прогон | | |

Ставку на количество умножает сайт — по паре осей, а не по одной единице. Оси растут
независимо: появится новая мера (кадры, символы, токены) — она сразу работает с обеими
базами.

Место напрашивается само: нода `description` уже несёт `contact`, уже `required`, уже
`deletable: false`, и сайт её уже читает
(`../innovation-hub/lib/pipeline/build-task.ts#buildDescription`). Ещё два обязательных
поля рядом с первым — ровно тот же путь, ни одной новой связи.

### Правка

`src/NODE_WIN/definitions/description.ts`, в массив `properties` рядом с `contact`:

```ts
{
    id: `payBase`,
    controlType: 'ddm',
    controlProps: {
        label: 'Отталкиваемся от',
        tooltip: 'От чего сайт считает оплату: финал, исходник, время обработки или сам прогон',
        options: ['output', 'source', 'render', 'fixed'],
        multiSelect: false,
        value: 'output',
    },
    required: true,
    outputType: 'string',
},
{
    id: `payMeter`,
    controlType: 'ddm',
    controlProps: {
        label: 'Считаем в',
        tooltip: 'Секунды, штуки или объём. При payBase = fixed не используется',
        options: ['sec', 'count', 'bytes'],
        multiSelect: false,
        value: 'sec',
    },
    required: true,
    outputType: 'string',
},
```

`ddm` выбран потому, что он есть в списке контролов, которые сайт умеет показывать
(`EXPOSED_CONTROL_TYPES`): если позже захочется дать клиенту видеть эти поля в
«Параметрах обработки», отдельная работа не понадобится.

Больше ничего делать не нужно: значения уедут в `description` объекта обработки тем же
путём, что и `contact`, и приедут на сайт в `payload.description.payBase` / `payMeter`.

### Какие пары сайт поддерживает

Словарь общий, менять только согласованно. **Пары проверяются целиком**, а не каждая ось
по отдельности: неподдержанное сочетание отклоняется с внятной причиной, а не считается
как попало.

| Пара | Откуда сайт берёт количество | Готовность |
|---|---|---|
| `output` × `sec` | `outSec` строки архива | ✅ |
| `output` × `count` | длина `out[]` | ✅ |
| `source` × `count` | манифест задачи, у сайта уже есть | ✅ |
| `source` × `bytes` | размеры файлов в каталоге, у сайта уже есть | ✅ |
| `render` × `sec` | `renderSec` строки архива | ✅ |
| `fixed` | сама задача | ✅ |
| `source` × `sec` | `srcSec` — **нужен от нас**, см. §2 | ⬜ |
| `output` × `bytes` | в архиве нет | 🔧 позже |

`render` × `sec` — запасная база на случай, когда ни вход, ни выход не поддаются
измерению: на входе папка с чем попало, на выходе набор разнородных артефактов. Работает
уже сегодня, `renderSec` в схеме v1 есть и означает `endedAt − startedAt` без времени в
очереди. От нас не требуется ничего.

**Пару проверяет сайт по `mainSearch`.** Тип файла, попадающий в `IN`, объявлен в графе, и
сайт его уже разбирает. Значит «проект тарифицируется по `source` × `sec`, а `mainSearch`
ищет картинки» отклоняется при разборе графа, а не при первой обработке. Нам из этого
следует одно: если у пары осей и `searchType` разная природа, ошибку покажут сразу — это
не молчаливый сбой, чинить его в программе не придётся.

### ⚠️ Ловушка, о которой надо знать до того, как проставите единицы

`outSec` — это **сумма** длительностей по всем терминальным выходам. Смотреть
`collectOutputInfo` (`src/PROCESSING/processItem.ts:762-796`):

```ts
if (stream?.duration) totalSecs += parseFloat(stream.duration) || 0;
```

Для одного ролика верно. Для нескольких параллельных дорожек — нет. Подготовка к
редактированию субтитров: диалог на три минуты, пять дорожек по персонажам, `outSec`
приезжает как 900 секунд. Сайт выставит счёт за пятнадцать минут вместо трёх, и заметить
это будет нечем — число сходится, оно просто отвечает не на тот вопрос.

Важная деталь оттуда же: в `files` попадают **все** терминальные выходы, включая не-медиа,
а в `totalSecs` — только медиа. То есть JSON рядом с дорожками уже сейчас считается в
`out[]`, но не в хронометраже. Это правильно и менять не надо.

**Три способа обойти, и ни один не требует кода:**

1. **Терминальным сделать только финальный микс.** Хронометраж считается только по
   терминальным шагам — дорожки по персонажам становятся промежуточными и в счёт не
   попадают. Работает, когда клиент получает микс, а дорожки это кухня.
2. **Тарифицировать такой проект не минутами.** `run` или `out_files`, если ценность в
   самом факте разбора, а не в его длине.
3. **Считать честно суммой.** Клиент получает все пять дорожек — значит платит за пять.

Выбор ценовой, а не технический, и делается он на проект — теми же осями.

**Если ни один не подойдёт**, понадобится способ сведения `max` — брать самый длинный
выход вместо суммы. Вот он уже требует правки у нас: сайт получает готовую сумму и
разложить её обратно не может. Это поле схемы **v2**, рядом с `plugins[]`. Заводить
заранее не стоит: сначала должен появиться случай, который не закрывается тремя способами
выше.

### Про ноду-счётчик на `jsCode`

Идея рабочая, стоит записать. Оговорка одна: **нода должна возвращать количество, а не
цену.**

«Сколько единиц получилось» — знание графа, ему там место. «Сколько это стоит» —
распоряжение владельца сервиса, и в графе оно становится невидимым и непроверяемым:
кто угодно вернёт единицу за час работы, а узнаем мы об этом из выручки.

Значит нода отдаёт число, сайт умножает на свою ставку. Тогда это просто ещё один
источник количества, наравне с `outSec` и `out[]`, и остальная схема не меняется.
Технически это тот же путь, что у `payUnit`: значение уезжает в `description` объекта
обработки и приезжает на сайт готовым.

### ⚠️ Хвост: старые графы поля не получат

`onInit` ставит ноды из `options.json` **как есть** — обновляются только `cost`/`costUnit`
через `syncCostsFromManifest` (`src/NODE_WIN/CLAUDE.md`). Значит в графах, сохранённых до
этой правки, `payUnit` не появится, и сайт по ним тарифицировать не сможет.

Два пути, и они не исключают друг друга:

**A. Руками.** Открыть каждый существующий проект в редакторе и проставить единицу.
Быстро, пока проектов немного. На сайте страховка есть: единицу можно задать настройкой
проекта в админке, если в графе её нет.

**B. `syncRequiredProps` по образцу `syncCostsFromManifest`.** Функция рядом с
`src/NODE_WIN/utils/syncCostsFromManifest.ts`: при загрузке графа добирает в узлы
статических определений те `required`-свойства, которых в сохранённом узле нет, — со
значением по умолчанию из определения.

B стоит примерно столько же, сколько A на пятом проекте, и закрывает проблему навсегда:
следующее обязательное поле в `description` (а оно будет) приедет в старые графы само.
Ограничить только `required`-свойствами и только статическими определениями — иначе
получится тихая правка чужих графов.

### Проверка

1. Новый граф: оба поля есть, пустыми сохранить нельзя.
2. Прогон из конвейера: в задаче на сайте `payload.description.payBase` и `payMeter`
   не пустые, пара из белого списка.
3. Старый граф без правки B: поля не появились, обработка не сломалась — сайт берёт
   оси из настройки проекта.
4. `npx tsc --noEmit` зелёный.

## 2. `srcSec` — хронометраж исходника 🎯 (сайт готов, ждёт поле)

### Зачем

Ось `source` × `sec` (§1) закрывает случай, на котором ломается счёт по выходу:
подготовка к редактированию субтитров даёт диалог на три минуты и пять дорожек по
персонажам, `outSec` приезжает как 900 секунд, и клиент платит впятеро. Если считать не
выход, а вход, вопроса нет вовсе: три минуты остаются тремя минутами независимо от того,
сколько дорожек, JSON-ов и служебных файлов родилось в процессе.

Поле **уже запланировано**: `+STATS_SCHEMA_PLAN.md`, раздел «Отложено в v2» —
«`srcSec` — хронометраж исходника: только отдельным ffprobe-проходом по источнику».
Этот план не добавляет нового решения, а даёт причину сделать.

### Побочная выгода, которая, возможно, важнее самого случая

Количество по входу известно **до** обработки. Сайт резервирует деньги по оценке и
уточняет по факту именно потому, что не знает, что выйдет. С `source` резерв равен факту:
ни перерасхода, ни списаний в убыток, ни ухода баланса в минус в таких проектах не
возникает совсем.

Для `source` × `count` и `source` × `bytes` сайт это умеет уже сегодня — манифест и
размеры лежат у него в каталоге. Не хватает ровно секунд, и это мы.

### Правка

Отдельный ffprobe-проход по источнику, результат в строку архива. Инструмент уже есть —
`commands.ffprobeGetInfo`, тот же, которым `collectOutputInfo` меряет выход
(`src/PROCESSING/processItem.ts:789`). Путь источника известен: `desc.pathForDelete`
(`processItem.ts:327`).

| Что | Где |
|---|---|
| Померить источник | `processItem.ts`, рядом с `collectOutputInfo`; для папки — сумма по вложенным медиа |
| Положить в результат | `processItem.ts:415`, в `return` рядом с `outSec` |
| Дописать в архив | `write_local_archive`, `src-tauri/src/commands/db_analytics.rs` |
| Поднять версию | `LOCAL_ARCHIVE_SCHEMA_VERSION` → 2 |
| ~~Принять на сайте~~ | ✅ **сделано 2026-08-28**: колонка `src_sec` (миграция `2026-08-28-processing-src-sec.sql`), приёмник читает `srcSec`, списание считает по нему пару «вход × секунда» |

Схему это переводит в **v2**. Ломающего в этом ничего нет: `schemaVersion` для того и
заведён, приёмник читает обе версии, старые строки остаются валидными. Заодно логично
поднять вместе с `plugins[]`, если руки дойдут — они из одного раздела «Отложено в v2».

### Что уже готово на той стороне

Пара «вход × секунда» на сайте **включена целиком**: ставку можно задать в
«Тарифах», проект — настроить, задача — собраться. Не хватает ровно значения.
Пока его нет, такие обработки не списываются и попадают в отдельный счётчик
прохода (`awaitingSrcSec` в логе тика), а не пропадают молча и не считаются
бесплатными. То есть день, когда вы допишете поле, — это день, когда деньги
начнут списываться, без единой правки у них.

### Оговорки

- **Не для всех входов.** Источник-картинка или JSON хронометража не имеет; `srcSec`
  тогда `null`, и проект с такой парой осей сайт не примет — это ошибка настройки, а не
  сбой.
- **Папка на входе** — сумма по вложенным медиа, **но только по тем, что прошли по
  `searchExts`**. В папке может лежать что угодно; сайт считает штуки и объём уже с этим
  фильтром, и `srcSec` должен считаться так же, иначе три ролика рядом с сотней PDF дадут
  разные ответы у нас и у них. Здесь суммировать правильно: это разные исходники, а не
  параллельные дорожки одного.
- **Стоит ли слать в `taskDone`.** По той же логике, что `outSec` (§5): даёт мгновенное
  списание вместо часового ожидания архива. Но `srcSec` известен ещё раньше — в момент
  старта, а не завершения, — поэтому его разумнее отдавать первым `taskProgress`. Тогда
  сайт уточняет резерв до конца обработки, а не после. Необязательно, но дёшево.

### Проверка

1. Ролик на 3 минуты, граф с пятью выходными дорожками: `srcSec` = 180, `outSec` = 900.
   Оба поля в строке архива, оба доехали на сайт.
2. Папка из трёх клипов: `srcSec` = сумма трёх.
3. Картинка на входе: `srcSec` отсутствует, обработка не падает.
4. Старый приёмник, новая строка: `schemaVersion: 2` не ломает импорт.

## 3. Валюта себестоимости — объявить контрактом 🎯

### Зачем

`totalCost` в архиве — **одно число без валюты**. Сегодня это работает случайно: цену
реально сообщает один плагин, и сообщает в долларах (`costUsd`,
`plugins-dev/AIparser/AIparser.ts:127`), а у остальных `cost` в `plugin.json` равен нулю.

Как только появится второй платный сервис в другой валюте, сумма молча смешает доллары с
евро. Заметить это будет нечем: число сходится, оно просто ничего не значит.

Сайту это число нужно привести к рублям по курсу ЦБ. Без объявленной валюты приводить
нечего.

### Правка

**Контракт: себестоимость всегда в долларах США.** Плагин, работающий с сервисом в
другой валюте, приводит к доллару сам.

Что сделать:

1. Записать это в `+STATS_SCHEMA_PLAN.md` (поле `totalCost`) и в подсказку поля `cost`
   в `PluginBuilderWin` — там, где автор плагина цену вводит
   (`src/MAIN_WIN/options/plugin/PluginSortableListItem.tsx:180-219`).
2. **Провести ревизию ненулевых цен.** Сейчас такая одна:
   `distr-plugins/AItranslateVA@0.1/plugin.json` — `cost: 1, costUnit: run`.

   Единица здесь **верная**: плата за сам запуск плагина, время работы значения не имеет —
   именно для этого `run` и существует. Вопрос только к валюте: по числу `1` не понять,
   рубль это или доллар. Момент удачный — у остальных плагинов цены нулевые, договориться
   можно до того, как их проставят.

Кода это почти не касается — касается договорённости. Но записать надо сейчас: потом
придётся выяснять валюту по каждой строке архива задним числом, а там её нет.

### Отложено до схемы v2

Настоящее решение — построчная себестоимость: `plugins[]` с ценой, валютой и id сервиса
на каждый шаг. Тогда и сумма перестаёт быть загадкой, и на сайте появляется отчёт «за
месяц в этом сервисе столько, в том столько». В `+STATS_SCHEMA_PLAN.md` `plugins[]` уже
отложен в v2 — этот план ничего в том решении не меняет, только добавляет причину.

## 4. Чего делать НЕ надо: не считать `HH`/`MM`/`ss` у себя ⛔

В `src/PROCESSING/processItem.ts:550-558` ветка стоимости выглядит незаконченной:

```ts
if (capturedSiteCost !== undefined) { … }        // fromSite
else if (costUnit === 'run') { … }               // run
// HH / MM / ss — ветки нет
```

Соблазн дописать умножение на время есть, и он ошибочный. Если время начнёт считаться
здесь, цена минуты окажется зашита в `plugin.json` **на каждой машине парка**, и смена
тарифа превратится в переустановку плагинов по всем машинам. Тариф — распоряжение
владельца сервиса, а не свойство установки.

Время умножает сайт, по ставке из одного места. `costUnit: 'MM'` у ноды остаётся
**декларацией** «этот шаг тарифицируется временем» — сайт её читает, а множит у себя.

Оставлено осознанно. Комментарий об этом стоит поставить прямо в коде рядом с веткой,
иначе следующий читатель починит «пропущенный случай».

## 5. Необязательное ускорение: `outSec` в `taskDone` ⏸

**В объём биллинга не входит, всё работает и без этого.** Записано, чтобы не искать
заново, когда понадобится.

Сейчас сайт узнаёт хронометраж результата только из архива `_stats`, который он читает
часовым тиком. То есть между «обработка закончилась» и «деньги списаны» проходит до часа,
и всё это время сайт вынужден держать резерв.

Между тем мы знаем хронометраж **в момент отчёта**: `processItem.ts:402` уже посчитал
`mediaDurationSecs` через `collectOutputInfo`, а строкой ниже отдаёт его как
форматированный `duration`.

Правка на четыре строки:

| Файл | Что |
|---|---|
| `src/PROCESSING/processItem.ts:415` | в `return` добавить сырые секунды: `outSec: mediaDurationSecs` (рядом с форматированным `duration`) |
| `src/PROCESSING/remoteWorker/runTask.ts:55` | в `TaskOutcome` добавить `outSec: number` |
| `src/PROCESSING/remoteWorker/runTask.ts:399,413` | прокинуть `outSec: result.outSec ?? 0` |
| сайт | принять поле в `taskDoneSchema` |

Схему архива v1 это **не трогает**: `outSec` там уже есть, речь только о втором канале
доставки того же числа. Дублирование безопасно — на сайте вставка идёт с дедупом по
`itemId`.

## 6. Имя папки служебного аккаунта в зеркале ⏸

**Необязательно.** Записано, потому что решать это надо один раз и заранее.

Шаблоны пробного периода лежат у служебного аккаунта сайта, и в зеркале они окажутся под
папкой верхнего уровня, подписанной по `RemoteUser::label()`
(`src-tauri/src/storage/types.rs:118`):

```rust
for candidate in [&self.email, &self.full_name, &self.display_name] { … }
```

То есть **email вперёд всего**. Аккаунт `templates@ffworks.pro` даёт папку
`templates@ffworks.pro`: `@` санитайзер не трогает
(`layout.rs:246` заменяет только `/ \ : * ? " < > |`). Это уже конкретное обозначение, и
делать для него ничего не надо.

Если захочется имя вида `_ШАБЛОНЫ` — правка на одну строку: поставить `display_name`
**первым** в этом массиве. Сайт со своей стороны начнёт присылать его в `users[]`
(сейчас там только `id`, `email`, `fullName`). У существующих пользователей поле пустое,
поэтому порядок для них не меняется ни в чём.

⛔ **Чего делать нельзя: ставить вперёд `full_name`.** Он заполнен у всех, и первый
уровень зеркала переименуется **каждому** пользователю — то есть на каждой машине парка
зеркало переразложится целиком. Комментарий в `types.rs:105` про это прямо и написан:
email выбран потому, что уникален и всегда есть.

⚠️ **Момент важен.** Переименование верхнего уровня заставляет программу переразложить
зеркало этого аккаунта. Пока папка пустая — бесплатно; после заливки шаблонов — лишнее
движение файлов. Решать до наполнения.

## 7. Чего от нас не требуется вовсе

- **Тестовый период.** Грант, кошельки, копирование шаблонов, кнопка, таблички — всё на
  сайте. Шаблонные проекты мы правим как обычные: служебный аккаунт сайта + его машинный
  токен `mch_…` в настройках десктопа, дальше они видны в программе как свои (имя их
  папки — §6).
- **Балансы и списания.** Машина про деньги пользователя не знает и знать не должна:
  она получает задачу, только если сайт уже решил, что оплата есть.
- **Курс валют.** Тянет сайт с ЦБ и фиксирует в транзакции.
- **Проверки «хватает ли денег».** Допуск живёт в конвейере на сайте, до создания задачи.

## 8. Зависимость на стороне сайта

Биллинг опирается на **сквозной `itemId`** — пункт C из
[`SITE_STATS_LINK_PLAN.md`](./SITE_STATS_LINK_PLAN.md): сайт кладёт `task.id` в
`description.dbItemId`. Наши A и B там сделаны с 2026-08-19.

Без него `processing_stats.item_id` не равен `tasks.id`, и «какая задача сколько стоила»
остаётся догадкой по совпадению «проект + имя + время». В их плане это этап 0, до всего
остального.
