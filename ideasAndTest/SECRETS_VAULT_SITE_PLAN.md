# Секреты на сайте (сейф) + выдача токенов компам — план

**Статус:** проектирование (2026-07-22). Модель **B** (сайт = UI + сейф, компы авторизуются и
тянут токены по необходимости). Модель A (сайт-брокер, сам постит) — **отклонена**: сайт это
интерфейс пользователя + хранилище, а не оркестратор.

## Идеология (зачем и почему так)

Принцип программы: **одна папка-проект = источник истины для всего, что относится к папке.**
Но секрет (токен/ключ) — **не данные папки-проекта, а данные уровня пользователя (аккаунта)**:
он и так переиспользуется во всех проектах одного человека. Значит, класть его в папку логически
неверно, а класть в `options.json` на Google Drive — ещё и опасно.

**`options.json` считаем публично читаемым:** папку можно расшарить, у Google есть открытый
текст, она синкается на все диски, живёт в истории версий/бэкапах навсегда, отозвать/ротировать
размазанный секрет невозможно. Поэтому в папку идёт только **конфиг + ссылка** на аккаунт, но
**никогда сам секрет** (даже зашифрованный — шифротекст всё равно расползётся по истории версий).

Три ортогональные части системы:
1. **Drive-папка** — общее состояние и план работ (истина для *что делать*). Настоящий «оркестратор» — это данные, не сайт.
2. **Компы** — исполнители: читают папку, обрабатывают, постят. Каждый комп сам ищет+обрабатывает (проще администрировать, темповые файлы локальны). Мультикомп на одну папку → нужен claim-файл (вне этого плана).
3. **Сайт** — человеческий UI + сейф секретов. НЕ оркестратор.

## Неизбежная правда

В момент постинга какая-то машина обязана держать рабочий токен (иначе не зальёт видео).
«Безопасно» = **не в общей Drive-шине + привязано к аккаунту + отзываемо + минимальный радиус
поражения**, а не «никто не видит токен».

## Асимметрия платформ (решено осознанно)

| | Долгий секрет | Что приходит на комп | Радиус поражения |
|---|---|---|---|
| **YouTube (OAuth)** | `refreshToken`+`clientSecret` **остаются на сайте** | только 1-часовой `access_token` | 1 час |
| **VK (Kate Mobile)** | долгоживущий токен, короткого обмена НЕТ | полный долгий токен, оседает в кэше | до отзыва на стороне VK (ограничение платформы, не архитектуры) |

**Правило сейфа:** OAuth-платформы → сайт чеканит короткий токен из долгого секрета server-side
(это операция *хранилища*, не оркестрация); long-lived-платформы → сайт отдаёт долгий токен, комп
кэширует с TTL.

## Текущее состояние (от чего отталкиваемся)

Хорошая новость: **шов уже готов, плагины трогать не придётся.**

- Хранилище сейчас: `app_data_dir/accounts/<mainFolderName>/<platform>.json`, токен plaintext
  (`account_commands.rs`). Уже **вне Drive** — но ключевание по *имени папки* (слабая граница) и
  открытый текст.
- Плагины **не читают файл**, а зовут IPC: VK `account_get_token`, YT `youtube_get_access_token`
  (`autoPostVK.ts:92`, `autoPostYT.ts:77`).
- `account_list` уже **вырезает `accessToken`** и отдаёт только метаданные; токен возвращает
  **единственная** команда `account_get_token`. → Разделение «list = метаданные / get = секрет»
  уже есть, сайт его реплицирует.
- В коде явно заложено: *«бэкенд подменяемый (позже RemoteTokenStore/сайт)»* (`account_commands.rs:10`).
- Нода `account` — уже **reference-only**: `ddm`, хранит в options.json только **имя аккаунта**,
  токен отдельно (`autoPostVK/ui.json:47`).
- YouTube уже почти по Модели B: `refreshToken`/`clientSecret` не уходят в JS, наружу идёт только
  свежий `access_token` (`youtube_auth_commands.rs:252`).

## Пункт 3 (закрыт): как account_save/account_list переезжают на сайт

Мост — существующий `exposedToSite` (`types.ts:87`), но с разделением на **два вида expose**:

- **Конфиг-expose (уже работает):** значение круговым рейсом идёт через options.json. Безопасно
  для: выбор аккаунта (имя), target-группа, categoryId, madeForKids. Ничего не меняем.
- **Секрет-expose (НОВЫЙ смысл):** компонент — это *действие авторизации*, а не поле. Токен НЕЛЬЗЯ
  возвращать значением свойства (иначе сядет в options.json → в Drive). Правило:
  1. авторизация выполняется **на сайте**;
  2. секрет пишется в **сейф** (server-side `account_save`), ключ = аккаунт пользователя;
  3. в ноду/options.json возвращается **только ссылка** (имя/id аккаунта).

**Реализация для VK/YT:**
- Дропдаун `account` по форме НЕ меняется (хранит имя). `exposedToSite` = «сайт рисует селектор»,
  опции тянет `list` сайта.
- «Add New Account» / «вставить токен» / OAuth-connect → **действие на сайте** (зовёт серверный
  `account_save`/auth-flow). В приложении гасим → «управление аккаунтами на сайте».
- **Новый маркер `vaultAccount` / `secretRef: true`** (НЕ перегружать голый `exposedToSite`) —
  чтобы фреймворк принудительно знал: «значение здесь = всегда ссылка, никогда секрет».

## Пункт 1: enrollment устройства

Комп один раз доказывает сайту «я — этот пользователь», получает **device-credential** (долгий,
per-device, отзываемый), кладёт в **OS keychain** (не в Drive, не в plaintext app-data).

**Флоу (переиспользуем YouTube-паттерн: системный браузер + loopback + PKCE):**
1. Настройки → «Подключить аккаунт сайта».
2. Системный браузер → логин на сайте → сайт регистрирует устройство (`deviceId` = UUID,
   генерится 1 раз на инсталляцию) и выдаёт `deviceRefreshToken`.
3. `deviceRefreshToken` → в OS keychain (Rust `keyring`, service=`fsmanager`, account=`device`).
   `deviceId` — рядом (можно app-data, он не секрет).
4. Сайт ведёт **реестр устройств** пользователя → отзыв устройства с сайта = комп теряет доступ.

Рантайм: из `deviceRefreshToken` чеканится короткий `deviceAccessToken` (~1ч, Bearer для вызовов
сейфа), кэш в памяти/keychain по expiry.

**Граница «чьи это токены» = аутентифицированный пользователь устройства, НЕ имя главной папки.**
`mainFolderName` → максимум неймспейс/подсказка при резолве аккаунта.

## Пункт 2: контракт endpoint'ов сейфа

База `https://site/api/vault`, Bearer = `deviceAccessToken`.

**Auth / устройство:**
- `POST /device/authorize` + `POST /device/token` — device-flow (или OAuth Device Grant), выдаёт
  device access/refresh.

**Аккаунты (метаданные, НИКОГДА секреты):**
- `GET /accounts?platform=vk` → `[{id, name, platform, targetType, ...}]` — зеркало `account_list`
  (рисовать дропдаун).
- `POST /accounts` — **только site UI**: создать/обновить, прогнать auth-flow, записать секрет в
  сейф (= `account_save` server-side). Приложение это для секретов НЕ зовёт.
- `DELETE /accounts/{id}`.

**Выдача токена (единственные endpoint'ы, отдающие рабочий секрет; device-gated):**
- VK-стиль (long-lived): `POST /accounts/{id}/token` → `{ token, kind:"long_lived", cacheTtl }`.
- OAuth-стиль (YouTube): `POST /accounts/{id}/access-token` → сайт делает refresh server-side
  (держит `refreshToken`+`clientSecret`) → `{ accessToken, expiresAt }`. Долгий секрет не уходит.

**Сейф на сайте:** шифрование at-rest (envelope/KMS), изоляция по пользователю, аудит-лог,
предпочтение отзываемым OAuth refresh-токенам, короткие access-токены по запросу.

## Локальный кэш (вариант B2, с TTL)

- Кэш `{token, expiresAt}` по ключу `(user|mainFolder, platform, accountName)`. Короткие токены —
  шифрованный app-data или keychain; device-credential — обязательно keychain.
- Miss/expiry → тянем с сайта. Сайт недоступен + кэш жив → используем кэш; expired + offline →
  постинг падает с внятной ошибкой.
- **B2, а не B1 (навсегда):** отзыв на сайте протухает на всех машинах сам. TTL/refresh живут в
  слое синхронизации *над* плагинами → плагины не меняются.

## Отзыв (revocation)

- Устройство: отозвать с сайта → нет доступа к сейфу.
- Аккаунт: удалить на сайте → `get_token` 404 → постинг падает.
- OAuth: отозвать refresh на сайте → mint не проходит, радиус ≤1ч.
- VK long-lived: уже закэшированные копии валидны до отзыва на стороне VK + истечения TTL.

## Итоговые свойства безопасности

- Секрет в Drive-папке — **никогда**.
- OAuth: долгий секрет не покидает сайт, на компе максимум 1ч.
- VK: долгий токен на компе неизбежен (ограничение платформы), смягчён TTL + отзывом на сайте.
- Device-credential в OS keychain, отзываемый.
- Граница доступа = аутентифицированный пользователь, не имя папки.
- `list` = метаданные; единственный секрет-возвращающий endpoint, device-gated.
