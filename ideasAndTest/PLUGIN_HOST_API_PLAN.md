# Плагины как настоящее расширение программы (host API, contribution points)

> Статус: **направление на будущее, отложено осознанно.** Зафиксировано 2026-08-05.
>
> **Решение на сейчас:** новые не-нодовые возможности (первый случай — коннектор очереди задач)
> пишем **в ядро**, а плагин остаётся гейтом вкл/выкл. Перестраивать программу под generic-API ради
> одной задачи преждевременно — правильно, но дорого не по месту.
>
> **Ценность этого документа — раздел 4:** как писать код сейчас, чтобы переезд в плагин потом стоил
> перемещения файлов, а не переписывания.
>
> Связанные: [`DISTRIBUTED_QUEUE_PLAN.md`](./DISTRIBUTED_QUEUE_PLAN.md) (сам коннектор очереди — его
> спека там, не здесь), [`R2_SYNC_PLAN.md`](./R2_SYNC_PLAN.md).

## 1. Постановка: чем «гейт» отличается от «расширения»

| | Что лежит в ядре | Кто приносит фичу |
|---|---|---|
| **Гейт** (как сейчас, как автопостинг) | сама фича | ядро; плагин только включает видимость |
| **Расширение** (как VS Code) | **generic слоты + API возможностей** | плагин |

Важное наблюдение про VS Code, которое снимает ложную развилку: там **нет** фичи «коннектор
очереди», но там нет и механизма «плагин рисует что угодно где угодно». Есть **contribution
points**: слот для команды, слот для кнопки в меню, слот для секции настроек, слот для дерева в
сайдбаре. **Ядро строит слоты, а не фичи.** Плагин объявляет в манифесте, что даёт, и реализует
поведение в `activate(context)`.

## 2. Что уже есть — и это больше, чем кажется

**Самое сложное в модели contribution points уже построено:**

```
plugin.json → ui.json → controlType ('ddm'|'checkbox'|'slider'|'timecode'|'valueRange'|…)
                              ↓
                      GenericProperty.tsx рендерит по типу
```

Плагин присылает JSON — ядро рисует интерфейс. Это ровно механика contribution point, просто она
прибита к телам нод. Движок есть, реестр типов контролов есть, билдер этого JSON
(`PluginBuilderWin`) тоже есть.

Остальной фундамент:

| Есть | Где |
|---|---|
| Манифест с `type[]` и `apiVersion` | `plugin.json` — механизм объявления возможностей уже заложен |
| Загрузчик возвращает **весь ES-модуль** | [`src/PluginAPI/loader.ts`](../src/PluginAPI/loader.ts) — плагин может экспортировать любые функции, привязки к нодам в загрузчике нет |
| Реактивность вкл/выкл/наличие | `plugin_store`, `useHasAnyPlugin` |
| Протокол доставки ассетов | `plugin://` + `convertFileSrc` |
| Поверхность хоста для плагинов | `_template/tauri.ts` (ffmpeg, exec) — но через **статический импорт**, а не через переданный `ctx` |

`type` сегодня читается в четырёх местах, и все про ноды: `usePluginNodes.ts:25`,
`loadPluginUIs.ts:11`, `CustomNodeSettings.tsx:48`, `plugin_store.ts`. То есть `type` — это
**описание возможностей, а не сущности плагина**; добавить новый тип ничему не противоречит.

## 3. Чего не хватает — по цене

| Contribution point | Цена | Что нужно сделать |
|---|---|---|
| Жизненный цикл `activate(ctx)` / `deactivate()`, тип `runner` | **малая** | держатель инстанса + вызов на вкл/выкл. **Грабля:** loader намеренно не кэширует инстансы (cache-bust из-за module-local `_bound`/`_sendToMW`) → раннер грузить ОДИН раз и держать, а не на каждый тик |
| Команда/кнопка (`contributes.commands`) | **малая** | манифест объявляет `{id, title, icon, slot}`; ядро рисует в отведённом слоте, клик → `mod.commands[id](ctx)` |
| Секция настроек из плагина | **малая** | переиспользовать движок `controlType`: `settings.json` той же схемой, что `ui.json`, отрендерить во вкладку Опций |
| Возможности в `ctx` | **средняя** | работа по проектированию, не по коду: решить, что именно выставляем |
| Произвольная кастомная панель | **большая** | декларативная схема (ограниченно) / React в общем инстансе (падение плагина валит программу) / webview с мостом (безопасно, тяжело) |

Первым четырём строкам хватает для коннектора очереди — кастомная панель ему не нужна.

## 4. Как писать сейчас, чтобы переезд потом был дешёвым

**Это главный практический раздел.** Решение «пишем в ядро» не обязывает писать так, чтобы потом
переписывать.

### Правило 1: точка входа в форме будущего контракта

Модуль коннектора экспортирует ровно то, что потом будет экспортировать плагин:

```ts
// src/PROCESSING/queueConnector/index.ts
export async function start(host: ConnectorHost): Promise<void>
export async function stop(): Promise<void>
export function status(): ConnectorStatus
```

Переезд в плагин = перенести файлы и поменять `import` на `loadPlugin`. Логика не меняется.

### Правило 2: возможности ядра — через тонкий адаптер, а не прямыми импортами

**Плохо:** коннектор напрямую импортирует сторы, `AppMain`-хелперы, `folderState`, `commands.*`.
Тогда переезд = распутывание десятков импортов.

**Хорошо:** один модуль-адаптер, который и станет будущим `ctx`:

```ts
// src/PROCESSING/queueConnector/host.ts   ← ЭТО потом станет ctx
export interface ConnectorHost {
    folders: {
        register(p: { userId: string; projectId: string; prefix: string;
                      displayName: string; sticky: boolean }): Promise<void>;
        list(): Promise<RegisteredFolder[]>;
    };
    processing: {
        startForProject(projectId: string): Promise<void>;
        onProgress(cb: (e: ProgressEvent) => void): () => void;
    };
    settings: { get<T>(key: string): T | undefined; set<T>(key: string, v: T): void };
    log: (level: 'info' | 'warn' | 'error', msg: string) => void;
}
```

Коннектор пользуется **только** этим интерфейсом. Ядро отдаёт его реализацию. Когда придёт время
плагинов — тот же объект передаётся в `activate(ctx)`, и код коннектора не трогается вообще.

### Правило 3: узкие именованные возможности, не сторы целиком

Если `ctx` отдаёт сторы, «плагин» перестаёт быть границей. Давать `folders.register`, а не
`useMainFolders_Store`. Это полезно уже сейчас, до всяких плагинов: границу видно в одном файле.

### Правило 4: связь только в одну сторону

Кнопка в `AppMain.tsx` зовёт `start`/`stop` и больше ничего не знает. Если **ядро** начинает знать
про внутренности коннектора — это сигнал вывернуть зависимость в возможность.
Прецедент уже есть: автопостинг (`startPostScheduler`/`stopPostScheduler` в
`AppMain.tsx:142`, авто-гашение по `postingReady` на `:147`).

### Правило 5: изоляция ошибок с первого дня

Долгоживущий раннер со своими таймерами — не то же, что нодовый плагин внутри пайплайна с ловлей
ошибок по элементу. Один unhandled rejection деградирует всё. Заложить сразу: try/catch вокруг
`start`, watchdog по `status()`, принудительный стоп. Правильный ответ в будущем — отдельный процесс
extension host, как в VS Code; пока избыточно, но направление такое.

## 5. Критерий: что можно выносить в плагин, а что нельзя

| Хороший кандидат | Плохой кандидат |
|---|---|
| Раннеры и вотчеры: TS-only, уровень приложения, ясный `start`/`stop` | **Всё, что резолвит ещё и Rust**: маски (`apply_vars`), резолв путей, сборка ffmpeg-графов |
| Транспортные адаптеры к внешнему сервису (VK/TG/YT — уже так) | Всё на горячем пути обработки: loader перепарсивает модуль на каждый вызов |
| Декларативные данные, которые читает только TS | Всё, что является SSOT для генераторов (`npm run masks:docs`) |

**Разбор конкретного соблазна — вынести маски путей в плагин.** Мотив понятен (обновлять, не залезая
в ядро), но маски **реализованы дважды**: TS в `src/Utils/masks.ts` и Rust `apply_vars`, который
синхронизируется вручную. Плагин расширит только TS-сторону → маска будет работать в одних местах и
молча не работать в других. Это **хуже** текущего состояния: сейчас drift один и известный, а стало
бы по drift'у на каждый плагин. **Не выносить, пока резолв не станет одноместным.**

## 6. Порядок, если/когда возвращаемся

Каждый шаг полезен сам по себе, ничего из предыдущего не переписывается.

1. `activate`/`deactivate` + тип `runner` в манифесте — раннер плагином, включается настройкой
2. `contributes.commands` + слот кнопок — своя кнопка у плагина
3. `contributes.settings` на движке `controlType` — своя секция настроек
4. `ctx` с возможностями (уже спроектирован по правилу 2, если следовали ему)
5. *(только если понадобится)* панели через webview + мост

**Шаги 1–4 = не-нодовый плагин полностью, без предустановленной в ядре фичи.**

## 7. Главный риск, о котором стоит помнить заранее

**Публичный API — это навсегда.** VS Code за десять лет не удалил из своего API ничего: как только
плагины поехали против `ctx`, его поддерживают вечно. Это не сложность реализации, а постоянное
обязательство.

Смягчения: `apiVersion` в манифесте уже есть; начинать с минимального `ctx`; **добавлять, не
менять**; всё, что не уверен — не выставлять.

Именно поэтому отложить — правильно: `ctx`, спроектированный под одну задачу (правило 2), проверится
на реальном коннекторе прежде, чем станет публичным контрактом.
