## 1. Одна фраза

> **Решения о хранилище — на бэкенде. Байты — у меня.**
> Бэкенд говорит «можно, вот подписанная ссылка», а везёт файл моя программа: сервер физически не
> может залить файл, которого у него нет.

Это не компромисс, а стандартная схема, и API коллеги на ней и построено:
«Bytes go directly to/from R2, **not through the API**».

## 2. Разделение ответственности

| | Бэкенд (`innovation-hub`) | Локальный клиент (эта программа) |
|---|---|---|
| Каталог: что существует, где, что изменилось | **да** (Postgres `project_files`) | копия для скорости |
| Журнал изменений, курсоры | **да** (`storage_changes`) | хранит свой курсор |
| Права, кто что может | **да** | не реализует ничего |
| Ключи R2, подписи | **да** | не имеет ключей вообще |
| Раскладка ключей в бакете | **да** | не выбирает |
| Реиндекс, сверка с бакетом | **да** (`/reindex`) | зовёт при нужде |
| **Передача байтов** | **нет** | **да, напрямую в R2** |
| Что лежит на диске, кэш, вытеснение | нет | **да** |
| Локальная рабочая папка, копии вне зеркала | нет | нет — это другая подсистема программы |
| Состояния файлов, значки, UI | нет | **да** |

**Терминология** (чтобы не путаться в разговоре с коллегой): его часть — **бэкенд хранилища**,
моя — **локальный клиент**. Слово «синхронизатор» означает разное для каждого и порождает споры
на пустом месте.

## 3. Две зоны, а не три

Клиент хранилища отвечает **за одну папку** — зеркало. Всё остальное его не касается.

| Зона | Что | Кто следит |
|---|---|---|
| **remote** | R2 через бэкенд | бэкенд |
| **mirror** | зеркало логической структуры, TTL 4 часа | **клиент хранилища** |
| локальная рабочая папка | `localFolder` → `mainWorkFolder`: сюда нода копирует файлы, тут работают ffmpeg / AE / Moho | **уже существующая часть программы**, там своё автоудаление |

> **Ревизия:** раньше в плане была третья зона «scratch» с собственным TTL и CoW-клонированием.
> Это была ошибка: локальная рабочая папка существует в программе давно (`localFolder` в
> настройках), ею занимается другая подсистема, и клиенту хранилища за ней следить не надо.
> Убрано.

Изначальный мотив третьей зоны — «не дать ffmpeg писать в синхронизируемую папку, чтобы не залить
недописанный файл» — закрыт другим решением: **триггер заливки это явный вызов**, а не слежка за
файловой системой. Значит недописанный файл никто и не увидит.

**Путь файла:** в каталоге виден слепок → нода копирования обращается к зеркальному пути →
`ensureLocal` качает → нода копирует в рабочую папку → обработка → результат кладётся в зеркальную
папку → автозаливка → через 4 часа зеркальная копия вытесняется.

## 4. Контракт с бэкендом

Все запросы: `Authorization: Bearer mch_…`. Токен — **непривязанный** к проекту
(`machine_tokens.project_id = NULL`), иначе не пустит даже админа: `scopedProjectId` проверяется
до роли.

| Эндпоинт | Используем для |
|---|---|
| `GET /api/storage/v1/tree?projectId=&prefix=` | bootstrap индекса, `{ entries, cursor }` |
| `GET /api/storage/v1/delta?projectId=&since=` | догон, до 5000 событий, `truncated` → заново `/tree` |
| `POST /api/storage/v1/presign` | подписанная ссылка PUT/GET, TTL 60–86400 (деф. 3600) |
| `POST /api/storage/v1/notify` | **обязательно** после PUT, иначе бэкенд про файл не узнает |
| `POST /api/storage/v1/mkdir` | создать папку (строка в Postgres, объекта в R2 нет) |
| `DELETE /api/storage/v1/object` | удалить файл/папку каскадом |
| `POST /api/storage/v1/reindex` | сверка с бакетом, owner-only, до 120 с |
| `GET/PUT /api/storage/v1/sidecars` | `folderState.json`, `options.json`, `kind: raw` с `ifMatch` |

**Раскладка ключей** (не наша забота, но знать надо):

```
{AWS_S3_PREFIX}/projects/{userId}/{projectId}/project-meta.json
{AWS_S3_PREFIX}/projects/{userId}/{projectId}/options/folderState.json
{AWS_S3_PREFIX}/projects/{userId}/{projectId}/{folderPath}/{uuid}-{safeName}
```

> **`s3Key` непрозрачный.** Логическое имя (`name`) и путь (`folderPath`) живут в Postgres отдельно
> от ключа. **Локальный путь строим из логического пути, не из ключа** — иначе на диске появятся
> папки вида `a3f9c1-clip.mov`.

**Политика загрузки** (`lib/project-upload-policy.ts`) — не блокер: `video/quicktime` разрешён
(ProRes и HAP пройдут, политика смотрит MIME, не кодек), `application/octet-stream` — универсальная
лазейка. Где тип известен — присылать точный, чтобы сайт понимал, что можно проиграть.

### Capability-флаги — приходят с бэкенда

Хардкодить не нужно: **эндпоинт есть.**

```
GET /api/storage/v1/capabilities
→ { "apiVersion": 1, "multipart": false, "rename": true, "copy": false,
    "sharing": false, "clients": true, "originMtime": true, "contentHash": true }
```

Клиент читает их при подключении и по ним гасит недоступные пункты интерфейса. **Нигде в коде не
должно быть предположения «оно есть»** — только проверка флага.

Состояние на 2026-08-07: `rename`, `clients`, `originMtime`, `contentHash` — **есть**;
`multipart`, `copy`, `sharing` — нет.

## 5. Локальный индекс — схема

SQLite в app data (**не** внутри синхронизируемой папки).

```sql
PRAGMA journal_mode = WAL;

-- Копия каталога. Производное, можно снести и пересобрать через /tree.
CREATE TABLE remote_entries (
    file_id      TEXT PRIMARY KEY,   -- UUID бэкенда: СТАБИЛЕН через переименования и переносы
    project_id   TEXT NOT NULL,
    folder_path  TEXT NOT NULL,      -- 'IN', '' = корень проекта
    name         TEXT NOT NULL,      -- логическое имя
    is_folder    INTEGER NOT NULL,
    s3_key       TEXT,               -- NULL у папок; непрозрачный у файлов
    size_bytes   INTEGER,
    content_type TEXT,
    etag         TEXT,
    content_hash TEXT,
    origin_mtime INTEGER,
    last_seq     INTEGER,
    deleted      INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_re_folder ON remote_entries(project_id, folder_path, name);
CREATE INDEX idx_re_name   ON remote_entries(name);

-- ТОЛЬКО эта машина. Никуда не уходит.
CREATE TABLE local_state (
    file_id      TEXT PRIMARY KEY,
    state        TEXT NOT NULL,     -- Cloud|Downloading|Fresh|Stale|LocalOnly
                                   -- |LocalModified|Uploading|Conflict|Error
    local_path   TEXT,
    -- ВАЖНО: local_size и local_mtime — состояние на момент ПОСЛЕДНЕЙ УСПЕШНОЙ
    -- синхронизации (гидрации или заливки), а НЕ текущее с диска. Текущее берётся
    -- stat-ом и сравнивается с ними — это и есть baseline для детекта локальной правки.
    local_size   INTEGER,
    local_mtime  INTEGER,
    synced_etag  TEXT,
    hydrated_at  INTEGER,
    last_access  INTEGER,
    pinned       INTEGER NOT NULL DEFAULT 0,
    error        TEXT
);
CREATE INDEX idx_ls_evict ON local_state(last_access) WHERE pinned = 0 AND state = 'Fresh';

-- Очередь передач: переживает перезапуск.
CREATE TABLE transfers (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    file_id      TEXT,
    project_id   TEXT NOT NULL,
    direction    TEXT NOT NULL,     -- 'up' | 'down'
    local_path   TEXT NOT NULL,
    bytes_total  INTEGER,
    bytes_done   INTEGER NOT NULL DEFAULT 0,
    strategy     TEXT NOT NULL,     -- 'single' | 'multipart'
    upload_id    TEXT,              -- ← для multipart, пока NULL
    parts_done   TEXT,              -- ← JSON [[partNumber, etag]], пока NULL
    attempts     INTEGER NOT NULL DEFAULT 0,
    state        TEXT NOT NULL,     -- queued|active|paused|error|done
    error        TEXT,
    updated_at   INTEGER NOT NULL
);

-- Курсор НА ПРОЕКТ (не глобальный: /delta требует projectId).
CREATE TABLE project_cursors (
    project_id TEXT PRIMARY KEY,
    cursor     INTEGER NOT NULL,
    tree_at    INTEGER
);

-- Что и куда копировали: чтобы нода «переписать устаревший» решала БЕЗ скачивания.
CREATE TABLE copied_files (
    dest_path  TEXT PRIMARY KEY,   -- куда скопировали (вне зеркала)
    file_id    TEXT NOT NULL,      -- из какого файла
    src_etag   TEXT,
    src_hash   TEXT,
    src_size   INTEGER,
    copied_at  INTEGER NOT NULL
);

-- Медиа-характеристики облачных файлов. Заполняется ЛЕНИВО, без скачивания.
CREATE TABLE media_probe (
    file_id   TEXT PRIMARY KEY,
    src_etag  TEXT NOT NULL,       -- инвалидация: etag изменился → проба протухла
    duration  REAL,
    width     INTEGER,
    height    INTEGER,
    codec     TEXT,
    fps       REAL,
    audio     TEXT,
    probed_at INTEGER NOT NULL
);

CREATE TABLE sync_meta (k TEXT PRIMARY KEY, v TEXT);
```

### Метаданные и превью без скачивания

В каталоге бэкенда **нет медиа-характеристик** — он знает файл как объект (размер, тип, `etag`), но
не знает, что внутри. Длительность, разрешение, кодек добываются пробой:

> **`ffprobe` читает по HTTP через Range-запросы** — вытягивает только заголовок контейнера (moov).
> Сотни килобайт вместо гигабайт, ~секунда. Для облачного мастера на 5 ГБ показываем
> «1920×1080, 00:02:34, h264, 25 fps», ничего не качая.

- Кэш — `media_probe`, инвалидация **по `etag`**.
- Заполнять **лениво**: навёл на файл / открыл «Информацию». Не при обходе дерева.
- `+faststart` ускоряет пробу (moov в начале = один короткий Range).
- **Зависимость:** Range-запросы по presigned GET — отдельный пункт проверки в шаге 0.

**Превью картинок:** presigned GET URL отдаётся прямо в `<img src>`, файл на диск не сохраняется. Это
заодно обходит боль WKWebView с `file://`. **Грабля:** для чтения пикселей через canvas
(`getImageData`, `canvasFilters.ts`) нужен `crossOrigin="anonymous"`, а он требует настроенного CORS
на бакете — это настройка владельца бэкенда.

**Превью видео-кадра — отложено осознанно**, обсудим отдельно.

**Ключевое свойство:** `file_id` не меняется при переименовании и переносе. Значит дельта с новым
`name`/`folder_path` у известного `file_id` = **локальное переименование файла в зеркале, без
перекачивания**.

### 6.1. Шов гидрации — главное место всей работы

Объект на обработку собирается **до** того, как файл появится на диске: в каталоге виден слепок,
построен локальный путь, путь положен в объект. **Путь есть, файла нет.** Файл появляется, когда
нода копирования его открывает.

Отсюда неочевидное следствие:

> **Любая проверка `exists()` / `stat()` по зеркальному пути вернёт «файла нет».**
> Если где-то есть «файл существует? нет — пропускаем», негидратированный файл будет молча
> выпадать из обработки.

Значит шов — это не только чтение:

| Что | Почему |
|---|---|
| `exists`, `stat`, размер | иначе пропуск элемента или «0 байт» |
| чтение / открытие | очевидно |
| **нода копирования** | **основной путь, 99% случаев** |
| передача пути внешней программе (AE, ffmpeg, Moho) | они откроют сами, наш код этого не увидит |

### Шов оказался ТРЁХ видов, а не одного

Это выяснилось при реализации и в исходном плане отсутствовало. Одинаково гидратировать всё — ошибка:

| Что нужно коду | Что делать | Где |
|---|---|---|
| **байты** | гидратировать | `read`, `copy`, `hash`, ffmpeg, AE |
| **метаданные** | ответить **из каталога**, НЕ качать | `stat`, `info`, `getFileInfo` |
| **существует ли** | ответить **из каталога**, НЕ качать | `exists`, `pathExists` |

> **Ловушка, которая стоила бы всего архива.** `findFilesForSingleFolder` зовёт `getFileInfo` на
> **каждый найденный файл**. Если бы `stat` гидратировал, первый же обход проекта скачал бы весь
> архив целиком.

И обратное следствие: **`exists` для облачного файла обязан возвращать `true`**, даже если копии нет.
Файл существует — просто пока не здесь. Иначе проверки вида «нет файла — пропускаем» молча выбросили
бы из обработки всё облачное.

Реализовано командой `storage_path_info`: отвечает про путь (существует / локально / размер / время /
`file_id`) **без единого байта по сети**.

**Форма шва — принимает путь, который у кода уже есть:**

```ts
// было
const data = await readFile(p)
// стало
const data = await readFile(await ensureLocal(p))
```

Внутри путь разворачивается в `file_id` через индекс. **Вне зеркала `ensureLocal` — no-op:** путь в
рабочей папке, абсолютный путь из Custom File, режим `PlainFolder` — всё возвращается как есть,
мгновенно.

Это снимает главный риск шага 5: **не надо решать «здесь надо или не надо», ставим везде**, где путь
превращается в файл.

**Полное дерево решений:**

```
абсолютный нормализованный путь
│
├── НЕ под корнем зеркала  →  как раньше: exists? да / нет. Никакой сети
│
└── под корнем зеркала
    ├── разобрать путь в (projectId, folderPath, name)
    ├── в индексе НЕТ такой записи
    │   ├── файл на диске есть  →  LocalOnly (положили руками) → отдать путь
    │   └── файла нет           →  обычная ошибка «не найдено»
    └── в индексе ЕСТЬ
        ├── локально нет                    →  качаем → отдать путь
        ├── локально есть, версия совпадает →  отдать путь  ← быстрый путь, 0 сети
        └── локально есть, в облаке новее   →  качаем заново → отдать путь
```

Две ветки здесь неочевидны:

1. **«Локально есть, но в облаке новее»** — без неё работаешь со старой версией и не знаешь об этом.
   Проверка бесплатная: актуальный `etag` уже в локальном индексе, запроса в сеть не нужно.
2. **«В зеркале есть, в индексе нет»** — файл положили руками, это `LocalOnly`, его надо **залить**,
   а не гидратировать. Перепутаешь — программа полезет качать то, чего в облаке нет.

**Как надёжно определить «под корнем зеркала».** Наивный `startsWith` ломается:

| Грабля | Что делать |
|---|---|
| **Регистр на macOS** | ФС регистро-нечувствительна, сравнение строк — нет. `/Users/x/Mirror` и `/users/x/mirror` — один путь, но `startsWith` скажет «нет». Сравнивать в нормализованном регистре |
| Относительные пути | сначала привести к абсолютному |
| Хвостовые слэши, `..` | канонизировать до сравнения |

Корень зеркала не настроен (режим `PlainFolder`) → под зеркалом не находится ничего, всегда локальная
ветка. Без ветвлений.

**Свежесть индекса.** Быстрый путь доверяет индексу, а индекс догоняется дельтами при открытом
проекте — если проект закрыт, поллинга нет и индекс отстаёт. Поэтому: **один `/delta` в начале витка
обработки**, дальше весь виток доверяем индексу. Один запрос на проект вместо HEAD на каждый файл —
при десяти тысячах элементов это разница между одним запросом и десятью тысячами.

**Где врезано (сделано):**

| Слой | Точка | Охват |
|---|---|---|
| **Плагины** | обёртка `fs` в `src/PluginAPI/host.ts` (плагины импортят его напрямую) | **все 34 плагина, ни один не изменён** |
| Ядро | `src/Utils/storageSeam.ts` + врезки в `findFilesForSingleFolder`, `processItem` | `commands.*` идут мимо шаблона |

Плагинный шов оказался **одним чокпоинтом**: 34 плагина импортируют `fs` из шаблона, поэтому обёртка
там покрыла всех сразу.

**Быстрый гейт — обязателен.** Сканирование локальной папки не должно платить ни одним лишним
IPC-вызовом за облако, которого нет. `storageSeam` один раз спрашивает корень зеркала и кэширует; пока
он пуст, все функции отвечают мгновенно и в Rust не ходят. Кэш сбрасывается при подключении — иначе
шов остался бы выключенным до перезапуска программы.

**Префетч — почти бесплатное улучшение.** `findAllFilesForProcess` строит весь список заранее,
значит известно, какие файлы понадобятся. Пока обрабатывается первый элемент, тихо качаем следующие.
Вместо «каждый элемент ждёт свои три минуты» — «подождал один раз в начале». Новой механики не
нужно: та же очередь передач, задания в неё кладёт раннер.

**Что должно быть видно:** элемент показывает «скачивается 47 %», а не выглядит зависшим; отмена
витка отменяет передачу; два элемента запросили один файл → качаем один раз; не скачалось → элемент
падает с внятным «не удалось получить исходник», а не «файл не найден».

### 6.1.2. Три триггера заливки — реализовано 2026-08-11

План говорил «триггер заливки — явный вызов», но врезан он не был: заливку запускал только пункт
контекстного меню, а фоновый демон **раз в 15 секунд обходил всё зеркало рекурсивно** и на каждый
файл спрашивал индекс. То есть программа платила обходом диска за то, чего в 99 % тиков не
происходило, а результат пайплайна уезжал в облако не потому, что его положили, а потому что до него
дошёл обход.

Теперь работа приходит событием. Три триггера, по убыванию важности:

| | Триггер | Кто зовёт | Задержка |
|---|---|---|---|
| 1 | **Явный вызов** | раннер: `markUploads(outFiles)` после успешного элемента (`processItem`), `flushUploads()` в конце витка (`runProcessing`) | ≤ 3 с |
| 2 | **Вотчер зеркала** | `storage/watcher.rs` — рекурсивный `notify` на корне, поднимается при `attach` | ≈ 6 с (затишье) |
| 3 | **Полный обход** | демон, раз в 10 минут либо при переполнении очереди | до 10 мин |

**Почему нельзя заливать по событию файловой системы.** ffmpeg пишет файл минутами, события идут всё
это время; залить по первому — залить огрызок и объявить его результатом. Ждать «файл закрыт» тоже
нельзя: на macOS FSEvents такого события не даёт вообще. Поэтому кандидат становится готовым либо
**явно** (раннер знает: шаг завершён), либо **по затишью** — размер и mtime не менялись два пульса
подряд (`storage/pending.rs`).

**Очередь кандидатов, а не список файлов.** `pending.rs` держит пути с состоянием осмотра; при
переполнении (`MAX_ITEMS`, `mv` десяти тысяч файлов) поднимает флаг и деградирует к полному обходу —
то есть теряет скорость, но не файлы.

**Эхо.** Вотчер видит и наши собственные записи: скачали файл — пришло событие «создан файл». Гасится
тремя слоями: `.part` и скрытые в очередь не принимаются вообще; `needs_upload` перед заливкой сверяет
файл с baseline; удаления вотчер игнорирует (вытеснение по TTL выглядит для него так же, как удаление
человеком, а заливать по нему `delete` в облако — потеря данных).

**Демон на пульсах** (`daemon.rs`): 3 с — разгрузка очереди, 1 мин — сверка локальных правок, 5 мин —
вытеснение, 10 мин — полный обход. Раньше всё сходилось в один 15-секундный тик.

**Ещё одна дыра, закрытая тем же проходом:** `detect_local_changes` ставил метку `LocalModified`, но
заливать по ней было некому — перерендеренный файл получал значок «надо залить» и ждал ручного
нажатия. Теперь демон забирает такие пути (`index.paths_in_state`) и ставит в очередь.

**Диагностика:** `status.watching` и `status.pendingUploads` видны в Настройки → Хранилище. Слежка,
которая не поднялась, — не поломка, но разница между «за секунды» и «до 10 минут», и молча это
оставлять нельзя.

### 6.1.1. Статистика: JSONL остаётся, меняется момент заливки

`db_analytics.rs` **не трогаем.** Он пишет JSONL рядом с проектом
(`{project}/options/__stat/2026.06.jsonl`) плюс агрегаты в `.json` — децентрализованно, данные
путешествуют вместе с проектом. Это правильная конструкция, и к индексу хранилища отношения не имеет:
статистика про проделанную работу, индекс про то, что где лежит.

**Заменять статистику на SQLite нельзя** — и как раз из-за R2: файл базы в объектном хранилище это
та самая отвергнутая ловушка (объекты неизменяемы → каждая новая строка = перезалив всей базы).
JSONL тут строго лучше.

Но одна вещь меняется:

> **В R2 нет дописывания в конец.** Локально `appendRecord` через `O_APPEND` работает как раньше. А
> попадание файла в облако перестаёт быть бесплатным: каждая новая строка означает перезалив всего
> месячного JSONL целиком.

Лечится не переделкой статистики, а **моментом заливки: один раз в конце витка, а не после каждого
элемента.** Раз триггер заливки явный, раннер сам решает когда.

Порядок цифр: строка ≈ 500 байт, 1000 элементов в месяц ≈ 500 КБ. Заливка раз в виток (20 витков) =
20 PUT'ов и ~5 МБ. На каждый элемент = 1000 PUT'ов и ~250 МБ. **В деньгах разницы нет** (доли цента),
батчим ради того, чтобы не гонять четверть гигабайта впустую.

### 6.2. Нода «переписать устаревший» — проверка ДО гидрации

У ноды копирования есть режим «переписать устаревший». Файл копируется в рабочую папку, живёт там
своей жизнью, а зеркальная копия за это время вытесняется. На следующем витке надо понять, нужно ли
качать заново.

**Порядок критичен** — иначе скачаешь 3 ГБ, чтобы выяснить, что качать было не нужно:

```
1. copyState(src, dest)?     ← локальный индекс: 0 запросов, 0 байт
2. UpToDate → не делаем ничего
3. Stale/Missing → ensureLocal(src)   ← только теперь качаем
4. копируем с заменой
5. recordCopy(src, dest)
```

**Сравнивать не время, а версию источника.** Mtime ломается в трёх местах: часы разъезжаются между
машинами, копирование не всегда сохраняет mtime, и если руками правил локальную копию — её mtime
изменился, а источник нет, и сравнение соврёт.

Поэтому таблица `copied_files` помнит, **из какой версии** сделана копия, и сравнение идёт по
`content_hash`, а если его нет — по `etag`. Правило сразу правильное: когда появится multipart,
`etag` перестанет быть хэшем содержимого, а `content_hash` продолжит работать.

```
copyState(srcMirrorPath, destPath) -> UpToDate | Stale | Missing | Unknown
recordCopy(srcMirrorPath, destPath)
```

`Unknown` — dest есть, а записи о нём нет (скопировали руками или до внедрения). По умолчанию
считать устаревшим и перекопировать: безопасно, случай редкий.

Побочная выгода: файл, который не менялся, **не поедет по сети вообще** — заметная экономия на
повторных витках.

### Два инварианта кэша — не настройки

1. **Никогда не вытеснять незалитое** (`LocalOnly`, `LocalModified`, `Uploading`, `Conflict`, `Error` с непрошедшей заливкой) —
   иначе результат рендера исчезнет вместе с локальной копией.
2. **Никогда не вытеснять горячее и запиненное** — `options/*.json` читаются постоянно.

### Состояние считается в ОДНОМ месте

> Один селектор `badgeState`, один `folderAggregate`. Всё, что рисует значки, зовёт только их.

Иначе через месяц три места разойдутся и папка покажет ✓, когда внутри лежит незалитый файл.
Правило приоритета (**ошибка и «не залито» перебивают всё**) живёт внутри селектора.

### Провайдеры и деградация

```
StorageProvider
├── PlainFolder   — локальная папка / сетевой диск. Всё всегда Fresh, значков нет, заливки нет
├── StorageApi    — бэкенд коллеги
└── MockApi       — фикстуры: заготовленные ответы /projects, /tree, /delta, /capabilities
```

**`MockApi` нужен не только на время ожидания доступов.** Он позволяет разрабатывать и проверять всё,
что выше HTTP-слоя, без сети — и остаётся полезным навсегда: тесты, воспроизведение багов, показ
интерфейса без бэкенда. Фикстуры берём из реальных форм ответов (разобраны по коду роутов, не
выдуманы).

При ненастроенном хранилище программа ведёт себя **точно как сейчас**, без единого `if` в
прикладном коде.

### 6.3. Три направления расхождения и конфликт

Различить «в облаке новее» и «у меня новее» по двум величинам нельзя — обе дают `local ≠ remote`.
Нужна третья: **что было на момент последней синхронизации** (baseline в `local_state`).

| локально vs baseline | в облаке vs baseline | Вывод |
|---|---|---|
| не менялся | не менялся | `Fresh` — ничего |
| не менялся | **изменился** | `Stale` → **качаем** |
| **изменился** | не менялся | `LocalModified` → **заливаем** |
| **изменился** | **изменился** | **`Conflict`** |

Детект локальной правки дешёвый: `mtime` + `size` против записанных baseline-значений. Хэш считать не
надо (у mtime есть ложноотрицательный случай — изменили файл и восстановили время, но это редкость).

**Конфликт не авторешаем.** Оба автоварианта теряют данные: «победило облако» — стёрли свой
перерендер, «победило локальное» — стёрли чужую правку. Поэтому: помечаем `Conflict`, показываем `⚠`,
ничего не трогаем, а в контекстное меню даём **«Залить мою версию»** и **«Взять из облака»**.

**Но у явной заливки конфликтов не бывает** — иначе логика конфликтов налезет на нормальную работу:

| Путь | Что делаем |
|---|---|
| **Пайплайн положил результат и вызвал заливку** | **заливаем, точка.** Явное действие всегда право |
| Фоновое обнаружение (вотчер/сканирование) нашло изменённый файл | считаем baseline, при конфликте помечаем |

Перерендер в тот же путь идёт по первому пути — то есть самый частый случай «у меня новее» проходит
без всякой арифметики.

## 8. UI

**Соответствие уровней.** Онлайн-иерархия трёхуровневая и повторяет локальную:

| Колонка | Локально | Онлайн | Откуда имя |
|---|---|---|---|
| 1 | главные папки | **пользователи (владельцы)** | `users.display_name`, иначе `userId` |
| 2 | проекты | **проекты** | `projects.name` |
| 3 | содержимое | содержимое | `project_files.name` |

> **Ревизия 2026-08-11: первый уровень — ВЛАДЕЛЕЦ, а не клиент.** Клиентский уровень был нашей же
> просьбой (1.0.1), бэкенд его сделал — но `client_id` в живых данных не заполнен ни у одного
> проекта, поэтому группировать по нему нечего. А раскладка бакета `projects/{userId}/{projectId}/…`
> даёт пользователя всегда, и именно её человек видит в панели R2. Поэтому группируем по владельцу;
> `client_id` остался в типах для будущей группировки, папок из него не строится.
>
> Засада: `/projects` **не отдаёт `userId`** (`serializeProject` его теряет, хотя рядом сам же им
> проверяет доступ). До правки бэкенда владелец добывается из `s3Key` двумя способами, и порядок
> важен: (1) ключ из индекса — бесплатно, если дерево уже загружено; (2) **`/presign` на PUT** — один
> запрос, ноль байт. Ключ бэкенд строит сам из владельца (`projectUploadObjectKey(access.ownerId, …)`),
> а объект при этом **не создаётся**: подпись это только подпись, файл появляется от PUT, строка в
> каталоге — от `/notify`.
>
> Второй способ и есть настоящий: он работает у **пустого** проекта. Первая версия умела только
> первый — и у человека владельцы определились лишь у двух проектов из пяти: у двух каталог был пуст,
> а у третьего в нём лежали только папки, а у папок ключей не бывает.
>
> Поле из ответа имеет приоритет, поэтому обходной путь самоустранится.
> Просьба — 1.11 в `STORAGE_BACKEND_REQUESTS.md`.
>
> **Подпись папки владельца:** `email` → `fullName` → `displayName` → «Пользователь <первый сегмент
> id>». Email первый потому, что уникален и узнаваем; `full_name` бывает пустым и повторяется. Полный
> UUID в списке папок нечитаем, а нумерация («Пользователь 1») врала бы — номер зависел бы от состава
> списка. Первый сегмент виден и в панели R2, значит папку можно сверить глазами. В БД бэкенда всё
> есть (`users.email`, `users.full_name`), в ответе `/projects` — нет.
>
> Внутренние имена (`ClientDir`, `MirrorNode::Client`, `storage_clients`) сохранены: это «верхний
> уровень зеркала». Читать их следует как «владелец».

Все три имени меняются **бесплатно**: ключи в бакете от них не зависят (`s3Key` непрозрачный,
`writeRename` его не трогает). Клиентский уровень — связь в Postgres, не папка в бакете; это просьба
1.0.1 в [`STORAGE_BACKEND_REQUESTS.md`](./STORAGE_BACKEND_REQUESTS.md). Если его не будет — стартуем
с плоского списка проектов в колонке 1.

**Колонка 1** — `MyDivider` делит на «Локальные» / «Онлайн», своя кнопка добавления в каждой секции,
фильтр сверху (**только по этой колонке**, кросс-проектный поиск уже есть в модалке 🔍). Пустая
секция сворачивается до разделителя. Кнопка «Добавить онлайн-папку» показывает список клиентов
(или проектов, если клиентского уровня не будет), полученный от бэкенда.

**Колонки 2 и 3** — значки на папках и файлах. Признак «онлайн» — иконка `Cloud` + подпись в
`TopPanelGD` («Папка Пользователя · онлайн»); цвет тени вторичен, сам по себе он слабый сигнал.

**Контекстное меню** — новые пункты (это **данные** для `ContextMenuItem`, компонентов не нужно):
Скачать · Обновить · Оставить оффлайн · Освободить место · **Информация**.
Пункты Переименовать / Копировать — **задисейблены по `Caps`** с тултипом.

**Модалка «Информация»** — дерево **только папок**, ленивое раскрытие, четыре колонки:
имя / файлов / размер / **локально**. Внутренние папки (`options`, `_*`) приглушены, не скрыты.
Данные: локальный индекс → при отсутствии префикса в индексе показать **«не знаю»**, а не «0 Б», и
предложить обход. Клик по папке → переход (путь из ProjectSearch + `requestAnimationFrame`).
Действия: скачать поддерево (**с подтверждением объёма**), освободить место.

**Панель передач** — прогресс, пауза, отмена, ошибки.

**Клик по облачку на папке** — рекурсивная гидрация, поэтому **с подтверждением**:
«Скачать 47 файлов, 52 ГБ?» Цифры бесплатны, они уже в индексе.

Диагностика: счётчики запросов, скачано/залито, время последнего `/tree`.

### Токен, а не ключи от R2

Выданные ключи бакета (`AWS_S3_BUCKET`, `AWS_ENDPOINT_URL`, `S3_KEY_ID`, `S3_SECRET_KEY`) — это
**конфиг бэкенда, а не то, чем пользуется программа**.

> Если работать ими напрямую, файлы попадут в бакет **мимо каталога**: строк в Postgres не появится,
> журнал не пополнится, и **сайт этих файлов не увидит** — пока кто-нибудь вручную не запустит
> `/reindex`. Это ровно тот рассинхрон, ради устранения которого бэкенд и написан.

Ключи стоит сохранить для трёх вещей: PoC и замеров, ручного разбора в панели Cloudflare, разовой
миграции с гуглдиска. Программа на них не строится.

### Помощь под полем «Всегда горячие»

Синтаксис — glob-маски от корня проекта, по одной в строке. Текст подсказки:

> Эти файлы не удаляются с диска по таймеру и всегда остаются доступны мгновенно.
> Указывай **мелкие файлы, которые читаются часто** — настройки, сайдкары.
> Видео и мастера сюда добавлять не нужно: они займут диск и не дадут его освободить.
> Маски пишутся от корня проекта: `options/*.json`, `IN/*.txt`, `*.aep`

Дефолт правильный, 95 % пользователей поле не трогают.

Чего в настройках **нет**: Account ID, бакет, ключи R2, версионирование, lifecycle — это бэкенд.

## 10. Multipart: заложить сейчас, включить потом

**Проблема:** `/presign` отдаёт **один** PUT-URL. Одиночный `PUT` в S3/R2 ограничен **5 ГиБ** и не
возобновляется: оборвалось на 4 ГБ — начинай сначала. Бэкенд это изменить не может, потому что
байты идут мимо него; нужны multipart-эндпоинты.

Что делаем **сейчас**:

1. **Схема готова** — `transfers.upload_id` и `transfers.parts_done` уже в DDL. Не удалять.
2. **Исполнитель — стратегия, а не одна функция:**
   ```rust
   trait UploadStrategy { async fn run(&self, t: &Transfer) -> Result<ObjectMeta>; }
   struct SinglePut;   // реализуем
   struct Multipart;   // заглушка
   ```
3. **Выбор по размеру:** `size > multipart_threshold` → `Multipart`.
4. **Гейт по `Caps`:** попал в ветку Multipart, а `caps.multipart == false` → **понятный отказ до
   начала передачи**, а не падение на 4 ГБ из 5.
5. В настройках порог и число частей показываем **задисейбленными** с подписью «бэкенд пока не
   поддерживает».

Когда появятся `create` / `presign-part` / `complete` / `abort` — пишем одну реализацию трейта и
снимаем флаг. Больше ничего не трогается.

**Так же с `rename` и `copy`:** пункты меню есть, задисейблены по `Caps`.

### Демо-сервер — почему он оказался ключевым

Изначально шов (шаг 6) планировался **после** проверки на живом бэкенде. Ход, который снял эту

бэкенда.

Мок остаётся полезным навсегда: тесты, воспроизведение багов, демонстрация.

## 13. Граблевник

### Контракт бэкенда

1. **`s3Key` непрозрачный** → локальный путь строить из `folder_path` + `name`.
2. **Presign живёт час** → запрашивать в момент старта передачи, не пачкой на всю очередь.
3. **`/notify` обязателен** после PUT, иначе бэкенд про файл не знает.
4. **`/delta` максимум 5000 событий** → крутить в цикле; `truncated` → выбросить индекс и заново `/tree`.
5. **Курсор на проект**, не глобальный.
6. **Одиночный PUT ≤ 5 ГиБ и без докачки** → гейт по `Caps` до начала передачи.
7. **`options` зарезервирован** бэкендом — 403 на `mkdir` и `delete`.
8. **`scopedProjectId` проверяется до роли** → для программы выпускать непривязанный токен.
9. **Ретеншен журнала ~90 дней** → машина, не включавшаяся дольше, получит `truncated`.

### Охват синхронизации: «тёплое» вместо режимов (2026-08-11)

Идея двух режимов (ленивый на машине обработки / активный у оператора) **отменена как
настройка** — и правильно: переключатель описывал бы то, что и так следует из работы.

**Правило одно: синхронизируется то, с чем работают.**

| Касание | Кем | Что подтягивается |
|---|---|---|
| открыл папку пользователя | рукой | список его проектов (уже из `/projects`) |
| зашёл в проект | рукой | `/tree` этого проекта (`ensure_catalog`) |
| раннер взял проект в виток | кодом | `/delta` этого проекта |

Дальше проект считается **тёплым** `WARM_WINDOW` (15 минут) и живёт в опросе дельт; не
трогали — выпадает сам (`warm_projects` выбрасывает остывшие тут же, иначе список рос бы вечно и
«ленивое» превратилось бы в «всё подряд»).

Отсюда обе картины получаются сами, без флага:

- **оператор** лазает по папкам руками → тёплым оказывается то, что он открывал;
- **машина обработки** трогает один проект задачи → опрашивается только он, а не вся папка
  пользователя. Когда появится очередь задач ([`DISTRIBUTED_QUEUE_PLAN.md`](./DISTRIBUTED_QUEUE_PLAN.md)),
  источник касания сменится с «включённые папки» на `projectId` из задачи — механика та же.

Файлы в обоих случаях качаются **по требованию** и так, это ядро зеркала: папки видны из каталога,
байты приезжают на `ensureLocal`.

Повторный полный `/tree` (раз в 10 минут) — тоже только по тёплым: нужен ровно для того, чтобы
увидеть **чужое переименование**, которое бэкенд не журналит (просьба 1.8). Перечитывать проекты, с
которыми никто не работает, значит платить за чужую папку без причины.

### Каталог синхронизируется сам (2026-08-11)

Требование: **все изменения онлайн-объектов идут через бэкенд и синхронизируются постоянно** —
переименовал на сайте, поехало здесь; переименовал здесь, поехало на сайте.

| Что | Как |
|---|---|
| Опрос дельт | демон, раз в 30 с (`DELTA_EVERY`), по проектам с `tree_at`; раньше `/delta` звали только в начале витка и из модалки — при простое программа про облако не узнавала ничего |
| Чужое переименование → диск | `reconcile_local_paths`: логический путь изменился → **двигаем локальную копию на диске** и правим `local_state.local_path` |
| Создание папки | `POST /mkdir` в каталог, потом на диске (`mkdir_in_cloud`) |
| Удаление | `DELETE /object` каскадом, потом с диска (`delete_in_cloud`); записи каталога забываются (`forget_files`), а не помечаются вытесненными |

**Почему сверка путей обязательна.** Дельта меняет логический путь записи, но файл на диске от этого
не двигается. Копия остаётся по старому пути, сверка её там не находит, решает «удалили руками» и
обнуляет baseline — свежий файл на диске начинает показываться как «только в облаке».

**Что мешает первому пункту прямо сейчас:** бэкенд переименования **не журналит вообще** (просьба
1.8). Значит чужое переименование придёт не дельтой, а только полным `/tree`. Наша часть готова:
появятся события — применятся тем же циклом, без правок у нас.

**Папка, созданная только на диске, для облака не существует** — нет строки в каталоге, значит нет
`file_id`, значит ни переименовать, ни удалить через API, ни значка. Ровно это и ловил человек:
«создать могу, переименовать — нет, удалить могу (потому что папка только на диске)». Теперь создание
идёт через каталог.

**Значок у папок вместо иконки папки.** В трейлинге стоял `FolderClosed` для агрегата `empty` — то
есть «это папка», что и так видно по большой иконке слева. Пустая папка синхронизирована по
определению (скачивать нечего) → `CircleCheck`. Остальные агрегаты уже были осмысленными: `allCloud`
— ничего не скачано, `mixed` — частично, `allLocal` — скачано полностью, `needsUpload` — внутри есть
незалитое.

### Активность проекта: каталог важнее сайдкара (2026-08-12)

Галочка «проект активен» во второй колонке и переключатель на сайте — одно состояние. Направления:

| Направление | Как | Статус |
|---|---|---|
| сайт → программа | `is_paused` приезжает в каждом `/projects` → снимаем галочку в `reloadFolders` | ✅ работает, колонка на проде есть |
| программа → сайт | `storage_set_project_paused` → `POST /project-state` | ⬜ ждёт эндпоинта (просьба 5.1) |

**Порядок был ошибкой.** Блок синхронизации паузы стоял ДО `hydrateMainFolder`, а гидрация из
`options/folderState.json` его затирала: файл «выигрывал», и снятая на сайте галочка возвращалась
обратно. Два источника истины на один флаг — верный способ получить «не переключается».

Решение: для **облачных** проектов истина — каталог (`projects.is_paused`), его пишет сайт.
`folderState.json` остаётся локальным папкам и офлайн-кэшу. Блок перенесён после гидрации.

Новых полей в БД для этого не нужно — колонка есть, не хватает только эндпоинта.

### Что реально задеплоено на бэкенде (проверка 2026-08-12)

`GET /projects` под machine token на живом `ffworks.pro` отдаёт: `clientId, groupName, id, isActive,
isPaused, name, updatedAt`.

**Ни `userId`, ни `isArchived`, ни массива `users`** — эти правки лежат у коллеги в рабочем дереве
незакоммиченными, на прод не задеплоены. Отсюда два «наших» симптома, которые нашими не являются:

- архивный проект не показывается вообще — показывать нечего;
- папки владельцев подписаны `Пользователь 093025a9` вместо email.

Вывод на будущее: прежде чем искать баг в клиенте, стоит спросить сам эндпоинт — один `curl` снимает
час гадания.

### Одно действие — одна реализация (инвариант, 2026-08-12)

**Горячая клавиша и пункт меню обязаны делать одно и то же.** Визуально действие одинаково для
локального и облачного файла, а внутри различается — и различие живёт **в одном месте**:
`fileSystemActions` (+ шов `storageSeam`). Компоненты вызывают эти функции, а не `commands.*`.

Нарушения, найденные при проверке, и чем они пахли:

| Точка | Что было | Симптом |
|---|---|---|
| `Delete` (клавиша) | своя функция звала `commands.deleteItem` напрямую и обрезала колонку | «нажимаю — ничего не происходит»: копия стёрта, запись в каталоге осталась, строка вырезана, хотя путь живой |
| `deleteAfter` в раннере | `commands.deleteItem` напрямую | облачный исходник оставался в каталоге → следующий скан находил его снова и обрабатывал заново |
| Пробел (превью) | `previewOpen` без гидрации | у нескачанного файла превью пустое, хотя «Открыть» в меню того же файла работал |

Правило на будущее: **в компонентах не должно быть `commands.copyItem` / `moveItem` / `deleteItem` /
`renameFile` / `previewOpen`** — только вызовы общего слоя. Единственное исключение — явная ветка «это
локальный путь», написанная рядом с облачной (например, локальное переименование проекта).

Проверяется грепом:

```bash
grep -rn "commands\.\(copyItem\|moveItem\|renameFile\|renameFolder\|createFolder\|deleteItem\|previewOpen\)" src/MAIN_WIN
```

### Перенос — тот же `/rename`, только папка (2026-08-12)

Последняя мутация, которая молча расходилась с каталогом. Перенос в зеркале шёл по диску
(`moveItem`), то есть болел ровно тем же, чем болело переименование: путь перестаёт разбираться,
`browse` отвечает «не найдено в каталоге», колонка читает диск, значки исчезают, а в облаке файл
остаётся в прежней папке.

Теперь `move_in_cloud` → `/rename` со сменой `folderPath`. Для бэкенда это `UPDATE` логического пути:
**байты не двигаются вообще**, `s3Key` от папки не зависит. Перенос папки с сотнями гигабайт внутри
стоит один SQL-запрос.

Врезано во все три пути: вставка из буфера (`cut`), drag внутри эксплорера, drop на папку проекта.

Что отклоняем и почему:

| Случай | Ответ |
|---|---|
| приёмник вне зеркала | `None` — это выгрузка наружу: гидрация + обычное копирование, не наше дело |
| та же папка | `None` без запроса — гонять сеть ради ничего незачем |
| другой проект | понятная ошибка: `/rename` работает в границах `project_id`, переноса между проектами у бэкенда нет |
| папка внутрь себя | ошибка — в каталоге это дало бы цикл, из которого логический путь не восстановить |

**Порядок проверок:** структурные (внутрь себя, другой проект) — **до** гейта по `caps`. Бессмыслицу
надо отклонять как бессмыслицу, иначе сообщение «бэкенд не поддерживает перенос» уводит от настоящей
причины. Тест на это есть — он же и поймал неверный порядок.

### Колонка 1: обновление и удаление владельца (2026-08-12)

Проверил спеку 4.4 и 5.1 — обе работали **наполовину**.

**«Обновить» (4.4)** дёргала `/projects`, то есть обновляла только список проектов. Содержимое
проектов оставалось таким, каким его застал последний заход. Добавлено `syncNow()` →

**Удаление владельца (5.1)** убирало запись из колонки и ключ из LS, а **локальные копии оставались

Что здесь важно и неочевидно:

| Правило | Почему |
|---|---|
| онлайн не трогаем вообще | «убрать из колонки» = «на этой машине не нужно», а не «удалить в облаке». Записи каталога остаются, добавить обратно можно всегда |
| **незалитое не стираем** | инвариант кэша: в `LocalOnly`/`LocalModified`/`Uploading`/`Conflict` лежит работа, которой в облаке ещё нет |
| папку владельца уносим только если незалитого не осталось | иначе снесли бы вместе с ней то, что решили сохранить |
| отчёт возвращает `keptUnsafe` | интерфейс обязан сказать «удалено не всё», а не соврать «готово» |

### Префетч исходников (2026-08-12)

Очередь строится целиком заранее, значит уже известно, что понадобится. `prefetchNextItems()`
тянет исходники следующих трёх элементов, пока обрабатывается текущий: вместо «каждый элемент ждёт
свои минуты по очереди» — «подождали один раз в начале».

Безопасно по построению: `ensureLocal` в Rust — single-flight по файлу, поэтому когда до элемента
дойдёт настоящая очередь, он не начнёт вторую передачу, а дождётся этой же. Худшее, что может
сделать префетч, — скачать файл, который потом не понадобился (виток прервали); он ляжет в зеркало и
вытеснится по TTL, как любой другой.

Тянем **последовательно**: три параллельных мастера отобрали бы полосу у файла, который нужен прямо
сейчас. Список отданных путей сбрасывается на старте витка.

### Конфликт разрешается двумя стрелками в строке (2026-08-11)

**Только у файлов.** Папок в R2 физически нет — они строки в Postgres, и расхождение содержимого
возможно только у файла. Поэтому стрелки живут в компоненте строки файла (`CurentFileItem`), а у папок
остаётся лишь агрегат `⚠` «внутри есть конфликт»: он указывает, куда идти, но решения не предлагает —
решение принимается по конкретному файлу.


Состояние `Conflict` считалось и рисовалось `⚠`, а **разрешить его было нечем**: пунктов в меню не
было, и строка просто висела с предупреждением.

Теперь рядом со значком появляются две стрелки: вниз — «взять из облака», вверх — «залить мою».
Выбор стоит **в строке, а не в контекстном меню**, потому что конфликт требует именно выбора, а не
повтора действия: спрятанный выбор оставляет человека с непонятным `⚠`. Тултипы называют цену
(«локальные правки будут потеряны» / «облачная будет перезаписана») — обе ветки что-то теряют, и
человек должен понимать что.

Исполнение — `storage_resolve_conflict(path, takeCloud)`:

- **взять облако:** сначала снять метку и обнулить baseline (`mark_evicted`), потом убрать файл, потом
  обычная гидрация. Порядок важен: между шагами сверка не должна увидеть «файл пропал» и решить за нас;
- **залить свою:** снять метку в `LocalModified` **до** заливки — `upload_local` файлы в состоянии
  `Conflict` не трогает, и без этого заливка молча ничего бы не сделала.

### Статистика: файл на машину (2026-08-11)

`options/__stat/2026.08.jsonl` → `options/__stat/2026.08.<имя-хоста>.jsonl`. В объектном хранилище нет
дописывания в конец: заливка перезаписывает объект целиком, и две машины, пишущие один файл, затрут
строки друг друга — тихо и задним числом. Со своим файлом конфликта нет по построению.

Имя хоста, а не uuid: его видно глазами, и когда через полгода придётся разбираться, чья это
статистика, отвечать будет само имя. Приводится к безопасному куску имени файла
(`Alexeys-iMac.local` → `alexeys-imac`), спрашивается один раз за процесс.

**Метка добавляется ТОЛЬКО в зеркале.** Локальная папка, которая ни с чем не синхронизируется,
затирать друг друга не может — там метка была бы мусором в имени. Проверка через
`paths::under_global_mirror` (корень зеркала кладётся в глобал при `attach`, снимается при `detach`) —
единственный потребитель этого глобала, тащить `StorageService` в статистику ради одного вопроса
незачем. Сама `machine_scoped_if` принимает флаг **аргументом**, а не читает глобал внутри: так её тест
не зависит от того, что параллельно делают другие тесты (грабля 11 — тест с недетерминированным
входом скрывает ошибку).

Чтение статистики за месяц становится склейкой файлов всех машин — это впереди, сейчас её никто не
читает.

### Удаление: две ступени (2026-08-11)

**Первое нажатие — только локальная копия, второе — облако.** Одноступенчатое удаление стирало
запись каталога и объект в R2 сразу, а **корзины у бэкенда нет** (`writeFileDelete` делает
`DELETE FROM project_files` + `DeleteObjectCommand`) — отменить было нечем. Для мастера, который
считали часами, единственной защитой оказывалось «не нажми лишний раз».

| Ситуация | Ступень | Что делаем |
|---|---|---|
| есть локальная копия | 1 | удаляем копию, `mark_evicted` (НЕ `forget_files`: в облаке файл остался), значок → «только онлайн» |
| копии нет, файл в каталоге | 2 | `NeedsConfirm` → подтверждение → `DELETE /object` + `forget_files` |
| в каталоге записи нет (`LocalOnly`) | одна | просто стираем с диска: в облаке удалять нечего |

Для **папки** «локальная копия есть» означает «внутри есть хоть один скачанный файл»: удалить папку
целиком по первому нажатию значило бы снести всё поддерево в облаке.

Подтверждение — `window.confirm` с прямым текстом «восстановить будет нельзя: корзины на стороне
сайта пока нет». Когда корзина появится (просьба 6), текст меняется на «уйдёт в корзину на 30 дней», а
механика остаётся.

`mark_evicted`, а не `forget_files`, на первой ступени — принципиально: baseline обнуляется, иначе
повторное скачивание сочтёт файл «локально изменённым» и попросит заливку (грабля 12).

### Копирование облачного файла наружу требует гидрации (2026-08-11)

`ensureLocal(src)` **перед** `copyItem`/`moveItem` — иначе копируется пустота: в каталоге файл есть,
на диске нет. Врезано во все три пути наружу: вставка из буфера (`pasteFromClipboardFs`), перетаскивание
(`dragOut`), drop на проект (`CurentProjectFolder`). Вне зеркала вызов ничего не делает, так что
локальные файлы работают как раньше.

Копия в новом месте — обычный локальный файл, синхронизатор за неё не отвечает (спека 7.5).

### Статистика: `options/__stat/*.jsonl` в горячих по умолчанию (2026-08-11)

Дефолт горячих масок был `options/*.json` и **не покрывал stat-файл**. Статистика дописывается в конец
на каждом элементе, а в R2 дописывания нет — вытесненный между дописываниями файл пришлось бы качать
заново каждый раз. Теперь дефолт из двух шаблонов.

### Переименование (2026-08-11)

**Локальное переименование ломало связь с каталогом — и это стоило значков.** Имя живёт в каталоге
бэкенда; переименуй только на диске, и `classify` такую папку не найдёт → `browse` ответит «не найдено
в каталоге» → `browseMirror` вернёт `null` → колонка молча прочитает диск → **у файлов исчезнут все
значки синхронизации**, а в облаке имя останется прежним. Именно так это и выглядело при первой
проверке: «не вижу значка» и «на сайте не переименовалось» — один и тот же баг.

Теперь `renameFile`/`renameFolder` в `fileSystemActions` идут через шов: в зеркале → `POST /rename`
(`s3Key` не трогается, байты не двигаются) → переименование локальной копии → каскад в индексе
(`reprefix_children` + `rebase_local_paths`, потому что **бэкенд потомков не журналит**) → событие
`storage-changed` на обе папки. Вне зеркала — как раньше.

**Уровни выше проекта** дают внятный отказ: имя владельца это email из БД сайта, имя проекта —
`projects.name`. В меню пункт остаётся на месте, но серый и с пояснением в подписи («Переименовать —
на сайте»), двойной клик по имени онлайн-проекта поле ввода не открывает. Эндпоинта для
переименования проекта под machine token нет — просьба 5 в `STORAGE_BACKEND_REQUESTS.md`.

Принцип, который стоит держать: **меню одинаковое для локального и облачного, механика разная,
результат один.** Поэтому пункты не убираются и не переименовываются — добавляется только то, чего у
локального файла быть не может (скачать/залить/оставить оффлайн).

### Архивные проекты (2026-08-11)

Бэкенд добавил `is_archived` / `archived_at` (миграция `2026-08-11-project-archive.sql`), и в его
`STORAGE_API.md` записано прямо: **обработчик обязан пропускать архивные проекты.**

Три флага рядом, и путать их нельзя: `is_paused` — человек приостановил, `is_active` — legacy-зеркало
`!is_paused`, `is_archived` — уехал в архив. **Архивность не выводится из `group_name`** — группа
отвечает только за раскладку интерфейса сайта.

У нас сделано:

| Что | Где |
|---|---|
| Флаги в типе и индексе (схема v4) | `types.rs`, `index.rs` |
| Признак в строке проекта листинга | `BrowseEntry.archived` (только у строк проектов) |
| Вопрос по пути для раннера | `storage_project_info` → `projectArchived` в шве |
| **Пропуск обработки** | `findAllFilesForProcess`, ПОСЛЕ `/delta` — флаг мог измениться на сайте |
| Значок перед именем проекта | `ProjectFolderItem` + `archivedProjects_store` |

Почему значок питается стором, а не пропом: колонка проектов получает от главной папки только
**имена** (`projectFolders: string[]`), и тащить архивность через всю цепочку пропов ради иконки
значило бы менять форму данных у всех, включая локальные папки. Набор наполняет `reloadFolders` — он
и так читает каталог зеркала на каждом проходе, так что отдельного запроса значок не стоит.

Решение обработки при этом **не зависит от интерфейса**: раннер спрашивает каталог сам. Если
запрос не удался, проект считается неархивным — молча потерянный виток хуже, чем обработка архивного.

### Найдено при первом подключении к живому бэкенду (2026-08-11)

42. **У файла вне каталога прогресс не показывался в принципе.** Строка такого файла рисуется обходом
    диска (`merge_local_only`) с жёстко прошитым `LocalOnly` и `progress: None`, а `badge_state`
    начинается `FROM remote_entries` — то есть для файла, которого в каталоге ещё нет, состояние не
    считается вообще. У новой заливки `file_id` появляется только из ответа `/notify`, поэтому связать
    строку с передачей можно лишь **по пути**. Итог до правки: файл на 200 МБ полторы минуты показывал
    статичную стрелку «надо залить» — заливка шла, а на экране не двигалось ничего.

43. **Колонка сравнивала только пути — и выбрасывала обновление значка.** Самая дорогая грабля этой
    серии: Rust эмитил события, кэш сбрасывался, `refreshAffectedColumns` находил колонку, папка
    перечитывалась заново — а `refreshColumn` в конце сравнивал старый список с новым **по длине и
    путям** и, не найдя разницы, возвращал прежнее состояние. Свежие данные молча уходили в мусор.
    У облачного файла путь не меняется никогда: меняются `state`, проценты, пин, агрегат папки. То
    есть защита от мерцания гасила ровно то единственное, что и должно было обновляться.
    Симптом идеально маскировался под «события не приходят»: значок оживал только при уходе в другую
    папку и обратно — там колонка **создаётся заново**, а не сравнивается. Отсюда же второй симптом —
    «показывает тот процент, на который я попал»: одно чтение при входе, дальше тишина. При этом
    верхняя панель проценты крутила исправно (она читает статус, а не колонки), что уводило поиск в
    Rust, где всё было в порядке. **Урок: любой guard «ничего не изменилось» обязан сравнивать то, что
    рисуется, а не то, что удобно сравнить.** Сравнение вынесено в `sameItem`, и форма
    `FileItem['storage']` теперь берётся из `MirrorItem` — своя копия типа уже успела разойтись
    (в ней не было `archived`/`paused`, и сравнение молча их не замечало).

44. **У заливки прогресс писался в базу ПОСЛЕ ответа сервера — то есть никогда.** Тело PUT идёт
    потоком с диска, обёртка над потоком считает байты в `AtomicI64`, но она синхронная и в базу
    писать не может; единственная запись `bytes_done` стояла после `send().await`. Итог: файл на
    200 МБ всю заливку показывал «↑ 0 %» — значок был правильный, число мёртвое. Проверено по живой
    базе: у заливки `bytes_done` совпал с `bytes_total` (записан один раз, в конце), у скачивания
    того же файла — 210 из 212 МБ (пишется по ходу, раз в 4 МБ).
    **Второй симптом из той же причины:** в `active` передачу переводит именно запись прогресса
    (`set_transfer_progress`), поэтому строка всю заливку оставалась `queued` — а верхняя панель
    считает только `active` и показывала прочерк, пока у файла уже стоял значок заливки. Значок и
    панель расходились, и это уводило поиск в интерфейс, хотя причина была одна.
    Лечение: `report_progress_while` — запрос и опрос счётчика в одной задаче через `select!`, тик
    500 мс, первый тик отчитывается всегда (им и снимается `queued`). У скачивания порог свой (4 МБ)
    и остаётся в цикле чтения чанков: там события идут от сети, а не от таймера.
    Ограничение помощника: внутри переданного future нельзя ждать того, что зависит от продвижения
    этой же задачи — пока ветка тикера ждёт лок каталога, future не опрашивается. Для сетевого
    запроса условие выполняется всегда, но помощник общий, поэтому оговорено в доке.

45. **Заливка стояла в общем цикле демона — и на время передачи глушила весь демон.** `upload_round`
    ждёт каждую передачу целиком, а тик живого прогресса стоял в том же цикле следующей строкой.
    Файл на 450 МБ останавливал пульс на минуты: не эмитился прогресс, не шли дельты, не обновлялся
    список проектов. То есть **чем крупнее файл, тем надёжнее пропадал его значок** — ровно наоборот
    к ожиданию.
    Диагностика заняла долго из-за обманчивой картины: в модалке передач и в верхней панели проценты
    бежали, и это выглядело доказательством, что события ходят. А они там не при чём — оба
    потребителя **опрашивают Rust по таймеру** (в `SyncStatusButton` так и написано: «Опрос вместо
    событий»). Значок же у файла живёт только на событиях. **Урок: прежде чем искать поломку в
    доставке событий, проверь, не опрашивает ли Rust по таймеру тот индикатор, который «работает».**
    Попутно исключено (и это стоит помнить, чтобы не проверять снова): broadcast `app.emit` доходит
    до window-scoped слушателя — в `tauri-2.11.3` `emit_js_filter` вызывается с `filter: None`, а
    `match_any_or_filter` при `None` даёт `unwrap_or(true)`, то есть цель слушателя не сверяется вовсе.
    Лечение: заливка вынесена в свою задачу (`start_uploads`), пульс остался быстрым. Передачи
    по-прежнему последовательные — параллелить их отдельное решение, уплинк один.

46. **Список передач хранил всё завершённое.** Успешная синхронизация — закрытый вопрос, а список
    про то, что происходит сейчас; доехавшие файлы закапывали едущий. Фильтр (`state <> 'done'`)
    поставлен в SQL, а не в интерфейсе: у списка было ДВА потребителя, и правило, скопированное в
    оба, разъехалось бы. Ошибки остаются видны намеренно. Заодно удалён `TransfersPanel.tsx` —
    мёртвый (никем не импортированный) дубль той же логики опроса; правка в нём не дала бы эффекта,
    а на такую ловушку в этом проекте уже тратили время (грабля 41).

47. **ГЛАВНАЯ грабля серии: `memo`-компаратор строки не сравнивал `storage`.** `DraggableFileItem` и
    `DraggableFolderItem` обёрнуты в `memo` со СВОИМ компаратором:
    `name && path && isSelected && isActiveSelection && isMultiSelected`. Значка синхронизации в этом
    списке не было — а у облачного файла имя и путь постоянны, меняется ровно значок. React честно
    отвечал «пропсы те же» и строку не перерисовывал **никогда**. Работало только после ухода в
    другую папку и обратно: там компонент монтируется заново, компаратор не при чём.
    Диагностика заняла три круга и вот почему: **симптом идеально имитировал «события не доходят»**.
    Проверено и отброшено по пути — сравнение в сторе (грабля 43), доставка broadcast до
    window-scoped слушателя (исходник Tauri), блокировка демона заливкой (грабля 45), запись
    прогресса (грабля 44). Каждая из них была настоящей ошибкой и требовала правки, но ни одна не
    была ЭТОЙ. Решил дело зонд, писавший в файл прямо из стора: в логе было видно
    `["файл","downloading",0.709]` → `0.727` каждые 3 секунды — то есть данные доезжали до стора, а
    на экране стояла стрелка «надо залить». После этого оставался единственный подозреваемый.
    **Урок методический:** когда «данные есть, а на экране нет», следующий шаг — не искать поломку
    ещё глубже в поставщике, а **измерить границу** стор↔рендер. Один зонд в файл дешевле трёх
    правильных догадок.
    **Урок технический:** любой ручной компаратор `memo` — это тот же guard «ничего не изменилось»,
    и он обязан сравнивать всё, что рисуется. Правило теперь ОДНО на всю программу — `sameStorage`
    в `readDirContent.ts`, — и его зовут все три места (стор колонок и оба компонента строки).
    Своя копия правила в этом файле уже однажды разошлась (в ней не было `archived`/`paused`).

48. **У упавшей передачи не было ни одного действия.** Строка с ошибкой висела в списке вечно: ни
    повторить, ни убрать. Список при этом отвечает на вопрос «всё ли в порядке» — и отвечал «нет»
    про давно решённое. Добавлены `storage_retry_transfer` и `storage_dismiss_transfer` (кнопки ↻ и
    корзина на строке с ошибкой). Повтор заливки ставит файл в очередь сразу, без ожидания затишья:
    файл лежит на диске давно. Повтор скачивания уходит фоновой задачей — гидрация идёт минутами, и
    команда, которая её дожидается, повесила бы интерфейс. Если исходника больше нет, «Повторить»
    снимает задачу и говорит об этом текстом: молча удалять чужую задачу нельзя.

49. **«Остановить» останавливало только строку, а не заливку.** Отмена проверялась ровно в одном
    месте — цикле чтения кусков при СКАЧИВАНИИ. У заливки своего цикла нет: тело уезжает потоком
    внутрь `reqwest`, и про отмену она узнать не могла. Строка красилась «отменено», байты ехали до
    конца. Лечение — проверка в тике `report_progress_while` (единственная точка, где заливка вообще
    может что-то узнать по ходу): `None` роняет future запроса, соединение закрывается. Объект в
    бакете при этом не появляется (PUT атомарен) и `/notify` не звался — то есть требование
    «остановил, и в облаке этого файла нет» выполняется буквально, без отдельного удаления.
    Оговорка: при ПЕРЕзаливке существующего файла в облаке остаётся прежняя версия — это правильно,
    мы её не удаляли.

50. **Пункты меню молча глотали отказ.** `commands.storageX(path).then(refresh)` — specta ошибку не
    бросает, она приходит как `{status:'error'}`, и результат никто не смотрел. Отказ выглядел как
    «нажал, и ничего не произошло» — ровно та же неотличимость, что и с исчезающей задачей повтора.
    Теперь ошибка показывается словами, а пункты скрыты, пока передача идёт (звать «скачать» во время
    скачивания было бессмысленно). Заодно переименованы в термины «где файл, а не что делает
    программа»: «Взять на диск» / «Обновить копию на диске» / «Отправить в облако» — «скачать» и
    «закачать» на слух почти одинаковы.

51. **Пауза/возобновление — чего нельзя обещать сегодня.** Для ЗАЛИВКИ докачки нет: один PUT, и
    возобновить его с середины невозможно, пока у бэкенда нет multipart. Кнопка «Пауза», которая
    втихую перезаливает с нуля, врала бы про 3-гигабайтный файл дороже всего. Для СКАЧИВАНИЯ пауза
    реализуема честно: мы уже пишем в `.part`, а presigned GET держит Range (на нём стоят
    метаданные и превью). Значит «пауза» = отменить, `.part` НЕ удалять, при возобновлении дослать
    `Range: bytes=<len>-`. Не сделано; сознательное решение — не выдавать за паузу перезапуск с нуля.

52. **«Остановить» держалось до следующего полного обхода — то есть до 10 минут.** Страховка честно
    видела «файл на диске есть, в облаке нет» и ставила его в очередь снова: программа спорила с
    человеком, который только что нажал стоп. Лечение — `Pending::decline`: остановленный путь
    запоминается вместе с тем, как файл выглядел (size+mtime), и в очередь сам не возвращается.
    Запрет снимают два события, и оба означают «намерение изменилось»: файл на диске стал другим
    (это уже другое содержимое) или прозвучала ЯВНАЯ команда.
    **Тонкость, на которой правка почти сломалась:** сперва запрет снимался в `mark_ready` — а его
    зовёт и полный обход (`full_scan_round` → `mark_dirty(..., ready = true)`), то есть страховка
    продолжала перебивать решение человека. Пришлось развести: `mark_ready` — «файл дописан»,
    `allow` — «человек передумал». Один вызов, но разница смысловая, и тест на неё есть.
    Запрет живёт в памяти и после перезапуска программы исчезает — осознанно: иначе он стал бы
    невидимым чёрным списком, о котором никто не помнит.

53. **Вкладка «Не в облаке».** Прямое следствие предыдущей грабли: остановленная заливка сама
    больше не начнётся, а значок такого файла видно только в его папке — вопрос же «всё ли я
    отправил» стоит про зеркало целиком. Без списка такой файл теряется навсегда.
    Список собирается из ДВУХ источников, и ни один по отдельности не отвечает на вопрос: обход
    зеркала даёт файлы, которых в каталоге нет вовсе, `local_modified_paths` — те, что в каталоге
    есть, но правились здесь. Причина показывается словами («в облаке нет» / «правили здесь» /
    «остановлено вручную»), у остановленных — свой знак: они не поедут сами.

    ним одни, и копия логики разошлась бы на первой правке — как уже разошлось сравнение значков.

    не показывалось **вообще**. Лечение двойное: escape `\0` вместо байта и **единственная** функция
    `dirKey` на всех (ключ, собираемый в двух местах, разъедется снова).
19. **`flex: 1` без `minWidth: 0`.** Flex-элемент не сжимается ниже min-content, а min-content задаёт
    самое длинное имя файла. Колонка распиралась, родитель с `overflow: hidden` срезал размер и значок,
    а многоточие не срабатывало — «места хватает». Нужен и на колонке, и на самой `Typography noWrap`.
20. **Значок с процентами шире голого** (40px против 15) — колонка размеров дёргалась влево на 26px,
    как только файл начинал качаться. Резервируем фиксированную ширину под значок: числа в списке
    обязаны стоять столбиком.
21. **Секция «Онлайн» росла без потолка** и при 25 клиентах забирала 534 из 684 пикселей колонки,
    сжимая локальные папки до полосы. `maxHeight: 50%` — потолок, а не размер.
22. **`Runtime.enable` в CDP переигрывает историю консоли** текущего контекста. Из-за этого прогон
    показал ошибки **предыдущего** прогона, и правки выглядели неработающими. Сбрасывать
    `Runtime.discardConsoleEntries` после каждой навигации — иначе выводы ложные.
23. **Заголовок в заголовке.** `DialogTitle` — это `h2`, а `Typography variant='subtitle2'` внутри —
    `h6`. Невалидный HTML и ошибка React на каждое открытие модалки; лечится `component='div'`.
24. **Tooltip на disabled-кнопке не показывается** (disabled-элемент не отдаёт событий) — нужна
    обёртка `span`. Касается кнопки «демо», которая disabled ровно в момент подключения.

## 14. Что умерло в ревизии

Чтобы никто не предложил заново:

| Умерло | Почему |
|---|---|
| Маркеры `.keep`, slash-маркеры, `role`/`owner` в маркере | папки логические, живут в Postgres; `mkdir` не создаёт объект в R2 |
| `display_name` отдельно от `prefix` | бэкенд уже разводит логический путь и физический ключ |
| `project_id` = nanoid, `user_id` в префиксе | идентичность — UUID бэкенда; в пути юзера нет |
| Схема ключей «вариант А против Б» | раскладку выбирает бэкенд |
| D1, Cloudflare Queue, consumer Worker | это Postgres, и это не моя часть |
| Свой обход `ListObjectsV2`, снимок индекса в R2 | есть `/tree` и `/delta` |
| Ключи R2 в keychain | machine token |
| Версионирование, lifecycle, abort incomplete multipart | настройки бакета — владелец бэкенда |
| Перенос папок как job с прогрессом, `moving`, окно 404, лимит `CopyObject` 5 ГБ | rename = один `UPDATE`, байты не двигаются |
| `last_known_prefix` для починки | `file_id` стабилен |
| Вся модель прав на моей стороне | enforcement на бэкенде; программа зовёт API и показывает 403 |
| Экран «проекты, потерявшие связь» | терять нечего: идентичность в Postgres |
| Веб-прокси `_web/*.mp4` и постеры | мастера и так MP4 → достаточно `-movflags +faststart` при генерации; кадр извлекается на месте по presigned GET за сотни килобайт |

## 15. Решённое (лог)

| Решение | Кратко |
|---|---|
| Ядро на Rust, **не плагин** | шов `ensureLocal` проходит через каждое чтение файла; плагин не перехватит то, что зовут все остальные |
| Облако = один из провайдеров | `PlainFolder` = деградация до сегодняшнего поведения без ветвлений |
| Триггер заливки — **явный вызов** | `notify`-вотчер только страховка для ручного перетаскивания; поэтому нет проблемы недописанного файла |
| **Зон две, а не три** | локальная рабочая папка (`localFolder`) существует давно и управляется другой подсистемой; клиенту хранилища за ней следить не надо. CoW-клон и «TTL scratch» убраны |
| Проверка «устарел ли» — **до** гидрации, по хэшу | иначе качаем 3 ГБ, чтобы выяснить, что качать не надо |
| Кэш = TTL + лимит + **два инварианта** | остальное не настройки |
| Состояние — **один селектор** | иначе агрегаты разъезжаются |
| Multipart заложить, выключить | стратегия + `Caps`, схема `transfers` уже готова |
| `+faststart` вместо прокси-файлов | не плодить файлы; браузер играет мастер, если moov впереди |

## 16. Открытые вопросы

### Ждут URL бэкенда

1. **Round-trip как сверка контракта.** Заодно ответит на два вопроса, которые пока не проверить:
   отдаёт ли `/tree` пустые логические папки, и работают ли Range-запросы по presigned GET (от них
   зависят характеристики и превью облачных файлов без скачивания).
2. **Максимальный размер мастера.** До ~3 ГБ — можно жить без multipart; от 5 ГиБ это блокер.

### Ждут решения (кода не требуют)

3. **`origin_mtime` на бэкенде.** Колонка есть, `/notify` его теперь принимает — но мы единственные,
   кто присылает. Пока не заполняется у файлов, залитых с сайта, время в интерфейсе будет времем
   регистрации, а не создания.
4. **Где в пайплайне ставить `-movflags +faststart`** для MP4: флаг ноды `convert` или дефолт для всех
   выходов. Без него браузер не начнёт играть файл, не скачав его целиком.

### Отложено осознанно

5. **Превью видео-кадра** — механика та же (ffprobe/ffmpeg по Range), решать будем отдельно.
   См. память `project_cloud_media_probe`.
6. **Тумбнейлы для файлового менеджера** — извлекать кадр на лету и кэшировать локально, или хранить
   постеры. Сайту кадр извлечь нечем (у Worker'а нет ffmpeg), но это решается задним числом.
7. **Multipart на нашей стороне** — стратегия и поля в `transfers` заложены, реализация ждёт
   эндпоинтов бэкенда.
