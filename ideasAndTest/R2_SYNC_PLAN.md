<a name="одна-фраза"></a>

## 1. Одна фраза, которую надо держать в голове

> **Бакет — единственный источник правды. Все базы данных — производные от него и восстанавливаются полным обходом.**
>
> Спутать → «БД сказала, что файла нет, значит его нет» и потерянные данные.
> Развести → любую БД можно удалить и пересобрать, ничего не потеряв.

И вторая, про поток файлов:

> **Онлайн — правда и адрес. Зеркало — транспорт. Scratch — рабочий стол.**
> Тяжёлые операции (ffmpeg, AE, Moho, нейронки) не касаются онлайна никогда.

<a name="глоссарий"></a>

## 2. Глоссарий — читать до всего остального

| Термин | Что это |
|---|---|
| **R2** | Cloudflare R2 — объектное хранилище с S3-совместимым API. Не файловая система: папок физически нет, есть плоские ключи вида `projects/client_A/IN/raw.mov` |
| **Ключ (key)** | Полный путь объекта внутри бакета. Играет роль пути к файлу |
| **Префикс (prefix)** | Ключ, обрезанный по `/`. Играет роль папки. «Папка» = запрос «дай ключи с этим префиксом» |
| **Бакет (bucket)** | Контейнер верхнего уровня в R2. У нас один на всё |
| **Маркер папки** | Мелкий объект `.keep` внутри префикса. Нужен, чтобы «папка» существовала, когда файлов в ней нет (папки `IN` обязаны существовать пустыми) |
| **ETag** | Хэш содержимого объекта, который отдаёт R2. **Для multipart-загрузок это НЕ хэш файла** (см. Граблевник) |
| **Presigned URL** | Временная подписанная ссылка на объект. По ней можно скачать/загрузить без ключей доступа. TTL от минут до дней |
| **Multipart upload** | Загрузка большого объекта частями. Возобновляемая: оборвалось на 80% — продолжаем с 80% |
| **Гидрация (hydration)** | Скачивание файла из облака в локальную папку по требованию |
| **Вытеснение (eviction)** | Удаление локальной копии файла, когда он больше не нужен. Онлайн-оригинал остаётся |
| **Зеркало (mirror)** | Локальная папка, которая соответствует структуре облака. Тонкая: в ней лежит только то, что реально понадобилось |
| **Scratch** | Локальная рабочая папка (`description.mainWorkFolder`). С облаком не связана вообще. Здесь идёт вся обработка |
| **Индекс** | Локальная SQLite-база со слепком дерева облака. Нужна, чтобы отвечать на вопросы про **всё дерево сразу**, не дёргая R2 |
| **Журнал изменений (changes / delta)** | Дописываемая таблица «что изменилось в бакете, по порядку». Позволяет спросить «что нового с моего прошлого визита» вместо перекачки всего дерева |
| **Курсор (cursor)** | Номер последней записи журнала, которую машина применила у себя |
| **Оператор** | Машина, на которой человек лазит по хранилищу через файловый менеджер программы. Нужен полный индекс |
| **Воркер** | Машина, которая тянет задачу с сайта и выполняет. По хранилищу не лазит |
| **Класс A / Класс B операции** | Тарификация R2. Класс A ($4.50/млн) — запись, копирование, **листинг**. Класс B ($0.36/млн) — чтение, HEAD |

<a name="почему-r2"></a>

## 3. Почему R2, а не гуглдиск

### Что получаем

| | |
|---|---|
| **Нулевой egress** | Скачивание бесплатно в любом объёме. 2 ТБ хранения ≈ **$30/мес**, операции — копейки. На S3 те же 10 ТБ скачивания стоили бы ~$900 |
| **Range-запросы = ffmpeg по URL** | `ffprobe <presigned-url>` читает только moov-атом (сотни КБ) и отдаёт длительность/кодек, не скачивая 5 ГБ. Превью-кадр можно отрендерить из **облачного** файла напрямую. Это новая возможность, которой с гуглдиском не было |
| **Предсказуемость вместо демона** | Уходит класс болей: gsync, откатывающий mtime каталога (из-за него `projectActivityLS` был вынужден отказаться от mtime папки), «файл есть, но нулевой», «синхронизация встала» |
| **Нет квотных стен** | У Drive API — 12k запросов/мин, лимиты записи на юзера, 750 ГБ/сутки, штормы `userRateLimitExceeded`. У R2 в data-plane таких стен нет |
| **Серверное копирование** | `CopyObject` — переместить/скопировать внутри бакета без трафика через машину |
| **Возобновляемые загрузки** | Multipart: оборвалось — продолжили |
| **Lifecycle + версионирование** | «`_tmp/` удалять через 7 дней», «нетронутое 90 дней — в Infrequent Access за $0.01/ГБ». Версионирование = корзина, которой у R2 иначе нет |
| **События бакета** | R2 event notifications → Cloudflare Queue. Реальный журнал изменений, а не поллинг листингов |
| **Строгая консистентность** | Read-after-write, листинги и удаления видны сразу глобально. Оговорка одна: если включить кэш на своём домене, там уже TTL |

### Что теряем и как закрываем

| Потеря | Чем закрываем |
|---|---|
| **Нет человеческого UI** — клиент не может «открыть папку и закинуть файлы» | UI пишем сами: наша программа + сайт для клиентов. Загрузка с сайта — через presigned PUT. Плюс уже готовый `tgCollect` как канал приёмки |
| **Нет превью и тумбнейлов** | На выходе пайплайна рядом с мастером кладём веб-прокси (см. ниже) |
| **Нет папок** — пустая папка не существует | Маркер `.keep`, программа само-лечит скелет проекта |
| **Объекты неизменяемы** — нет append, нет частичной записи | См. Граблевник, п. 1 |
| **Нет блокировок и атомарного rename** | Примитив захвата = условный PUT `If-None-Match: *`. Разбирается в `DISTRIBUTED_QUEUE_PLAN` |
| **Холодный обход дерева стоит времени и денег** | Индекс (раздел 6) |

### Веб-прокси на выходе — решает и превью, и просмотр онлайн

Браузер играет **только** MP4 / H.264 (или H.265, VP9) + AAC с moov-атомом в начале
(`-movflags +faststart`). Мастера в HAP / ProRes / DNxHD в браузере не заиграют никогда,
настройкой это не лечится.

Поэтому на выходе пайплайна — один лишний проход ffmpeg (нода `convert` уже есть):

```
projects/<client>/OUT/final.mov          ← мастер (HAP/ProRes), для работы
projects/<client>/OUT/_web/final.mp4     ← h264 720p faststart, для сайта и просмотра
projects/<client>/OUT/_web/final.jpg     ← постер-кадр
```

Закрывает сразу три вещи: превью в файловом менеджере, плеер на сайте, «показать клиенту, не
выгружая 5 ГБ». Cloudflare Stream (HLS, адаптивный битрейт) не нужен — платный за минуту
хранения и доставки, прогрессивного mp4 достаточно.

<a name="три-зоны"></a>

## 4. Три зоны и путь файла

**Трёхзонная модель уже есть в коде** — её не надо изобретать, надо переиспользовать:
`description.projectPathGD` (корень проекта в облаке, [`findFilesForSingleFolder.ts:104`](../src/PROCESSING/findFilesForSingleFolder.ts#L104))
и `description.mainWorkFolder = localFolder/mainFolderName/projectName`
([`findFilesForSingleFolder.ts:153`](../src/PROCESSING/findFilesForSingleFolder.ts#L153)).
`projectPathGD` перестаёт быть путём в папке гугл-синхронизатора и становится **префиксом в R2**.
Рекомендуется переименовать в `projectPathRemote`, но менять надо согласованно с `masks.ts`
(маска `$projectPathGD` торчит в UI и в `appSettings.ts`).

| Зона | Что это | Синхронизируется | Кто пишет | Время жизни файла |
|---|---|---|---|---|
| **remote** | R2. Единственный источник правды | — | синхронизатор, сайт | вечно (пока не удалили) |
| **mirror** | Тонкое зеркало структуры облака | ↔ обе стороны | синхронизатор + юзер вручную | по умолчанию 4 ч |
| **scratch** | `mainWorkFolder`. Вся тяжёлая обработка | не синхронизируется вообще | пайплайн (ffmpeg, AE, Moho, нейронки) | по умолчанию 7 дней |

### Путь файла на обработку

```
1. В облаке появился projects/A/IN/raw.mov
     └── событие/обход → индекс знает про него, значок ☁

2. Пайплайн решает, что файл можно обработать
     (options.json из зеркала — он мелкий и всегда горячий)

3. ensureLocal("projects/A/IN/raw.mov")
     └── качаем в зеркало: <mirror>/projects/A/IN/raw.mov   значок ⬇ → ✓
     └── живёт 4 часа

4. Пайплайн копирует вход в scratch
     └── CoW-клон (APFS clonefile / hardlink), НЕ побайтовая копия:
         мгновенно и не занимает места на диске повторно
     └── <scratch>/A/raw.mov   живёт 7 дней

5. Вся тяжёлая работа — только в scratch.
   ffmpeg / AE / Moho / нейронки на сторонних серверах.
   Онлайн-хранилище в этом шаге не участвует НИКАК.

6. Готовый результат кладётся в зеркальную папку OUT
     └── <mirror>/projects/A/OUT/final.mov   значок ↑ (только локально!)

7. Синхронизатор видит: такого ключа онлайн нет → multipart upload
     └── значок ↑ с процентами → ✓

8. Через 4 часа зеркальную копию вытесняем. Онлайн-оригинал остаётся, значок ☁.
   Копия в scratch живёт своей жизнью 7 дней.
```

**Про CoW-клон (шаг 4).** Две копии с разными сроками жизни — это осознанное решение, не
избыточность. Но платить за это диском не надо: на macOS APFS есть `clonefile()` — второй путь
создаётся мгновенно и не занимает места, пока файлы не разошлись. Удалили зеркальную копию через
4 часа — копия в scratch цела. Крейт `reflink` умеет macOS (CoW) и Windows (hardlink) с фолбэком
на обычную копию.
**Требование:** зеркало и scratch должны быть **на одном томе**, иначе клон невозможен. При выборе
папок в настройках это надо проверять и предупреждать.

### Почему нет проблемы «недописанный файл»

В зеркало **никогда не пишет ffmpeg**. Туда попадает только готовый файл, и попадает он нашим же
кодом в известный момент. Поэтому:

- **Триггер заливки — явный вызов** из пайплайна («положил файл в OUT → залей»), а не эвристика
  «размер не менялся N секунд».
- **`notify`-вотчер остаётся только страховкой** для случая «юзер вручную перетащил файл в зеркало
  через файловый менеджер». Для него эвристика стабильности нужна, но это редкий путь.

<a name="провайдеры"></a>

## 5. Провайдеры хранилища и деградация

**Принцип: программа независима от внешних факторов.** Не настроено облако — работаем с локальными
папками, сетевым диском или папкой гугл-синхронизатора. Не настроен сайт — всё задаётся в
настройках руками.

Поэтому облако — это **один из провайдеров**, а не фундамент:

```rust
trait StorageProvider {
    fn list_dir(&self, prefix: &str) -> Result<Vec<Entry>>;
    fn head(&self, key: &str) -> Result<ObjectMeta>;
    fn get_range(&self, key: &str, range: Option<Range<u64>>) -> Result<ByteStream>;
    fn put(&self, key: &str, src: &Path, meta: &Meta, cond: Condition) -> Result<ObjectMeta>;
    fn put_multipart(&self, key: &str, src: &Path, resume: Option<MultipartState>) -> Result<ObjectMeta>;
    fn copy(&self, from: &str, to: &str) -> Result<()>;
    fn delete(&self, key: &str) -> Result<()>;
    fn presign(&self, key: &str, ttl: Duration, method: Method) -> Result<String>;
    fn walk(&self, prefix: &str) -> Result<impl Iterator<Item = ObjectMeta>>;
    fn capabilities(&self) -> Caps;   // умеет ли presign, события, версии
}
```

Две реализации:

| Провайдер | Что это | Поведение |
|---|---|---|
| **`PlainFolder`** | Локальная папка, сетевой диск, **папка гугл-синхронизатора** | Индекса нет, гидрация — no-op, заливки нет, все файлы всегда `Fresh`, значки не рисуются |
| **`R2`** | Объектное хранилище | Полная механика этого документа |

**Ключевой вывод:** сегодняшний гуглдиск — это `PlainFolder`. При ненастроенном облаке программа
ведёт себя **точно как сейчас**, и для этого не нужно ни одной ветки `if (r2Enabled)` в прикладном
коде. Деградация — не костыль, а вырожденный случай той же абстракции.

Расширения на будущее без переписывания UI: MinIO, S3, свой сервер — просто третья реализация трейта.

### Где живут ключи доступа

**В программе, не на сайте.** Хранение — в keychain, **не** в `options.json` (это данные юзера, а не
папки — тот же принцип, что в `SECRETS_VAULT_SITE_PLAN`).

Вариант «сайт выдаёт presigned URL, на машинах ключей нет вообще» — привлекателен операционно
(отзыв доступа одной кнопкой, нет секретов на диске, есть аудит), но он **противоречит требованию
независимости** и поэтому отложен. Вернуться к нему стоит, когда машин станет много: тогда в
настройках воркера останется «адрес сайта + токен машины» вместо «Account ID + бакет + ключ + секрет».
Это Фаза 4, не сейчас.

### Выбор Rust-крейтов

Уже есть в `Cargo.toml`: `reqwest`, `sha2`, `md5`, `notify`, `filetime`. S3-крейтов нет — чистое поле.

Рекомендация: **`rusty-s3` (только подпись SigV4 и presign, без своего транспорта) + существующий
`reqwest`.** Даёт полный контроль над range-GET и multipart и не тащит в сборку половину AWS SDK.
`aws-sdk-s3` тоже работает с R2 (через `endpoint_url`), но это заметный рост времени сборки.

Дополнительно: `rusqlite` (индекс), `reflink` (CoW-клоны).

<a name="базы-данных"></a>

## 6. Базы данных: что где живёт и кто это пишет

Это центральный раздел. Тут три разных хранилища состояния, и путать их нельзя.

### 6.1. Какую задачу решает индекс — и какую НЕ решает

Зашли в файловый менеджер, кликнули в `projects/client_A/`. Чтобы нарисовать список, надо знать
содержимое. Два способа:

**(а) Спросить R2 прямо сейчас:** `ListObjectsV2(prefix="projects/client_A/", delimiter="/")` →
файлы этой папки и имена подпапок. Один запрос, ~60 мс, $0.0000045.

**(б) Иметь локальный слепок дерева** и ответить мгновенно, без запросов.

**Для «показать одну папку» вариант (а) полностью нормален.** 60 мс незаметно, денег ноль.
Индекс нужен не для этого. Он нужен там, где надо ответить на вопрос **про всё дерево сразу**:

- **Модалка поиска по проектам** — читает `options.json` по всем папкам, чтобы собрать облако
  плагинов. Без индекса это сотни LIST + сотни GET на каждое открытие.
- **`findAllFilesForProcess`** — обходит все проекты в поисках работы.
- **Агрегатный значок на папке** («внутри всё локально / частично / всё в облаке») — надо знать
  содержимое, не заходя внутрь.
- Сортировка и фильтрация по всему хранилищу.

> **Правило: одна папка — спрашиваем R2 напрямую. Вопрос про всё дерево — отвечает индекс.**

Приятное следствие: при заходе в папку всё равно делается свежий LIST, поэтому устаревший индекс
**не приводит к тому, что юзер видит неправду**. Индекс отвечает только за агрегаты, его
устаревание не критично.

### 6.2. Три хранилища состояния

```
┌─────────────────────────────────────────────────────────────┐
│  R2 БАКЕТ — ЕДИНСТВЕННЫЙ ИСТОЧНИК ПРАВДЫ                    │
│  содержимое файлов + метаданные объектов                    │
└─────────────────────────────────────────────────────────────┘
        │ производное                    │ производное
        ▼                                ▼
┌───────────────────────────┐   ┌─────────────────────────────┐
│ ЛОКАЛЬНЫЙ SQLite          │   │ БД САЙТА (Фаза 3, опц.)     │
│ (app data, у каждой       │   │ objects + changes-журнал    │
│  машины свой)             │   │ общая для всех              │
│                           │   │                             │
│ remote_objects  ← слепок  │◄──┤ отдаёт дельты по курсору    │
│ remote_dirs     ← слепок  │   │                             │
│ local_state     ← ТОЛЬКО  │   │ НЕ содержит local_state     │
│                   эта     │   │ ни одной машины!            │
│                   машина  │   │                             │
│ transfers       ← ТОЛЬКО  │   └─────────────────────────────┘
│                   эта     │              ▲
│                   машина  │              │ события
│ sync_meta       ← курсор  │   ┌─────────────────────────────┐
└───────────────────────────┘   │ R2 events → Cloudflare Queue│
                                │ → Worker-консьюмер          │
                                └─────────────────────────────┘
```

**Главное разделение, которое нельзя нарушать:**

- `remote_*` — **общая правда**, одинакова у всех машин, производна от бакета.
- `local_state`, `transfers` — **только про эту машину**. Что здесь скачано, когда трогали, что
  запинено. **В облако и на сайт не уходит никогда.** Иначе машины будут перетирать друг другу
  картинку мира.

### 6.3. Локальный SQLite — полная схема

Файл лежит в app data (`~/Library/Application Support/<app>/remote-index.sqlite`),
**не внутри синхронизируемой папки** — иначе он сам себя начнёт синхронизировать.

```sql
PRAGMA journal_mode = WAL;      -- читатели не блокируют писателя
PRAGMA synchronous = NORMAL;

-- ═══════════════════════════════════════════════════════════════
-- ОБЩАЯ ПРАВДА: слепок бакета. Производное, можно снести и пересобрать.
-- ═══════════════════════════════════════════════════════════════

CREATE TABLE remote_objects (
    key           TEXT    PRIMARY KEY,   -- 'projects/client_A/IN/raw.mov'
    parent        TEXT    NOT NULL,      -- 'projects/client_A/IN/'  ← денормализация!
    name          TEXT    NOT NULL,      -- 'raw.mov'
    is_marker     INTEGER NOT NULL DEFAULT 0,  -- 1 = '.keep', в UI не показывать
    size          INTEGER NOT NULL,
    etag          TEXT    NOT NULL,      -- как отдал R2 (для multipart — НЕ хэш файла)
    content_hash  TEXT,                  -- x-amz-meta-sha256, наш честный хэш; NULL если нет
    remote_mtime  INTEGER NOT NULL,      -- unix sec, LastModified из R2
    origin_mtime  INTEGER,               -- x-amz-meta-mtime, исходное время файла
    storage_class TEXT,                  -- 'STANDARD' | 'INFREQUENT_ACCESS'
    seen_seq      INTEGER,               -- курсор журнала, на котором строка обновлена (Фаза 3)
    deleted       INTEGER NOT NULL DEFAULT 0   -- tombstone, чтобы дельты сходились
);
CREATE INDEX idx_ro_parent ON remote_objects(parent, name);
CREATE INDEX idx_ro_name   ON remote_objects(name);        -- поиск по имени по всему дереву
```

**Зачем `parent` денормализован.** Листинг папки = `WHERE parent = ?` — мгновенно по индексу.
Без него пришлось бы делать `key LIKE 'projects/A/%'` и отфильтровывать более глубокие уровни
в коде — на 100k строк это медленно.

```sql
-- Материализованные папки: нужны для агрегатных значков и для того,
-- чтобы папка была видна в UI, даже если внутри только '.keep'.
CREATE TABLE remote_dirs (
    prefix     TEXT    PRIMARY KEY,   -- 'projects/client_A/IN/'  (всегда с '/' на конце)
    parent     TEXT    NOT NULL,      -- 'projects/client_A/'
    name       TEXT    NOT NULL,      -- 'IN'
    n_files    INTEGER NOT NULL DEFAULT 0,   -- прямых детей-файлов (без маркеров)
    n_bytes    INTEGER NOT NULL DEFAULT 0,
    agg_state  TEXT                   -- кэш агрегата: 'cloud'|'mixed'|'local'|'error'|NULL
);
CREATE INDEX idx_rd_parent ON remote_dirs(parent, name);

-- ═══════════════════════════════════════════════════════════════
-- ТОЛЬКО ЭТА МАШИНА. В облако/на сайт не уходит.
-- ═══════════════════════════════════════════════════════════════

CREATE TABLE local_state (
    key          TEXT PRIMARY KEY,
    state        TEXT NOT NULL,     -- Cloud|Downloading|Fresh|Stale|LocalOnly|Uploading|Error
    local_path   TEXT,              -- абсолютный путь в зеркале
    local_size   INTEGER,
    local_mtime  INTEGER,
    local_hash   TEXT,              -- sha256 локальной копии (считаем при заливке)
    synced_etag  TEXT,              -- etag облака, которому соответствует локальная копия
    hydrated_at  INTEGER,           -- когда скачали (для TTL)
    last_access  INTEGER,           -- когда последний раз открывали (для LRU)
    pinned       INTEGER NOT NULL DEFAULT 0,  -- «оставить оффлайн», не вытеснять
    error        TEXT
);
CREATE INDEX idx_ls_state  ON local_state(state);
CREATE INDEX idx_ls_evict  ON local_state(last_access) WHERE pinned = 0 AND state = 'Fresh';

-- Очередь передач. Живёт в БД, а не в памяти, чтобы multipart возобновлялся после
-- перезапуска программы и падения.
CREATE TABLE transfers (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    key          TEXT    NOT NULL,
    direction    TEXT    NOT NULL,   -- 'up' | 'down'
    bytes_total  INTEGER,
    bytes_done   INTEGER NOT NULL DEFAULT 0,
    upload_id    TEXT,               -- R2 UploadId — без него докачка невозможна
    parts_done   TEXT,               -- JSON: [[partNumber, etag], ...]
    attempts     INTEGER NOT NULL DEFAULT 0,
    state        TEXT    NOT NULL,   -- 'queued'|'active'|'paused'|'error'|'done'
    error        TEXT,
    updated_at   INTEGER NOT NULL
);
CREATE INDEX idx_tr_state ON transfers(state, id);

-- Служебное: курсоры, конфиг привязки, версия схемы.
CREATE TABLE sync_meta (
    k TEXT PRIMARY KEY,
    v TEXT
);
-- schema_version   = '1'
-- provider         = 'r2'
-- bucket           = 'my-bucket'
-- root_prefix      = 'projects/'
-- delta_cursor     = '1043'            (Фаза 3)
-- last_full_walk   = '1754400000'
-- walked_prefixes  = '["projects/client_A/", ...]'   (для экономного режима)
```

### 6.4. Три способа наполнять индекс — и почему «таблица» лучше «файла»

**Способ 1. Полный обход. Работает без всякой инфраструктуры.**

Программа сама делает LIST по бакету, по 1000 ключей за запрос, и пишет в SQLite.

| Объектов | LIST-запросов | Время | Стоимость |
|---|---|---|---|
| 20 000 | 20 | ~1.5 с | $0.00009 |
| 100 000 | 100 | ~6 с (параллелится по префиксам) | $0.00045 |

Никакого сайта, никакой очереди. **При текущих объёмах этого одного хватит надолго** — обход по
кнопке «обновить» и по расписанию раз в N минут.

**Способ 2. Снимок-файл в R2.** Кто-то периодически кладёт всё дерево одним объектом
`_index/tree.sqlite.gz`. Остальные скачивают **одним GET** вместо сотни LIST.

Ограничение врождённое: **файл можно только перечитать целиком.** Чтобы узнать «что изменилось за
5 минут», качаем весь снимок и сравниваем локально. Изменилось 3 файла из 100 000 — перекачали
100 000 записей. И спросить у файла «дай только `projects/client_A/`» невозможно — файл не отвечает
на вопросы, он умеет только быть скачанным.

**Способ 3. Таблица + журнал изменений (БД сайта).** Те же данные в настоящей БД **плюс
дописываемый журнал**. Машина помнит «я на seq 1040», спрашивает `GET /delta?since=1040` →
получает **три строки** → применяет → теперь на 1043.

| | Снимок-файл | Таблица + журнал |
|---|---|---|
| «дай всё дерево» | ✓ один GET | ✓ |
| «что изменилось с прошлого раза» | перекачать всё и сравнить | 3 строки |
| «только эта подпапка» | невозможно | ✓ |
| история изменений | нет | есть |
| нужна инфраструктура | нет | Worker + Queue + БД |

**Три способа — не альтернативы, а фазы.** Схема локального SQLite одна и та же во всех трёх,
меняется только источник наполнения. Весь UI, гидрация и кэш над ней не шевелятся.

### 6.5. БД сайта — схема (Фаза 3)

Postgres или Cloudflare D1. Одна общая на всё хозяйство.

```sql
-- Текущее состояние дерева. Производное от бакета.
CREATE TABLE objects (
    key           TEXT PRIMARY KEY,
    parent        TEXT NOT NULL,
    name          TEXT NOT NULL,
    size          BIGINT NOT NULL,
    etag          TEXT NOT NULL,
    content_hash  TEXT,
    remote_mtime  TIMESTAMPTZ NOT NULL,
    origin_mtime  TIMESTAMPTZ,
    deleted_at    TIMESTAMPTZ,          -- NULL = живой; tombstone нужен для дельт
    last_seq      BIGINT NOT NULL       -- последний seq журнала, изменивший строку
);
CREATE INDEX ON objects (parent, name);
CREATE INDEX ON objects (last_seq);

-- Дописываемый журнал. Никогда не UPDATE, только INSERT.
CREATE TABLE changes (
    seq         BIGSERIAL PRIMARY KEY,  -- монотонный курсор
    key         TEXT NOT NULL,
    op          TEXT NOT NULL,          -- 'put' | 'delete'
    size        BIGINT,
    etag        TEXT,
    event_time  TIMESTAMPTZ NOT NULL,   -- время события в R2, НЕ время вставки
    event_id    TEXT UNIQUE             -- id сообщения очереди → дедуп at-least-once
);
CREATE INDEX ON changes (seq);
CREATE INDEX ON changes (key, seq DESC);

-- Что чистить: журнал растёт вечно. Обрезать записи старше N дней,
-- но тогда клиент с курсором старше отсечки должен делать полный обход.
```

**Эндпоинты, которые сайт отдаёт машинам:**

| Метод | Что делает |
|---|---|
| `GET /tree?prefix=…` | Полное содержимое поддерева (bootstrap) |
| `GET /delta?since=<seq>&prefix=…` | Изменения после курсора. Отдаёт `{ changes: [...], cursor: <новый seq>, truncated: bool }` |
| `GET /snapshot` | Ссылка на `_index/tree.sqlite.gz` для холодного старта |
| `POST /reindex` | Запустить полную сверку с бакетом |

### 6.6. Кто что пишет — таблица владения

Это ответ на вопрос «кто обновляет базу».

| Данные | Источник правды | **Кто пишет** | Кто читает |
|---|---|---|---|
| Содержимое файлов | R2 бакет | программа (PUT/multipart), сайт (PUT) | все |
| `remote_objects`, `remote_dirs` (локально) | производное от бакета | **синхронизатор** этой машины: полный обход, LIST при заходе в папку, применение дельт | UI файлового менеджера, пайплайн |
| `local_state` | локальная ФС + синхронизатор | **только эта машина** | только эта машина |
| `transfers` | синхронизатор | **только эта машина** | UI (прогресс-бары) |
| `sync_meta` | синхронизатор | **только эта машина** | только эта машина |
| `objects` (сайт) | производное от бакета | **Worker-консьюмер очереди** + ночная сверка | сайт-UI, все машины |
| `changes` (сайт) | производное от событий R2 | **только Worker-консьюмер**, только INSERT | все машины |
| Пины локальные | эта машина | юзер через контекстное меню | эта машина |
| Пины глобальные | `options.json` проекта / БД сайта | юзер через сайт | все машины |

**Сайт тут не умный.** Он бухгалтер: принял событие → вставил строку в журнал → обновил строку в
`objects`. Никакой логики принятия решений в нём нет.

### 6.7. Применение событий: три вещи, без которых развалится

**(1) Очередь даёт at-least-once и не гарантирует порядок.** Одно событие может прийти дважды,
«создан» может опередить «удалён».

- Дедуп: `INSERT INTO changes … ON CONFLICT (event_id) DO NOTHING`.
- Порядок: строку в `objects` обновлять **только если событие свежее того, что уже записано**:

```sql
INSERT INTO objects (key, parent, name, size, etag, remote_mtime, last_seq)
VALUES (…)
ON CONFLICT (key) DO UPDATE SET
    size = EXCLUDED.size,
    etag = EXCLUDED.etag,
    remote_mtime = EXCLUDED.remote_mtime,
    deleted_at = NULL,
    last_seq = EXCLUDED.last_seq
WHERE EXCLUDED.remote_mtime >= objects.remote_mtime;   -- ← защита от перестановки
```

**(2) События теряются.** Нужна периодическая полная сверка: раз в сутки полный LIST бакета,
сравнение с `objects`, на расхождения — синтетические записи в `changes`. Отдельно проверить при
настройке: **удаления по lifecycle-правилам, по опыту S3, событий могут не присылать вовсе** —
ночная сверка закрывает и это.

**(3) Курсор и префиксы — скрытая ловушка.** Если клиент запросил дельту только по префиксу
`projects/A/` и продвинул курсор до глобального максимума, он **пропустит** изменения в
`projects/B/` — и не узнает об этом, когда позже туда зайдёт.
Варианты решения: (а) хранить **курсор на каждый подписанный префикс** отдельно, (б) при добавлении
нового префикса в подписку делать по нему полный обход. Рекомендуется (б) — проще и надёжнее.

### 6.8. Режим машины: один переключатель на два положения

| Режим | Дерево в индексе | Дельты | Кто так работает |
|---|---|---|---|
| **Оператор** | полное | да | машина разработчика: лазит по всему хранилищу через файловый менеджер |
| **Оператор экономный** | только посещённые префиксы | по посещённым | сервер: заходит редко; **воркер** — чтобы создать локальную структуру по пути к нужному файлу |

**Воркер = экономный оператор.** Отдельного третьего режима нет. Задача, которую воркер тянет с
сайта, несёт в себе всё нужное (пути от корня, маски, опции — см. `DISTRIBUTED_QUEUE_PLAN`,
Сдвиг №2), поэтому дополнительно ходить за `options.json` ему не надо. Но структуру папок он
создаёт лениво, по пути к файлу — как экономный оператор.

## 7. Состояния файла и значки

```
                   ┌──────────────────────────────────────┐
                   │             Cloud (☁)                │
                   │        только в облаке               │
                   └──────────────────────────────────────┘
                          │ ensureLocal()          ▲
                          ▼                        │ вытеснение (TTL / LRU)
                   ┌──────────────┐  ошибка   ┌────┴──────┐
                   │ Downloading  │──────────►│  Error ⚠  │
                   │    (⬇ %)     │           └───────────┘
                   └──────┬───────┘                ▲
                          │ ok                     │ ошибка
                          ▼                        │
                   ┌──────────────┐          ┌─────┴────────┐
             ┌────►│   Fresh (✓)  │─────────►│ Uploading ↑% │
             │     │ локально =   │ локально └──────┬───────┘
             │     │ облако       │ изменилось      │ ok
             │     └──────┬───────┘  или новый файл │
             │            │ событие: etag в         │
             │            │ облаке изменился        │
             │            ▼                         │
             │     ┌──────────────┐                 │
             └─────┤  Stale (⟳)   │                 │
   ensureLocal()   │ локальная    │                 │
                   │ копия старая │                 │
                   └──────────────┘                 │
                                                    │
    LocalOnly (↑) — файла в облаке нет вообще ───────┘
    (только что отрендерили) → автозаливка стартует сама
```

### Значки в UI

| Значок | Состояние | Смысл |
|---|---|---|
| ☁ контур | `Cloud` | Только онлайн, локальной копии нет |
| ⬇ + % | `Downloading` | Скачивается, с прогрессом |
| ✓ зелёный | `Fresh` | Локальная копия есть и совпадает с облаком |
| ↑ + % | `LocalOnly` / `Uploading` | **Есть только локально / заливается.** Самый важный значок |
| ⟳ | `Stale` | Локальная копия устарела, в облаке новее |
| ⚠ | `Error` | Заливка или скачивание упали |
| 📌 **наложением** | модификатор `pinned` | «Оставить оффлайн», не вытесняется |

**Пин рисуется поверх основного значка, а не вместо** — иначе не влезет в один слот.

**Почему `↑` обязателен, хотя автозаливка стартует сама.** 5-гиговый аплоад идёт минутами. В это
окно файл существует **в одной копии на одном диске**. А если заливка упала (сеть, токен), без
значка файл молча останется локальным навсегда. Именно на это состояние опирается жёсткое правило
«незалитое не вытеснять».

**Не оставляем «или ничего».** Значок есть всегда: отсутствие значка юзер читает как «не знаю» —
это худшее из состояний.

**Агрегат на папке:** всё локально / смешанно / всё в облаке / есть ошибка / идёт передача.
Считается из `remote_dirs.agg_state`, пересчитывается при изменении детей.

<a name="гидрация"></a>

## 8. Гидрация, заливка, кэш

### 8.1. Files-On-Demand на уровне приложения

Целевое поведение: **программа пытается открыть файл → открытие тормозится → файл скачивается →
появляется локальный путь → открытие продолжается.** Приложение не знает, что файла не было.

Это делается **на уровне приложения**, без системных расширений: `ensureLocal(key)` блокируется,
качает, возвращает локальный путь.

Разница с OS-уровнем (macOS File Provider / Windows Cloud Files API) одна: там блокировка
происходит в ядре и работает для **любой** программы, даже той, что про синхронизатор не знает.

Единственный случай, где app-уровень не срабатывает: **проектный файл со внутренними ссылками**
(открыли `.aep`, внутри 50 путей на футаж — AE полезет за ними сам, наш код этих открытий не
увидит). У нас этот случай **закрыт по конструкции**: футаж едет в scratch, AE видит только
локальные пути и в зеркало не смотрит никогда.

> **Правило: никогда не отдавать AE / Moho / внешним программам зеркальные пути. Только scratch.**

### 8.2. Два режима получения файла

| Вызов | Куда | Учёт в кэше | Когда |
|---|---|---|---|
| `ensureLocal(key) -> PathBuf` | в зеркало, по зеркальному пути | да, TTL 4 ч | юзер открыл файл руками в файловом менеджере; пайплайн взял вход |
| `fetchTo(key, dest)` | стримом в произвольный путь | нет | когда файл нужен разово и зеркальная копия не нужна |

Обязателен **single-flight по ключу**: две ноды попросили один файл — качаем один раз, второй
ждёт на том же future.

### 8.3. Заливка

- **Триггер — явный вызов** из пайплайна. `notify`-вотчер — только страховка для ручного
  перетаскивания.
- Порог multipart по умолчанию 64–128 МБ; параллельно 4 части.
- Возобновление: `upload_id` + `parts_done` персистятся в `transfers`.
- Условная запись `If-Match: <etag>` при перезаписи существующего объекта; ответ 412 = кто-то
  опередил.
- После подтверждённой заливки: `local_state.state = 'Fresh'`, `synced_etag` = новый etag.
  **До подтверждения вытеснять нельзя.**
- Метаданные при PUT: `x-amz-meta-mtime` (исходное время файла), `x-amz-meta-sha256` (наш хэш).

### 8.4. Кэш и вытеснение

Механика простая и ровно такая, как ожидается: пробежаться по `local_state` и удалить старое.

```sql
SELECT key, local_path FROM local_state
WHERE state = 'Fresh'
  AND pinned = 0
  AND last_access < :now - :ttl_seconds;
```

Основной критерий — **TTL** (по умолчанию 4 ч для зеркала). Дополнительно — **аварийный клапан по
размеру**: если зеркало превысило N ГБ, вытеснять самое давно нетронутое, не дожидаясь TTL. Это не
политика, а защита от забитого диска, когда кто-то открыл руками сорок мастеров.

**Два жёстких правила — не настройки, а инварианты:**

1. **Никогда не вытеснять файл, который ещё не залит в облако** (`LocalOnly`, `Uploading`, `Error`
   с непрошедшей заливкой). Иначе результат рендера исчезнет вместе с локальной копией.
2. **Никогда не вытеснять сайдкары и запинованное.** `options.json`, `_description`,
   `folderState.json` читаются поиском по всем проектам и облаком плагинов — гонять их через
   гидрацию каждый раз нельзя.

**Класс «всегда горячих» файлов** — отдельная настройка-маска, по умолчанию:
`options.json`, `_description*`, `folderState.json`, `*.json` в корне проекта.

**Пины — два разных смысла, путать нельзя:**

| | Где хранится | Смысл |
|---|---|---|
| **Локальный пин** | `local_state.pinned` этой машины | «на *этой* машине держи всегда». Контекстное меню «Оставить оффлайн» — аналог гугловского «Доступно офлайн» |
| **Глобальная политика** | `options.json` проекта / БД сайта | «держать локально на *всех* машинах». Нужно для класса сайдкаров |

В UI по умолчанию — только локальный пин. Глобальный — настройка проекта. Иначе юзер запинует папку
у себя и незаметно заставит десять серверов держать терабайт.

### 8.5. Проверка свежести при открытии

- **Явное открытие файла руками** → всегда `HEAD` перед открытием. Стоит $0.00000036 и ~50 мс,
  гарантия абсолютная.
- **Массовый прогон пайплайна** → доверяем индексу/дельтам. Иначе 10 000 HEAD-ов на витке.

### 8.6. Поверхность IPC (specta-команды)

```
remote_configure(cfg)              remote_test_connection() -> Caps
remote_list_dir(prefix)            -> [Entry { name, is_dir, size, state, pinned }]
remote_ensure_local(key)           -> String   (блокирующая гидрация, путь в зеркале)
remote_fetch_to(key, dest)         -> String
remote_put(local_path, key)        -> ObjectMeta
remote_delete(key)                 remote_copy(from, to)
remote_presign(key, ttl_sec, method) -> String
remote_pin(key, on)                remote_evict(key)  remote_clean_cache()
remote_walk(prefix)                -> WalkStats      (обновить индекс)
```

<a name="граблевник"></a>

## 10. Граблевник R2

**1. Объекты неизменяемы: нет append, нет частичной записи.** Любое изменение = полный PUT целиком.

> **`appendRecord` из `+STATS_SCHEMA_PLAN` (честный `O_APPEND`) в R2 не работает в принципе.**
> Но схема статистики («атомарные факты + агрегаты на чтении») ложится идеально: один факт = один
> мелкий объект `stats/2026/08/05/<uuid>.json`, агрегируем при чтении. Локальный JSONL можно
> оставить как буфер и сворачивать в объекты пачками.

**2. «1 запись в секунду на один и тот же объект» + last-writer-wins.** Это про горячие сайдкары
(`folderState.json`, `postSources.json`). Две машины пишут → тихо потеряем запись. Лечится условным
PUT (`If-Match` → 412 → перечитал-слил-повторил) либо переносом горячего состояния в БД
(`DISTRIBUTED_QUEUE_PLAN`: «горячая БД / холодная папка»).

**3. ETag ≠ хэш содержимого для multipart-загрузок.** Для одиночного PUT ETag = MD5, для
multipart — составное значение с суффиксом `-N`. **Нельзя строить «какая версия свежее» только на
ETag.** Поэтому в схеме есть `content_hash` (`x-amz-meta-sha256`).

**4. mtime не сохраняется.** Время объекта = время загрузки. Исходное — в `x-amz-meta-mtime`.
Пользовательских метаданных влезает **8 КБ**, длина ключа — до **1024 байт** (для UTF-8 с
кириллицей считаются байты, не символы).

**5. Пустых папок не существует.** Папка живёт, только пока есть хоть один ключ с этим префиксом.
Удалили последний файл из `IN` — папка исчезла.

- Маркер `.keep` ставится **при создании папки**, а не когда вспомнили.
- Внутрь маркера кладём мелкий JSON (кто создал, когда, `"role": "IN"`) — стоит те же деньги.
- Синхронизатор **фильтрует маркеры из UI** (`is_marker = 1`), юзер их не видит.
- Программа знает канонический скелет проекта → при открытии проекта **само-лечится**: нет
  маркера у обязательной папки — создать.

**6. Переименование папки = N × (copy + delete).** Атомарного rename нет. На больших папках это
долгая операция с прогрессом, а не мгновенная.

**7. Лимиты размеров.** Объект до 5 ТиБ. Одиночный PUT — до ~5 ГиБ, дальше **обязательно**
multipart. Части: минимум 5 МиБ (кроме последней), **все части кроме последней одного размера**,
максимум 10 000 частей.

**8. Листинг — это Класс A (платный) и по 1000 ключей за запрос.** 100k объектов = 100 запросов.
Не обходить дерево в цикле UI.

**9. Лимит «1200 запросов / 5 минут» относится к управляющему Cloudflare REST API** (создание
бакетов и т.п.), **не** к S3-операциям с объектами. Не путать и не пугаться.

**10. Кэш на своём домене ломает консистентность.** Удалённые объекты остаются в кэше, 404
кэшируются. По S3 API и Worker-биндингам кэш не участвует. Если включаем свой домен для
веб-прокси — держать в голове.

**11. Очередь: at-least-once, без гарантии порядка.** См. 6.7.

**12. Удаления по lifecycle-правилам могут не присылать события.** Проверить на своём бакете;
ночная сверка закрывает.

<a name="фазы"></a>

## 11. Фазы реализации

Каждая следующая фаза **необязательна и аддитивна**. Схема локального SQLite не меняется —
меняется только источник наполнения. UI, гидрация и кэш не переписываются.

### Фаза 0 — PoC провайдера (без UI)

`StorageProvider` + реализация `R2` на `rusty-s3` + `reqwest`. Проверить руками:
list / head / get_range / put / multipart с возобновлением / copy / delete / presign.
Отдельно проверить: `ffprobe` по presigned URL, воспроизведение mp4 в браузере,
условный PUT `If-None-Match: *`, события бакета доходят до очереди.

### Фаза 1 — рабочий синхронизатор без сайта ← **основной объём**

- Локальный SQLite по схеме 6.3.
- Наполнение **полным обходом** (способ 1) + свежий LIST при заходе в папку.
- `ensureLocal` / `fetchTo`, single-flight, очередь `transfers` с возобновлением.
- Заливка по явному вызову + `notify`-страховка.
- CoW-клон зеркало → scratch.
- Вытеснение по TTL + аварийный лимит + два инварианта.
- Значки, прогресс передач, контекстное меню.
- Настройки, keychain, счётчики операций.
- `PlainFolder`-провайдер (деградация до текущего поведения).

**После Фазы 1 можно полноценно работать. Сайт не нужен.**

### Фаза 2 — снимок в R2

`_index/tree.sqlite.gz`, холодный старт новой машины одним GET. Делать, когда полный обход станет
заметно долгим или машин станет много.

### Фаза 3 — сайт: очередь, журнал, дельты

R2 events → Queue → Worker-консьюмер → БД сайта (схема 6.5). Эндпоинты `/tree`, `/delta`,
`/snapshot`, `/reindex`. Ночная сверка. Машины переключаются на дельты, полный обход остаётся
как фолбэк и как кнопка.

### Фаза 4 — опционально, когда машин много

Сайт выдаёт presigned URL, на воркерах ключей R2 нет. В настройках воркера остаётся «адрес сайта +
токен машины». Отзыв доступа — одна кнопка. Глобальные пины.

### Миграция с гуглдиска

Объёмы пока небольшие → **вручную**: скачал из гуглдиска в зеркало, синхронизатор залил в R2.
**Версионирование бакета включить до начала.**

Если объём вырастет до терабайтов — `rclone` (обычная консольная утилита копирования, не демон и не
монтирование) умеет копировать **напрямую `gdrive:` → `r2:`**, не сохраняя файлы на локальный диск,
со сверкой контрольных сумм и продолжением после обрыва. Одна команда.

<a name="не-делаем"></a>

## 12. Что решили НЕ делать и почему

| Вариант | Почему нет |
|---|---|
| **Синхронизатор плагином** | Шов `ensureLocal` проходит через каждое чтение файла: файловый менеджер, `findAllFilesForProcess`, все ноды, все плагины, вызовы ffmpeg, `aeProcess`. Плагин не может перехватить то, что вызывают все остальные, включая плагины. Плюс нужны вещи, которых у плагинов нет: стриминговый multipart, keychain, фоновый демон, SQLite, range-GET. И класс отказа другой: нет плагина автопостинга — нет одной ноды; нет бэкенда хранилища — не работает ничего. **Ядро, Rust.** «Ощущение плагина» даёт гейт UI по «настроено ли хранилище» — тот же приём, что `useHasAnyPlugin` / `usePostingAvailable` |
| **Отдельная нода «залить в облако»** | Не нужна: пайплайн просто пишет в зеркальную папку, синхронизатор видит и заливает |
| **OS-уровневый Files-On-Demand** (macOS File Provider / Windows cfapi) | Отдельное подписанное расширение приложения на Swift, энтайтлменты Apple, большой объём. Нужно только для того, чтобы **чужие** программы открывали зеркальные пути напрямую. У нас этого случая нет: всё едет в scratch. Вернуться, если понадобится обзор хранилища прямо в Finder |
| **Индекс только как файл в R2** | Файл можно перечитать только целиком, нельзя спросить «что изменилось» и «только эта подпапка». Понижен до bootstrap + бэкап (Фаза 2) |
| **Гидрация пайплайна напрямую в scratch, минуя зеркало** | Обсуждалось, отклонено: ломает существующую систему обработки и убивает разные сроки жизни (4 ч зеркало / 7 дней scratch). Экономия диска достигается CoW-клоном без изменения модели |
| **Сайт как обязательное звено** | БД сайта — производные данные, бакет — источник правды. Сайт лёг → грузим в R2 напрямую → сайт поднялся и досчитал. Нужны только операции «пересчитать всё» и «досчитать за период» |
| **iroh как замена хранилища** | Разобрано ранее: iroh — транспорт, а не хранилище. Прямая замена гуглдиску — S3-совместимое хранилище |
| **Cloudflare Stream для видео** | Платный за минуту хранения и доставки. Прогрессивного mp4 + faststart достаточно |
| **`rclone` как постоянный мост** | Только как разовый инструмент миграции при больших объёмах |
| **Ключи R2 на сайте (Фаза 4) прямо сейчас** | Противоречит требованию независимости программы от внешних факторов. Вернуться, когда машин станет много |

<a name="открытые-вопросы"></a>

## 13. Открытые вопросы

1. **Как клиенты кладут файлы?** Страница загрузки на сайте (presigned PUT), существующий
   `tgCollect`, или оба? Это процессный вопрос, решать **до** миграции.
2. **Где в пайплайне генерируется веб-прокси** (`_web/*.mp4` + постер)? Отдельная нода, флаг на
   выходной ноде, или пост-шаг раннера?
3. **Тумбнейлы для файлового менеджера** — генерировать при заливке в `_thumbs/` или дёргать
   ffmpeg по presigned URL на лету и кэшировать локально?
4. **Переименовать `projectPathGD` → `projectPathRemote`?** Маска `$projectPathGD` торчит в UI,
   в `masks.ts` и в `appSettings.ts` — миграция согласованная, нужен план совместимости со
   старыми `options.json`.
5. **Ретеншен версий** — 30 дней хватит? Влияет на счёт: удалённые версии тарифицируются до
   истечения lifecycle-правила.
6. **Обрезка журнала `changes`** на сайте — через сколько дней, и что делает клиент с курсором
   старше отсечки (предположительно полный обход).
7. **UI: разделение первой колонки** на «локальные / онлайн» — обсуждается отдельно.
   Альтернатива, которую стоит рассмотреть: единый список со значками состояния + переключатель
   вида вместо жёсткого разделения.
