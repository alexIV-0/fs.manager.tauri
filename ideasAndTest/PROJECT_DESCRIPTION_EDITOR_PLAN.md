| место | что делает |

`fileId`. Не искать их в интерфейсе, это норма.

## 1. Формат: markdown с островками HTML

Имя файла задано контрактом с двух сторон (`Sidecar::Description` у нас,
`projectDescriptionKey` у сайта). `description.html` = правка Rust + правка контракта +
согласование, и всё это не нужно: **markdown по спецификации разрешает HTML внутри себя.**

Решение: **md как основа, теги — только там, где md не выражает нужного.**

| нужно | пишем | почему так |
|---|---|---|
| жирный, курсив, зачёркнутый | `**b**`, `*i*`, `~~s~~` | родное, отрисует любой просмотрщик |
| заголовки, списки, чеклисты, цитаты, код, линия, ссылки | родной md / gfm | то же |
| таблицы | gfm-таблица | то же |
| подчёркнутый | `<u>текст</u>` | в md подчёркивания нет вообще |
| цвет | `<span class="fg-blue">текст</span>` | в md цвета нет вообще |
| выделение маркером | `<mark>текст</mark>` | в md нет |
| выравнивание | `<div class="align-center">` | в md выравнивания нет |
| красная строка | `<p class="indent">` | в md отступа нет |
| спойлер | `<details><summary>` | форумный сворачиваемый блок |
| картинки | `![](data:image/webp;base64,…)` | см. §3 |
| блок-схемы | ` ```mermaid ` фенс | рисует просмотрщик, не мы |

**Цвет — классом, не `style`.** На сайте стоит `next-themes` (светлая и тёмная тема), а наши
цвета взяты из тёмной палитры программы: `#f9e2af` на белой странице — невидимый жёлтый.
Класс `fg-yellow` сайт мапит в свой токен для каждой темы, hex прибит навсегда. Плюс
содержимое атрибута `style` нельзя надёжно отфильтровать санитайзером (это разбор CSS), а
список допустимых значений `class` проверяется точно. Палитра и схема санитайза —
[`DESCRIPTION_FORMAT_CONTRACT.md`](./DESCRIPTION_FORMAT_CONTRACT.md).

**Почему не чистый HTML в этом файле.** Если сайт рендерит описание санитайзером с выключенным
raw-html, HTML-блоб превращается в кашу из тегов целиком. md с островками деградирует мягко:
теряются цвет и выравнивание, а текст, заголовки, таблицы, списки и картинки остаются. Цена
решения — ноль, редактор всё равно генерирует оба вида разметки.

### Грабля markdown, на которой легко сесть

Блочный HTML **съедает** markdown внутри себя. Вот так жирный НЕ сработает:

```html
<div class="align-center">**жирный по центру**</div>
```

А так сработает — пустые строки возвращают парсер в режим markdown:

```html
<div class="align-center">

**жирный по центру**

</div>
```

Тулбар обязан вставлять блочные обёртки **с пустыми строками**. К строчным тегам
(`<span>`, `<u>`) это не относится: внутри них md разбирается нормально.

## 2. Редактор: два режима, одна панель

По умолчанию правка идёт **в отрисованном виде** (WYSIWYG), а режим «текст markdown + превью»
остаётся вторым — посмотреть, что реально уедет в файл.

### Почему не contentEditable поверх превью

Потому что источник истины — markdown, и «редактировать в нормальном виде» означает
**сериализовать документ обратно** в наш закрытый набор тегов. Браузер на каждый Enter, вставку и
Backspace добавляет свои `div`, `br`, `span style` — обратное превращение такого HTML в markdown
теряет структуру. Именно поэтому нормальные WYSIWYG для markdown стоят на модели документа
(ProseMirror), а не на contentEditable.

### Выбран Tiptap 3 (2026-08-19)

| вариант | почему не он |
|---|---|
| **Milkdown Crepe** | markdown = модель документа, точность round-trip выше, но `@milkdown/components` тянет `vue ^3.5.20` прямой зависимостью, плюс CodeMirror 6 (второй редактор кода рядом с Monaco) и KaTeX: ~45–50 пакетов и два UI-фреймворка в бандле |
| **`@uiw/react-md-editor`** | не WYSIWYG, и приносит свой рендерер превью — третью реализацию показа md в проекте |
| **Monaco** (уже стоит) | ощущение «редактор кода»: описание пишут люди и для людей |

**Tiptap 3** — ProseMirror, React-first, без Vue (~20 пакетов). Наши классы `fg-*`/`bg-*`,
выравнивание и красная строка ложатся на марки и атрибуты узлов, тулбар остаётся наш (MUI).

### Как устроен round-trip

Асимметрично, и это осознанно:

- **в редактор — через HTML.** `markdownToHtml.ts` гоняет тот же конвейер, что просмотрщик
  (gfm → raw → sanitize), а правила `parseHTML` расширений разбирают результат. Свой разбор
  mdast был бы заметно хуже: строчный HTML в markdown приходит **непарным** — `<span
  class="fg-blue">`, текст и `</span>` это три отдельных узла, и собирать из них марки пришлось
  бы автоматом со стеком. `rehype-raw` уже делает ровно это.
- **из редактора — своим сериализатором.** `markdownSerialize.ts` (документ → markdown) —
  единственное место, которое пишет в файл, и потому единственное, которое обязано соблюдать
  контракт: закрытый набор тегов, никаких `style`/размеров, пустые строки вокруг блочных
  обёрток. Проверен 21 утверждением на рукописных документах.

Расширения под формат — `tiptapExtensions.ts`:

- `TextColor` — **один** mark с двумя атрибутами (`fg`, `bg`) → один `<span class="fg-… bg-…">`.
  Два отдельных марка вкладывали бы span в span при каждом втором нажатии;
- `BlockAttrs` — выравнивание и красная строка как атрибуты абзаца/заголовка. В файле
  выравнивание это блочный `<div class="align-*">`, поэтому при чтении `prepareHtml` переносит
  класс с обёртки на детей и разворачивает её (иначе ProseMirror выбросил бы обёртку вместе с
  выравниванием), а сериализатор оборачивает обратно;
- `Details` / `DetailsSummary` — спойлер;
- `DescTableHeader` / `DescTableCell` — атрибут `align` на `th`/`td`: так GFM-выравнивание
  колонок доживает до пересохранения;
- `DescTaskList` / `DescTaskItem` — распознавание чеклиста в разметке `remark-gfm`
  (`ul.contains-task-list`), а не только своего `data-type="taskList"`.

Панель кнопок одна на оба режима и не знает, какой активен: она дёргает `EditorApi`
(`editorApi.ts`), реализаций две — текстовая (поверх чистых функций `markdownCommands`) и
`tiptapApi.ts`. Отличия в поведении, о которых стоит помнить: в WYSIWYG «отступ ±» это
вложенность пункта списка (`sinkListItem`/`liftListItem`), а не два пробела, и отмена/возврат
берутся из истории ProseMirror, а не из нашей.

Новые пакеты: `@tiptap/react`, `@tiptap/pm`, `@tiptap/starter-kit` (в v3 включает link, underline
и undo/redo), `@tiptap/extension-table`, `@tiptap/extension-list`, `@tiptap/extension-highlight`,
`@tiptap/extension-image`, `hast-util-to-html`; из unified-семейства (оно уже приехало с
`react-markdown`) — `remark-gfm`, `rehype-raw`, `rehype-sanitize`, плюс явные `unified`,
`remark-parse`, `remark-rehype`.

базового кегля — меняется база, за ней тянется вся типографика. В текстовом режиме поле ввода
берёт на 2 px меньше: моноширинный шрифт при равном кегле выглядит крупнее пропорционального.

### Чего в тулбаре не будет и почему

- **Размер и семейство шрифта** (в двух из трёх присланных форм они есть). Формат их не
  выражает, а главное — это и есть те самые жёсткие размеры, от которых вёрстка разваливается на
  узком экране. Их работу делает «стиль абзаца»: заголовок на сайте получит свою адаптивную
  типографику, а `font-size: 18px` — нет.
- **Пипетка произвольного цвета** — только палитра имён (контракт §3).
- **Вставка видео/фреймов** — вне разрешённого списка тегов, это дыра в безопасности при том, что
  файл приходит по сети.

### Перетаскивание файла — отложено осознанно

HTML5-drop в Tauri не даёт путей (это было только в Electron), а нативный
`onDragDropEvent` — общий на окно, и в главном окне его уже слушают колонки файлового
менеджера (`ColumnFoldersViewProps.tsx`): картинка, брошенная в модалку описания, могла бы
одновременно скопироваться в папку проекта под ней. Чтобы это сделать правильно, нужен
общий арбитр дропа на окно — отдельная работа. Пока: кнопка выбора файла и вставка из
буфера (⌘V), чего для скриншотов достаточно.

Вставка из буфера идёт двумя путями: сначала HTML (`clipboardData.files` — работает, когда
копировали внутри webview), затем плагин буфера Tauri (`clipboard.hasImage()` /
`readImageBinary('Blob')`) — системный скриншот в webview не попадает вообще. Для второго
пути в `src-tauri/capabilities/default.json` добавлены `clipboard:allow-has-image` и
`clipboard:allow-read-image-binary` (окна `*`, потому что редактор открывается из двух).

### Механика

Работаем с `selectionStart` / `selectionEnd` у `textarea`: оборачиваем выделение, ставим каретку
внутрь вставленной конструкции, при пустом выделении вставляем заготовку с выделенным
placeholder'ом. Повторное нажатие снимает обёртку (toggle), если выделение уже ей обёрнуто.
Блочные кнопки работают построчно по всем задетым строкам.

### Адаптивность — свойство рендерера, а не формата

«Разваливается на другом размере экрана» приходит из одного места: из жёстких размеров в
разметке — `width=800`, `style="width:800px"`, вёрстка таблицами, флоаты, многоколоночные блоки.
Ровно это и выдаёт WYSIWYG-редактор HTML, потому что показывает «как на бумаге».
**markdown этого выразить не может** — он линейный поток блоков без размеров. В вопросе «не
развалится» он не компромисс, а страховка.

Что реально обеспечивает адаптивность — делаем в `MarkdownView` и о том же просим сайт:

- таблицы — в обёртке с `overflow-x: auto`, сама таблица `width: 100%`, без фиксированных
  колонок. Из markdown такую обёртку задать нельзя, её ставит только рендерер;
- `img { max-width: 100%; height: auto }`;
- длинные ссылки и пути — `overflow-wrap: anywhere`, иначе одна строка растянет страницу;
- `pre` — свой `overflow-x: auto`;
- колонка текста ограничена по ширине (`max-width` ~820px, как уже сделано в `DocModal`),
  контейнер при этом тянется.

Редактор **не имеет права** выдавать `width` — ни атрибутом, ни инлайн-стилем. Список
разрешённых тегов и свойств в §1 закрыт именно по этой причине.

В модалке — переключатель ширины превью (широкое / узкое ~380 px), чтобы видеть узкий экран
сразу, не открывая сайт.

## 3. Картинки — base64 внутрь файла

Markdown картинки **не хранит**, он их упоминает ссылкой. Файл описания едет сайдкаром — это
один файл, ничего рядом с ним не едет. А папку ассетов внутри `options/` даже не создать:
`options` зарезервирован бэкендом, 403 на `mkdir` и `delete`.

Поэтому: **картинка кладётся в текст как `data:`-URI.** Файл self-contained, сайту ничего
дополнительно резолвить не надо.

Обязательный даунскейл при вставке, иначе sidecar с `ifMatch` начнёт возить мегабайты на каждую
правку: max ~1600 px по длинной стороне, webp/jpeg q80 → 100–200 КБ на картинку. base64 добавляет
к весу ещё около трети.

Вставка изолируется в **одну функцию** `insertImage()` — если позже переедем на ассеты обычными
файлами в `_description/` (папки `_*` синкаются нормально), правка будет точечной. Тогда
понадобится просьба к сайту резолвить относительные ссылки описания в presigned URL.

Локальный превью: пути через asset-протокол, в WKWebView `file://` не работает (общая грабля
проекта). Для `data:`-URI это неактуально, но правило помнить при переезде на §вариант с папкой.

## 4. Где кнопка

Описание принадлежит **проекту**, поэтому вход в двух окнах:

- **MAIN_WIN**, `MainTopPanel.tsx` — рядом с документацией и поиском. Активна только когда
  проект выбран: путь = главная папка + `activeProjectFolder` из `setActiveFolders_store`.
  Второй вход — контекстное меню проектной папки, рядом со статистикой.
- **NODE_WIN** — там проект уже открыт и настраивается, путь приходит вместе с ним
  (`NODE_WIN/index.tsx` читает по нему `options/options.json`). Кнопка — иконкой в левой части
  панели, сразу за названием папки: описание принадлежит проекту, а правая группа (`Presets`,
  `Doc`) — про инструменты, не про конкретную папку.

**Окна — разные реалмы**, поэтому: компонент общий в `src/components/`, состояние **не в сторе**,
SSOT — файл на диске.

### Гонка трёх писателей

MAIN_WIN, NODE_WIN и сайт (через `pull_sidecar`) могут писать один файл. Схема:

1. При открытии модалки читаем файл и запоминаем хэш прочитанного.
2. При сохранении сверяем текущее содержимое файла с этим хэшем.
3. Не совпало — не затирать молча, спросить («файл изменился, перезаписать / открыть новую версию»).

Без п. 3 правка, сделанная на сайте, исчезнет без следа.

## 5. Сторона сайта

Показа описания на сайте **пока нет вообще** — делаем сами, но другим стеком: Next 16,
React 19.2, Tailwind, Radix/shadcn, `next-themes`. Библиотеки при этом те же самые
(`react-markdown` + `remark-gfm` + `rehype-raw` + `rehype-sanitize` — обычные npm-пакеты,
работают и в серверных компонентах), поэтому расходиться могут только стили и схема санитайза.
Схема поэтому вынесена в [`DESCRIPTION_FORMAT_CONTRACT.md`](./DESCRIPTION_FORMAT_CONTRACT.md) §7
как код, который копируется дословно.

Что нужно сделать там:

**Рендерить `options/description.md` как GFM с разрешённым raw-HTML по закрытому списку тегов**
(`u`, `mark`, `span.fg-*`, `div.align-*`, `p.indent`, `br`, `details/summary`, `img`) — точный
список, схема санитайза и палитра в [`DESCRIPTION_FORMAT_CONTRACT.md`](./DESCRIPTION_FORMAT_CONTRACT.md).

**Два правила вёрстки**, без которых описание сломает страницу проекта: таблицу оборачивать
в контейнер с `overflow-x: auto`, картинкам ставить `max-width: 100%`. Из markdown это не
задаётся принципиально — только стилями рендерера. `@tailwindcss/typography` (`prose`) закрывает
базу, но про классы `fg-*` / `align-*` / `indent` он не знает — их правила дописать.

**Критично: `img-src 'self' data:`** в CSP — иначе картинки в описании не покажутся вообще, а это
самый вероятный камень. И `next/image` для `data:`-URI не годится, нужен обычный `<img>`.

**Цвета мапить на тему**, а не брать hex из файла: в файле лежит имя (`fg-yellow`), значения для
светлой и тёмной темы — в контракте §3. У сайта есть `next-themes`, поэтому это обязательный шаг,
иначе половина палитры пропадёт на светлой странице.

**Mermaid** — пакет `mermaid` ^11 в клиентском компоненте через `dynamic import`, тему
инициализировать по текущей. У нас локальный превью диаграмм отложен (пакет ~2–3 МБ), фенс
пишется и хранится независимо от этого.

Если на сайте появится и **редактирование** — те же ограничения на выходе (контракт §9): только
разрешённые теги, цвет классами, никаких размеров, запись через `ifMatch` без молчаливого
затирания.

## 6. Что дальше: единый вид для остальных редакторов

Сейчас «подобные редакторы» в проекте хранят **HTML, а не markdown**:
`src/components/RichTextEditor.tsx` — это `contentEditable` + `document.execCommand`
(deprecated API). Потребителей три: комментарий ноды (`data.comment`), тултип свойства,
описание плагина. Показываются через `dangerouslySetInnerHTML` в четырёх местах
(`CustomTooltip.tsx:68`, `DocModal.tsx:468`, `DocModal.tsx:830`, `PluginSortableListItem.tsx:285`).

Цель — свести их на `MarkdownEditor`. Порядок безопасный:

1. Сначала новое описание проекта — на нём редактор обкатывается.
2. Рендерер учится обоим форматам. Приём уже есть в проекте: `TooltipBody` различает
   `isHtml()` → HTML как есть, иначе markdown.
3. Редактор с этого момента пишет только md; старый HTML продолжает показываться.
4. Разовый конвертер по исходникам `plugins-dev/` (precedent — `migrateTimecodeSeconds.ts`).
   Помнить: HTML лежит и в артефактах `distr-plugins/`, и в плагинах, уже установленных у людей,
   и в сохранённых флоу — поэтому п. 2 не выбрасывается никогда.

Цвет при переезде **не теряется** — он переезжает на `<span class="fg-*">`, как в §1.

## Что НЕ делать

- Не заводить `description.html` и не менять `Sidecar` — имя файла в контракте с сайтом.
- Не заливать описание обычным путём `presign` → `PUT` → `notify`: объект ляжет рядом с тем,
  который читает сайт, и правки уедут в никуда (на этом уже обжигались, R2-план п. 25).
- Не создавать подпапки внутри `options/` — 403 от бэкенда.
- Не решать межоконную задачу общим стором: MAIN_WIN и NODE_WIN — разные JS-реалмы.
- Не вставлять картинки без даунскейла.
- Не тащить второй рендерер markdown.
