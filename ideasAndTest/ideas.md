## 💡 Локальный ML в плагинах (Transformers.js / ONNX Runtime)

**Репозиторий:** https://github.com/huggingface/transformers.js
(пакет `@huggingface/transformers`, текущая версия 4.x)

### Суть идеи

Запускать готовые ML-модели **локально, без платных API и без сервера** — прямо внутри
приложения или плагина. Transformers.js — это JS-порт питоновской `transformers` от
Hugging Face: модель конвертируется в **ONNX**, инференс идёт через **ONNX Runtime**
(бэкенды: WASM на CPU по умолчанию, опционально WebGPU на GPU; квантизация fp32/fp16/q8/q4).

Главный вывод: ML-задачи делятся на два очень разных класса, и это определяет, где
локальные модели реально хороши.

| Класс | Задачи | Локально vs платно |
|---|---|---|
| 🟢 **Восприятие** (perception) | удаление фона, depth-map, сегментация, детекция, эмбеддинги, OCR, zero-shot (CLIP) | модели **маленькие, быстрые, на уровне SOTA, бесплатно** — часто не хуже платных |
| 🔴 **Понимание/генерация** (LLM-style) | суммаризация, переписывание, «умный» перевод, чат | маленькие локальные модели **заметно хуже** Claude/GPT/DeepL |

### Где может пригодиться в нашем проекте (AE-пайплайн)

| Идея плагина | Модель (пример) | Зачем |
|---|---|---|
| **Удаление фона** | RMBG-1.4 / MODNet (~44 МБ) | авто-маска для композитинга, замена фона |
| **Карта глубины** | Depth Anything (small, ~50 МБ) | 2.5D-параллакс, fake-3D из плоского кадра |
| **Сегментация / детекция** | SAM, YOLO | авто-рото, маски объектов, трекинг-подсказки |
| **Семантический поиск по медиа** | CLIP (zero-shot) | «найди клипы с машиной» текстом в файл-менеджере |
| **Эмбеддинги субтитров / имён файлов** | bge / e5 / gte (~100 МБ) | дедуп, поиск похожих фрагментов, авто-тегирование |
| **OCR** | document image-to-text | вытащить текст из кадра/скриншота |

Это дополняет существующее семейство AI-плагинов (`AIcomfyUI`, `AIparser`,
`AItranslateVA`, `AIrevoicer`…), которые ходят во внешние/платные сервисы — здесь часть
задач можно увести в локальный бесплатный инференс.

### ✅ Плюсы

- **Бесплатно** — нет per-request оплаты, нет ключей API, нет лимитов.
- **Офлайн / приватность** — данные не уходят наружу (важно для клиентского контента).
- Для perception-задач (фон, depth, эмбеддинги) **качество на уровне платных**.
- Модели **не гигантские**: vision/audio/embedding — десятки–сотни МБ, не многогигабайтные LLM.
- Та же модель (ONNX) переиспользуема и из JS, и из Rust.

### ❌ Минусы / риски

- ⚠️ **WebGPU в WKWebView (macOS) долго был недоступен** → Transformers.js во фронте
  свалится в **WASM на CPU = медленно**. Это ключевой блокер «в лоб».
- Для **генерации текста** локальные модели хуже платных — этот класс задач лучше
  оставлять на API.
- Первый запуск = **скачивание модели** (десятки–сотни МБ): нужен прогресс и обработка
  офлайна.
- Дополнительный вес зависимостей (onnxruntime).

## Куда это встраивать: в программу или в плагин?

### 🥇 Рекомендация: native ONNX в Rust + тонкий плагин (гибрид)

Transformers.js заточен под **чистый веб** (браузер/WASM). У нас **десктоп на Tauri с
Rust-бэкендом**, поэтому правильнее не гонять модель в WKWebView, а:

1. **Один раз** добавить нативный ONNX Runtime в Rust через крейт
   [`ort`](https://github.com/pykeio/ort) с **CoreML execution provider** на macOS →
   инференс на GPU/Neural Engine, **в разы быстрее WASM**, без тормозов вебвью.
2. Экспонировать его как Tauri-команду (specta) — по аналогии с тем, как сейчас сделан
   `exec_command` / `ffmpeg_exec_with_progress` в [_template/tauri.ts](plugins-dev/_template/tauri.ts).
3. **Плагин** остаётся тонким: вызывает команду + управляет своей моделью. Тяжёлая
   нативная зависимость живёт в ядре один раз, а плагинов на её основе можно делать много.

### Альтернативы

- **Только плагин (Transformers.js в webview)** — быстрый прототип без сборки Rust, но
  CPU/WASM-медленно. Годится проверить идею, не для прода.
- **Только в ядро** — оправдано, лишь если это сквозная общая возможность; иначе привязывает
  жизненный цикл моделей к релизам приложения. Скорее overkill.

## Как устанавливать модели и можно ли автоматически?

**Да, автоматически — и в кодовой базе уже есть готовый паттерн.** Плагин `transcribeVA`
кладёт whisper-бинарник и Silero-VAD модель в свою папку (`whisper/`, `whisper/vad/`) —
ровно та же схема подходит для ONNX-моделей.

Модели на Hugging Face Hub лежат как обычные файлы (`.onnx`), доступные по HTTPS, значит
их можно качать на лету. Готовые хелперы из [_template/tauri.ts](plugins-dev/_template/tauri.ts):

- **`http.download(url, dest, { nodeId, statusText })`** — качает файл с прогрессом в
  статусбаре (тот же формат, что у ffmpeg). Идеально для тяги модели с HF Hub.
- **`paths.pluginInstallPath(pluginId, version)`** — папка ассетов плагина, работает и в
  dev, и в prod. Сюда складывать модели (напр. `<install>/models/rmbg.onnx`).
- **`paths.platformTarget()`** — `mac-arm64` / `mac-x64` / … для выбора правильного
  бинарника/провайдера.
- **`fs.existsFile(p)`** — проверка перед скачиванием (ленивая установка «по требованию»).

**Схема авто-установки (lazy, на первом запуске):**

```
1. plugin start
2. const model = `${await paths.pluginInstallPath(id, ver)}/models/rmbg.onnx`
3. if (!(await fs.existsFile(model)))
       await http.download(HF_URL, model, { nodeId, statusText: 'Downloading model…' })
4. инференс (native ort-команда или Transformers.js с env.localModelPath = …)
```

Варианты доставки модели:
- **Lazy-download (рекомендуется)** — качаем при первом использовании, кэшируем в папке
  плагина. Дистрибутив плагина лёгкий. ✅ как сейчас с whisper.
- **Bundle в плагин** — модель внутри пакета плагина. Просто, но раздувает дистрибутив
  (особенно при нескольких моделях).
- **Transformers.js авто-кэш** — библиотека сама тянет с HF Hub и кэширует (через
  `env` настраивается путь/`localModelPath`/`allowRemoteModels`). Меньше контроля над тем,
  куда легло.

## 💡 Транслитерирующие ключи паттерна: `$clearName2en` / `$clearFileName2en`

### Откуда идея

На Windows whisper-плагин падал на файле `Copy of СapturedbytheCEO_S01E03_eng…` —
первая буква «**С**» оказалась кириллической (U+0421). `whisper-cli` (whisper.cpp, narrow
`char** argv`) на Windows коверкает не-ASCII пути → не нашёл/не записал JSON → шаг вернул
пусто → `saveFileOnGD` упал на `inputFile[0]`. На macOS (UTF-8) то же имя работает.

Корень шире самого whisper: `$clearName`/`$clearFileName` **намеренно сохраняют любые
юникод-буквы** — [clearFileName.ts:14](src/Utils/clearFileName.ts#L14) чистит по
`/[^\p{L}\p{N}\s\[\]()._\-]/gu`, где `\p{L}` = буква любого алфавита. То есть кириллица,
китайский и т.п. проходят насквозь и потом ломают нативные бинарники / не-UTF-8 окружения.

### Что хотим

Завести два новых ключа паттерна — `$clearName2en` и `$clearFileName2en` — которые делают
то же, что `$clearName`/`$clearFileName`, но **дополнительно транслитерируют все не-ASCII
буквы в латиницу** (Серёжа → Serezha, 北京 → Beijing/пиньинь). Старые ключи не трогаем —
обратная совместимость, выбор за пользователем по месту в маске.

### Где править (3 точки)

1. [searchType.ts](src/types/searchType.ts) — добавить `clearName2en` и `clearFileName2en`
   в `enum PatternKeys`.
2. [formatNameByPattern.ts:36](src/Utils/formatNameByPattern.ts#L36) — два новых replacer'а
   рядом с `clearName` / `clearFileName`, обернуть результат в `transliterate(...)`.
3. Новый хелпер `transliterate()` (напр. `src/Utils/transliterate.ts`) — после `clearFileName`
   прогоняет строку через транслитерацию и финально вычищает всё, что не `[A-Za-z0-9 ._\-()\[\]]`.

### Чем транслитерировать

- Кандидаты-библиотеки: `transliteration` (npm, покрывает кириллицу/CJK/много языков),
  либо `unidecode`-порт. Минус — вес зависимости.
- Лёгкий свой путь: `str.normalize('NFKD').replace(/\p{M}/gu,'')` снимает диакритику
  (é→e, ü→u), а кириллицу добивать своей map-таблицей. Покрывает 90% наших кейсов без
  зависимостей, но не CJK.
- Решение по объёму языков отложено — для текущих задач (RU→EN) хватит NFKD + кириллическая
  карта.

### Что уже сделано для whisper (отдельно от этой идеи)

В `transcribeVA` вся I/O whisper (temp WAV + сырой JSON) уведена в **ASCII-папку системного
temp** (`<os tmpdir>/whisper/<$random(5)>`), а готовый результат переносится в путь из
настроек ноды через Tauri `fs` (Rust, UTF-8 safe). whisper-cli больше **вообще** не видит
реальный путь → не-ASCII и в имени, и в родительских папках на Windows ему уже не мешают.
То есть для whisper проблема закрыта без `…2en`-ключей.

`…2en`-ключи всё равно полезны шире — для любых **других** плагинов/мест, где не-ASCII имя
уходит в нативный бинарь или не-UTF-8 окружение, и где результат должен лечь под осмысленным
(но латинизированным) именем, а не быть просто перенесён.

## 💡 Нода со скриптом: произвольный JS прямо в редакторе ноды

> **Статус: РЕАЛИЗОВАНО.** Плагин `plugins-dev/jsCode/` (+ `GUIDE.md`), общее eval-ядро —
> [`src/Utils/runUserCode.ts`](../src/Utils/runUserCode.ts) (одно и то же на кнопку «Run» в
> редакторе и на рантайм пайплайна), UI — `controlType: textedit` с флагом `runnable`,
> входы добавляются через «+» (имя-лейбл = имя переменной в коде).

### Суть идеи

Нода, в текстовом редакторе которой пользователь пишет **простой JS** — и он исполняется как
шаг пайплайна. Назначение: лёгкая логика над данными, без доп. библиотек, только на том, что
уже есть. Типовые задачи — **объединить/сравнить массивы, найти пары, условия, фильтрация,
перегруппировка путей/файлов**. Это generic escape-hatch: то, для чего лень делать отдельный
плагин, и полигон для прототипа логики, которую потом можно вынести в настоящий TS-плагин
(родственник JSX-playground, но другой рантайм).

### Node.js не нужен — нужен просто JS

Ключевой вывод обсуждения: для массивов/сравнений/условий **node-рантайм не требуется**.
Это чистый JS, который и так крутится во вебвью. Node давал бы fs/child_process/npm — но это
уже есть через Tauri-хелперы (`fs`, `ffmpeg`, `exec`, `paths`, `http` из
[_template/tauri.ts](plugins-dev/_template/tauri.ts)). Поэтому исполнять скрипт прямо в
рендерере с инъекцией курируемого API, а не тащить node.

### Модель исполнения

```ts
const fn = new Function('ctx', 'api', 'log', `return (async () => { ${userCode} })()`);
const out = await fn(ctx, api, log);   // out → уходит дальше по пайплайну
```

Инъекция в скоуп:
- **`ctx` / `item`** — текущий `_item` + `_description` (входы, пути, данные паттерна).
- **`api`** — курируемый набор хелперов (тот же, что у плагинов: fs/ffmpeg/exec/paths/http) +
  мелкие утилиты. Список расширяем по мере надобности.
- **`log()`** — вывод в logwin (как `[aeProcess] inObj → …`).
- **return** — то, что уходит дальше (массив файлов / данные).

### Что нужно прибить гвоздями (главное)

**Контракт ноды:** какая форма на входе, что скрипт *обязан* вернуть, и **когда** он
запускается — per-item (на каждый файл) vs один раз над всем списком. От этого зависит всё
остальное.

### Редактор

Тип свойства `TextEdit` уже есть ([TextEditProperty.tsx](src/NODE_WIN/nodes/properties/TextEditProperty.tsx),
[types.ts:139](src/NODE_WIN/definitions/types.ts#L139)). Для кода — расширить: моноширинный
шрифт, опционально CodeMirror (легче Monaco) для подсветки, боковой справочник «доступные
функции» (список инъектированного `api`). Старт — обычная textarea.

### Риски

- Бесконечный цикл подвесит вебвью (исполнение в рендерере). При необходимости — Web Worker
  с таймаутом.
- Ошибки скрипта должны явно вылетать в лог, а не молча ронять шаг.

## 💡 Плагин «оживить кадр» (zoompan / Ken Burns)

### Суть идеи

Отдельный плагин, который из **статичной картинки делает видео с движением** — наезд/отъезд
(zoom) и панорама (pan). Эффект Кена Бёрнса. Базируется на ffmpeg-фильтре `zoompan`.

### Почему отдельный плагин, а не фильтр convert

`zoompan` **меняет природу выхода**: на входе статика, на выходе — клип с длительностью. Это не
«коррекция кадра» (как фильтры convert), а **генерация движения**, поэтому в convert он
чужеродный.

### Механика и засада

- Параметры: выходной размер `s`, длительность `d` (в кадрах), выражения зума `z` и позиции
  `x`/`y` (наезд за N кадров в заданную точку).
- ⚠️ Работает покадрово и **дрожит на дробном зуме**. Стандартный приём против дрожания:
  сперва апскейл источника ×4-8, потом `zoompan`, потом `scale` обратно к целевому размеру.

### Что продумать

- [ ] UI выбора точки/направления движения (центр наезда, старт/конец рамки).
- [ ] Длительность клипа и fps на выходе.
- [ ] Пресеты движения (наезд в центр, отъезд, пан слева-направо…).

## 💡 Децентрализованная статистика: `options/__stat/YYYY.MM.jsonl` в каждом проекте

> **Статус: базовый механизм РЕАЛИЗОВАН (2026-06-22).** Добавлена переменная пути
> `$projectPathGD` ([db_analytics.rs](src-tauri/src/commands/db_analytics.rs) → `apply_vars`)
> + она выбирается в дропдауне путей архива ([TabMain.tsx](src/MAIN_WIN/options/tabs/TabMain.tsx)
> → `archiveOptions`). Запись `local-archive` сделана атомарной (один `write_all` вместо
> `writeln!`) — параллельная обработка не бьёт строки. Включается **строкой в настройках**:
> `local-archive` + путь `["$projectPathGD", "options", "__stat", "$YYYY.$MM"]`.
> **Отложено:** сводное чтение «по всем проектам» (обход папок) и производный rollup-кэш.

### Суть идеи

Хранить статистику не в одном общем месте, а **рядом с самим проектом** — в его папке
`options/__stat/` файлами помесячно (`YYYY.MM.jsonl`). Каждый проект носит свою статистику
сам. Тогда:
- статистика **децентрализована** по проектам и пользователям;
- можно смотреть как по одному проекту, так и агрегировать «по всем своим»;
- **отказоустойчиво** — пропал/побился один файл, остальное живо.

Идея-зеркало того, как уже устроен сбор по шаблонам.

### ⚠️ Главное, критически: это почти всё уже есть

В коде уже работает движок статистики — [db_analytics.rs](src-tauri/src/commands/db_analytics.rs):
шаблон **`local-archive`** пишет ровно такой append-only **JSONL** (одна строка = одно
событие), а путь задаётся в `storage.localArchives[]` ([appSettings.ts](src/types/appSettings.ts))
сегментами с переменными `$projectName / $YYYY / $MM / …`. Прецедент `options/_post/$MM.$YYYY.jsonl`
из VK-плагина — тот же паттерн.

То есть это **не новая архитектура, а выбор места записи** поверх готового движка. Прежде чем
что-то строить — проверить, нельзя ли просто настроить `local-archive` с путём в папку
проекта.

### Чего реально не хватает (единственный настоящий gap) — это 1 строка кода, а не 0

Шаблон и триггер готовы: `write_analytics` пишет **после каждого item и при ошибке**
([db_analytics.rs:339](src-tauri/src/commands/db_analytics.rs#L339)), а пер-item JSONL даёт
шаблон **`local-archive`** ([db_analytics.rs:307](src-tauri/src/commands/db_analytics.rs#L307)) —
он сам создаёт папку и сам форсит `.jsonl`. Так что да, это почти «просто строчка в настройках».

**Но «в папке проекта» из одного конфига сейчас не выразить.** Путь строится из сегментов,
где **segment[0] становится корнем ФС** (`PathBuf::from(resolved[0])`,
[db_analytics.rs:133](src-tauri/src/commands/db_analytics.rs#L133)). Переменные — это дата +
`$projectName`/`$mainFolderName` (это **имена, а не пути**) + `$localFolder`, который
резолвится в **пустую строку** ([db_analytics.rs:118](src-tauri/src/commands/db_analytics.rs#L118)).
То есть конфигом можно писать только в **захардкоженный абсолютный корень**, разбитый по
подпапкам `$projectName` — это **центральное** хранилище по имени проекта, а **не** внутри
`options/` самого проекта.

`projectPathGD` уже лежит в записи (используется на
[db_analytics.rs:322](src-tauri/src/commands/db_analytics.rs#L322)), просто не выставлен как
переменная пути. Выставить = **ровно одна строка** в `apply_vars`:

```rust
result = result.replace("$projectPathGD", &record.project_path_gd);
```

После этого идея — действительно просто запись в настройках:

```json
{ "enabled": true, "templateId": "local-archive",
  "path": ["$projectPathGD", "options", "__stat", "$YYYY.$MM"] }
```

→ append в `{project}/options/__stat/2026.06.jsonl`, децентрализовано по проектам. Имя берём
`$YYYY.$MM` (сортируется), не `$MM.$YYYY`. Остальные агрегаторы (день/месяц/год/проект) тоже
уже написаны.

### ❌ Чем децентрализация платит

1. **Дорогое чтение.** Запись дёшева (append в свой шард), но «по всем проектам» = обойти
   N папок × M помесячных файлов и слить на лету. На GDrive/gsync (твоя реальность) это
   медленно и IO-тяжело. Готовые шаблоны `total-by-project` / `by-month` наоборот
   **пре-агрегируют на записи** в общий файл → чтение O(1). Вывод: скорее всего нужны **оба**
   слоя — пер-проектный JSONL как источник правды (портабельный) **плюс** производный
   центральный rollup-кэш для быстрых дашбордов, пересобираемый из шардов. Чистая
   децентрализация делает «по всем» тормозной.
2. **Откуда список проектов?** Чтобы агрегировать «все мои», надо знать, где все корни. Если
   это обход GDrive — медленно и не увидит отключённые/несинхронизированные проекты. Охват
   зависит от того, что сейчас примонтировано.
3. **Конфликты записи на общей GDrive-папке.** `options/` синкается и **расшарен**. Два
   юзера (или одна машина в двух местах) пишущие в один `YYYY.MM.jsonl` → GDrive не мёржит
   текст, а плодит «conflicted copy» / перезатирает. Append-JSONL **не conflict-safe** на
   общем синке. Лечится шардингом по юзеру в пути: `__stat/$user/YYYY.MM.jsonl`. С учётом
   мультиюзер/GDrive-шины — риск реальный, не теоретический.
4. **config vs telemetry в `options/`.** `options.json` — это *конфиг флоу* (осмысленный,
   правится руками). `__stat/` — *бесконечно растущая телеметрия*. Смешивать их — мусор;
   при копировании проекта-шаблона потащишь чужую статистику. Прецедент `_post/` под
   `options/` за такое размещение, но решить надо осознанно (вариант: сиблинг
   `{project}/__stat/`, а не внутри `options/`).
5. **Версионирование строк.** Шарды пишут *разные версии приложения годами* → поля
   разнородны, и мигрировать тысячи файлов по проектам уже не выйдет. Reader обязан терпеть
   любую историческую схему вечно → класть `v` в каждую строку и парсить толерантно.
6. **Отказоустойчивость — палка о двух концах.** «Пропал файл — ничего не сломалось» — да для
   агрегации, но потеря **молчаливая**: не отличить «пусто, потому что не работали» от «файл
   удалён/побился/не доехал синком». Нет центрального журнала → дыры не детектятся.
   Resilience и аудит здесь в конфликте.
7. **Имя `MM.YYYY` не сортируется.** `06.2026` лексикографически меньше `01.2027` — список
   файлов в UI поедет. Брать `YYYY.MM` (`2026.06`) — сортируется естественно.

### Вердикт

Идея здравая и **по шерсти** того, что уже есть — но это не «построить БД», а: (а) прокинуть
одну переменную пути на папку проекта и настроить существующий `local-archive`; (б) всё равно
держать производный central-rollup для быстрого «по всем»; (в) шардить по юзеру из-за
GDrive-конфликтов; (г) решить config-vs-telemetry и взять сортируемое имя `YYYY.MM`. Само по
себе «чистая децентрализация» без rollup-кэша даст медленный кросс-проектный обзор.
