# Разделение по персонажам: цепочка нод и формат

**Статус:** ⬜ не начато (ТЗ составлено 2026-08-24)

> Зачем: и редактор реплик на сайте, и локальный редактор
> ([`DIALOG_EDITOR_PLAN.md`](./DIALOG_EDITOR_PLAN.md)) построены на «одна дорожка = один
> персонаж», где дорожка — это **титры персонажа**. Отдельное аудио на каждого не нужно:
> достаточно одного общего звука и разделённых титров. Задача цепочки — получить титры,
> приписанные персонажам, а не нарезать аудио. Сейчас такого разделения не делает ни одна нода: `transcribeVA` (whisper)
> диаризацию не умеет, `AItranslateVA` передаёт `num_speakers` во внешний сервис дубляжа и
> забирает **один смикшированный** результат. Это блокирующий пробел.
>
> Обе стороны связаны **одним файлом** — `dialog.json`
> ([`DIALOG_FORMAT_CONTRACT.md`](./DIALOG_FORMAT_CONTRACT.md), канон в
> `innovation-hub/docs/DIALOG_FORMAT.md`). Диаризация — то, что этот файл наполняет, поэтому её
> формат и её настройки нельзя проектировать отдельно.

## 1. Почти всё уже есть — цепочка из существующих плагинов

Новых нод нужно меньше, чем кажется: распознавание, приведение JSON к нужному виду, нарезка и
перевод в проекте уже сделаны. Цепочка:

```
IN: source.mp4
  1. convertFile_v2            → audio.wav (16 kHz, mono)        ✅ есть
  2. transcribeVA              → words.json (jsonfull, слова)     ✅ есть
  3. JSONnormalizeTranscribe   → cues.json (блоки + слова)        ✅ есть, нужен новый формат вывода (§1.1)
  4. diarizeSpeakers           → diarization.json                 ⬜ НОВОЕ (§3) — единственная новая способность
  5. dialogDocBuild            → dialog.json                      ⬜ НОВОЕ (§5), сборка из готовых частей
  6. audioPeaks                → mix.peaks.json                    ⬜ НОВОЕ, спека в плане сайта §V.4
  7. AItranslateVA             → переводы                          ✅ есть
  (—) splitBySpeaker           → 01/audio.wav …                    ⬜ НЕОБЯЗАТЕЛЬНО (§6): только если стемы
                                                                     понадобятся дальше, например озвучке
```

### 1.1. Новый формат вывода у `JSONnormalizeTranscribe`

Нода уже делает ровно то, что нужно: из пословного `jsonFull` whisper собирает
`{ lang, dur, words?, sentences }`, причём логика разбора и сборки блоков живёт не внутри
плагина, а в общем утиле `src/Utils/whisperTranscript.ts` (`parseTranscript`, `buildSentences`).
Её же настройки (`maxLineLength`, `maxLine`) — это и есть правила нарезки текста на блоки.

Добавляется третий формат вывода `cues`: тот же разбор, но блоки отдаются в виде, из которого
собирается документ — с миллисекундами вместо секунд и с сохранённой ссылкой на слова:

```jsonc
{ "lang": "en", "durMs": 718400,
  "cues": [ { "startMs": 26270, "endMs": 29190, "text": "So these guys just disappeared.",
              "wordFrom": 0, "wordTo": 5 } ],
  "words": [ { "startMs": 26270, "endMs": 26580, "text": "So" } ] }
```

Почему не сразу `dialog.json` из этой ноды: она ничего не знает про папки дорожек, аудиофайлы,
языки и раскладку задачи — это работа `dialogDocBuild` (§5). Разделение по способностям, а не
по «одна нода делает всё»: тогда `cues` пригодится и другим сценариям (титры в After Effects,
снап границ реза), а не только редактору.

### 1.2. Про «распознать один раз» против «распознать каждую дорожку»

Соблазн — сначала нарезать аудио по персонажам, потом гонять whisper по каждому куску. Так
делать не надо:

- **дороже:** N проходов whisper вместо одного;
- **хуже текст:** whisper сильнее всего опирается на контекст, а в куске с вырезанной чужой
  речью контекст рваный;
- **галлюцинации:** на длинной тишине (а стем персонажа — это в основном тишина) whisper
  склонен выдумывать текст. Известная и очень заметная на практике беда.

Порядок «один проход по целому файлу → отдельно разметка «кто говорит когда» → слова получают
спикера по перекрытию» этих трёх проблем не имеет. Режим `jsonfull` у `transcribeVA` (DTW-точные
пословные тайминги) даёт для этого всё необходимое.

Но у распознавания по дорожкам есть своё преимущество — настоящие стемы, — поэтому это не
«правильно против неправильно», а развилка. Все способы и их цена — §2.

## 2. Пять способов получить дорожки — и что у каждого на выходе

Способ ещё не выбран, и это нормально: **редактору всё равно, каким путём получены файлы**, он
работает с `dialog.json` (§2.6). Поэтому способы взаимозаменяемы, их можно пробовать по одному и
менять потом, не трогая ни редактор, ни формат. Ниже — что проверить у каждого.

### A. Разделить аудио по спикерам, потом распознать каждую дорожку

Граф ComfyUI (модель разделения голосов) через существующий плагин `AIcomfyUI`: он отправляет
workflow на сервер, дожидается и скачивает результат. На выходе — N аудиофайлов, каждый гоняем
через `transcribeVA`, потом `JSONnormalizeTranscribe`, потом складываем в раскладку.

| | |
|---|---|
| **плюс** | попутно получаются настоящие стемы. Редактору они не нужны, но пригодятся озвучке — и тогда их не придётся делать отдельно |
| **плюс** | почти всё уже есть: `AIcomfyUI` + `transcribeVA` + нормализатор |
| **минус** | N проходов whisper вместо одного (дороже и дольше) |
| **минус** | текст хуже: whisper живёт на контексте, а в стеме контекст рваный |
| **минус, самый неприятный** | **галлюцинации на тишине.** Стем персонажа — это в основном тишина, и whisper склонен выдумывать на ней текст. Лечится: подавать не весь стем, а только участки речи (VAD / границы по уровню), либо поднимать `no-speech-threshold` |
| **проверить** | сервер ComfyUI в плагине сейчас **внешний** (адрес зашит в коде: `https://x.kraslance.ru/v2/run`). Для NDA-контура он должен быть локальным — значит адрес надо вынести в настройку ноды |
| **проверить** | качество разделения на перебивках: там модели чаще всего мажут |

### B. Один прогон распознавания, отдельно атрибуция по голосу

Whisper по целому файлу (`jsonfull`, пословные тайминги), отдельно — разметка «кто говорит
когда» (эмбеддинги голоса + кластеризация), затем слова получают спикера по перекрытию (§5).

| | |
|---|---|
| **плюс** | один проход whisper, текст лучше (полный контекст), галлюцинаций на тишине нет |
| **плюс** | дёшево по времени: разметка голосов быстрее распознавания |
| **минус** | стемов не даёт. Для редактора это не минус (звук нужен один, общий), но озвучке их потом придётся готовить отдельно |
| **минус** | нужен новый инструмент под разметку голосов (§2.5) |
| **проверить** | сколько ошибок атрибуции на своём материале при 2–3 персонажах |

### C. Гибрид: текст из полного прогона, дорожки из разделения

Whisper один раз по целому файлу (как в B), разделение по спикерам (как в A) — но не ради
текста, а ради **аудио дорожек**; атрибуция слов делается сопоставлением с тем, в каком стеме в
этот момент есть речь.

| | |
|---|---|
| **плюс** | лучший текст, а стемы получаются попутно — пригодятся дальше |
| **плюс** | атрибуция получается почти бесплатно: сравнить уровень в стемах на интервале слова проще, чем считать эмбеддинги |
| **минус** | два тяжёлых шага в цепочке вместо одного |
| **оценка** | **вероятно лучший вариант**, если разделение из A даст приличное качество |

### D. Атрибуция с помощью видео

Дополнительный сигнал, а не самостоятельный способ: кто в кадре в этот момент говорит
(движение губ / активный спикер). Складывается с A, B или C как второе мнение — там, где голос
сомнительный, помогает картинка.

| | |
|---|---|
| **плюс** | берёт информацию, которой в звуке нет вообще |
| **минус** | работает только когда говорящий в кадре: закадр, спина, монтажная склейка — мимо |
| **оценка** | не для первой версии. Пригодится, если A/B/C дадут заметно меньше 70 % |

### E. Внешний сервис дубляжа

Если сервис, который уже используется в `AItranslateVA`, умеет отдавать пер-спикерную разметку
или дорожки — это самый дешёвый путь: ни моделей, ни бинарников локально.

| | |
|---|---|
| **плюс** | ничего не нужно ставить |
| **минус** | **не годится для NDA-контура**: материал уезжает. Значит для локальных папок всё равно понадобится A, B или C |
| **проверить** | спросить у владельца сервиса, что он умеет отдавать помимо смикшированного результата |

### F. Cast Analyzer Next — эталон результата, а не готовое решение

Отдельная программа (0.21.0-alpha.21), чей выход разобран на реальных данных (8 сцен, папка
`DUB/`). Это **тест**: она не встроена в наш конвейер и встроена не будет как есть. Её роль
двойная и обе важные:

1. **даёт финальный результат уже сейчас** — папки задач с документом, по которым делается и
   проверяется редактор, не дожидаясь наших нод;
2. **задаёт эталон, который надо воспроизвести нодами** в программе (§2.4) — постадийно, со
   своими моделями и на своём железе.

Внутри —
сочетание почти всех путей выше: разделение источника (`bs_roformer`), диаризация (MOSS),
локальная проверка структуры (Sortformer), постоянная личность по голосу (ReDimNet2) и
атрибуция по видео (ASD) в fusion.

Что отдаёт: `all_dialogue.json` (реплики с текстом, спикером, уверенностью и флагом «нужна
проверка»), `SPEAKER_XX.srt` + `UNKNOWN.srt`, `cast.json` (имена, статистика), стемы полной
длительности с тишиной вне своих реплик, нарезку по репликам, ASD-треки и граф персонажей.

Замеры её benchmark: ~92.7 % при требовании «один человек = один Character ID», ~95.4 % если
разрешить дробление, ~87 % на новых материалах. То есть **порог 70 % уже перекрыт**, а
доминирующая ошибка — дробление одного человека на несколько дорожек (9 дорожек на ~7
говорящих) и `UNKNOWN` по 6–7 реплик на сцену.

| | |
|---|---|
| **плюс** | ничего не нужно писать: программа есть, данные есть, качество измерено |
| **плюс** | покрывает и текст, и стемы, и атрибуцию по видео сразу |
| **минус** | это отдельная программа со своим форматом папок — нужен конвертер в наш документ (написан: `innovation-hub/scripts/import-castanalyzer.mjs`) |
| **минус** | пути в её JSON абсолютные и с чужой машины (`C:\\Users\\...`) — на них нельзя опираться, только на структуру папок |
| **проверить** | как встроить в граф: вызывать ли её как внешний процесс через `ctx.exec` (как whisper) или оставить отдельным шагом, а нодой только импортировать результат |

Практический вывод: **вопрос «каким способом» перестал быть блокирующим.** Финальный результат
собирается уже сейчас (конвертер написан), редактор делается по нему, а воспроизведение
нодами — отдельная работа с зафиксированным эталоном (§2.4). Способы A–E остаются как
альтернативы для отдельных стадий.

### 2.4. Как воспроизвести это нодами — постадийная карта

Зафиксировано по `project.json`, `analysis.json`, `07_EXPORTS/manifest.json` и `separation.json`
реального прогона. Одиннадцать стадий; для каждой — что она делает, что обязана отдать, и чем
это закрывается у нас.

| № | Стадия у них | Что делает | Что обязана отдать | Чем закрываем |
|---|---|---|---|---|
| 1 | `source_registered` | регистрация исходника | путь, длительность, fps | ядро конвейера, ноды не нужно |
| 2 | `source_separated` | отделить речь от музыки и шума: `audio-separator` 0.44.5, модель `bs_roformer_vocals_resurrection_unwa.ckpt`, вход 48 кГц (модель 44.1) | `DIALOGUE.wav`, `M&E.wav` | **есть чем**: граф ComfyUI через `AIcomfyUI` (у владельца уже лежит `audioseparation.json` и результат прогона `bs_roformer`), либо новая нода-обёртка над `audio-separator` |
| 3 | `dialogue_analysis_audio` | привести речь к 16 кГц моно | `audio_16k_mono.wav` | ✅ `convertFile_v2` |
| 4 | `moss_turns` | распознать текст **и** разметить реплики по спикерам одним движком (MOSS), 63 сегмента | реплики: `start`, `end`, `text`, `speaker`, `confidence` | ⬜ у нас whisper (`transcribeVA`) даёт текст и пословные тайминги, но **не спикеров** — значит либо новая нода под MOSS-подобный движок, либо whisper + стадия 6 (§2.5) |
| 5 | `sortformer_local_structure` | локальная проверка структуры: `nvidia/diar_streaming_sortformer_4spk-v2.1`, 25 локальных правок, 3 mixed-turn | границы реплик, флаг «в реплике двое» | ⬜ новая нода. **Важно про железо:** у них это NeMo на CUDA (RTX 3090); на macOS CUDA нет, нужен ONNX-аналог (§2.5) или пропуск стадии |
| 6 | `voice_embedded` | постоянная личность по голосу (ReDimNet2) — то, что склеивает возвращающегося персонажа | эмбеддинг на реплику + кластеры | ⬜ новая нода; это и есть «разметка голосов» из §2.5 |
| 7 | `asd_attempted` | атрибуция по видео (кто в кадре говорит): 86 треков, 27 реплик под сомнением | треки лиц + связь с репликами | ⬜ новая нода (способ D). Необязательна: работает только когда говорящий в кадре |
| 8 | `character_graph` | сборка персонажей из голосовых кластеров и лиц | `cast.json`, `character_graph.json` | ⬜ часть `dialogDocBuild` |
| 9 | `subtitles_exported` | `SPEAKER_XX.srt`, `UNKNOWN.srt`, `all_dialogue.json` | сырьё титров по персонажам | ⬜ `dialogDocBuild` (§5) + `JSONnormalizeTranscribe` с форматом `cues` (§1.1) |
| 10 | `speaker_stems_exported` | стемы полной длительности, тишина вне своих реплик, плюс нарезка по репликам | `SPEAKER_XX_guide.mp3`, `clips/` | ⬜ `splitBySpeaker` (§6), необязательный шаг |
| 11 | `analysis_complete` | манифест прогона | `manifest.json` + `dialog.json` | ⬜ `dialogDocBuild` |

**Минимальный набор, дающий рабочий результат:** стадии 2 → 3 → 4 → 6 → 9 → 11. Стадии 5, 7 и
10 повышают качество или готовят следующий шаг, но без них редактор уже полезен.

**Числа для планирования, снятые с их прогона:** 3-минутная сцена, RTX 3090, CUDA — 483 секунды
полного разбора (из них 65 с диаризация, 11 с fusion). То есть ~2.7× реального времени на
хорошей видеокарте. На CPU это будет в разы дольше — значит стадии 4–7 просятся в пул
`local` (по одной за раз), как уже сделано у `transcribeVA`.

**Что уже можно не проектировать заново:** правило стемов («полная длительность, тишина вне
своих реплик») и структура папок проверены на восьми сценах и совпали с тем, что мы написали
независимо. Расхождение только в именах: у них `04_SUBTITLES/SPEAKER_01.srt`, у нас `01/orig.srt`
— конвертер это переносит.

### 2.5. Если идём путём B или C — чем считать разметку голосов

Задача узкая: разметить участки речи и сравнить голоса между собой (эмбеддинги + кластеризация).
Берётся так же, как уже взят whisper: бинарник плюс модель в `copyAssets`, вызов через
`ctx.exec`, разбор вывода. Нода `diarizeSpeakers` (§3) устроена как близнец `transcribeVA`.

| Кандидат | Что тянет за собой | Годится для NDA | Оценка |
|---|---|---|---|
| **`sherpa-onnx`** — ONNX Runtime, готовые бинарники; сегментация pyannote-3.0 в ONNX + модель эмбеддингов | бинарник и модели на десятки МБ, как `whisper` в `copyAssets` | да | кандидат №1: тот же приём, без Python |
| `pyannote.audio` | Python + torch (~2–3 ГБ), модели за токеном HuggingFace | да | тяжело: второй рантайм в приложении |
| `whisperX` | Python + torch, зато распознавание и разметка одним инструментом | да | то же, плюс дубль уже имеющегося whisper |
| модель в ComfyUI | ничего локально сверх ComfyUI | если сервер локальный | если ComfyUI и так в цепочке (путь A/C) — разумно смотреть здесь первым |

Проверять руками, а не по документации: есть ли готовый бинарник под macOS и Windows, в каком
виде отдаёт результат, и как ведёт себя, когда число спикеров заранее неизвестно (самый частый
случай).

### 2.6. Что общего у всех способов — и почему выбор можно отложить

Выход один и тот же, независимо от пути:

```
{задача}/
  dialog.json          ← дорожки (персонажи), реплики, переводы, уверенность атрибуции
  source.mp4           ← кадр + общий звук
  mix.peaks.json       ← волна общего звука
  01/ orig.srt  es.srt ← сырьё титров персонажа
  02/ …
  (01/audio.wav)       ← только если стемы вообще делались
```

Отсюда практический вывод: **редактор можно делать и проверять уже сейчас** — тестовый комплект
собирается скриптом `innovation-hub/scripts/make-dialog-fixture.mjs` (видео, две дорожки с
волной, документ на 11 реплик, SRT-сырьё, включая неудобные случаи вроде дорожки «не
распознано» и перекрытия). Способ получения файлов выбирается параллельно и меняется потом без
правок редактора.

### 2.7. Целевая точность — 70 %, и это меняет приоритеты

Идеальная разметка не нужна и недостижима: перебивания, короткие реплики, похожие голоса
ошибаются всегда. Дальше материал правит человек, и наша задача — **подготовить правку**, а не
исключить её. Отсюда порядок вложения сил:

| куда **не** вкладываться | куда вкладываться |
|---|---|
| подбор идеальной модели и порогов | чтобы перенос реплики на другую дорожку стоил одного движения мышью |
| попытки разобрать перекрытия «правильно» | чтобы перекрытия были видны на таймлинии и оба текста сохранились |
| эвристики «угадать персонажа» при низкой уверенности | чтобы низкая уверенность была видна (`origin.confidence`) и сортировалась вперёд |
| выбрасывание сомнительного текста | дорожка `no: 0` «не распознано»: текст сохраняется всегда |

70 % правильной атрибуции при видимых 30 % сомнительных — рабочий результат. 95 % с
невидимыми ошибками хуже: человек не знает, где смотреть.

### 2.8. Где это всё исполняется

Обработка **всегда локальная**: сайт формирует задание, машины забирают и считают у себя.
Промежуточные файлы (`audio.wav`, `words.json`, `cues.json`, `diarization.json`) живут в
локальной рабочей папке несколько дней и вычищаются автоматически — ни в онлайн-хранилище, ни в
папке `OUT` их быть не обязано.

Два следствия, важных для формата:

1. **`dialog.json` обязан быть самодостаточным.** Он не имеет права зависеть от
   `diarization.json` или `words.json`: к моменту, когда человек откроет редактор, их может уже
   не быть. Поэтому уверенность атрибуции, спикер и способ **вписываются в сам документ**
   (`tracks[].diar`, `cues[].origin.confidence`), а не берутся ссылкой.
2. **В `OUT` попадает только финал** — документ, дорожки, пики, исходник. Структура настраивается
   графом; редактор привязан к ней, а не к промежуточным файлам.

Откуда взялся исходник — из онлайн-папки или из локальной сети — на цепочку не влияет вообще:
меняется только место, куда положили файл и откуда забрали результат.

## 3. Нода `diarizeSpeakers` ⬜

```jsonc
// plugins-dev/diarizeSpeakers/plugin.json
{
  "id": "diarizeSpeakers", "name": "Diarize Speakers", "version": "0.1",
  "apiVersion": 1, "type": ["nodeui", "processing"],
  "description": "Размечает, кто говорит когда: сегменты по спикерам в diarization.json.",
  "main": "diarizeSpeakers.js", "ui": "ui.json",
  "copyAssets": ["diar"], "external": [],
  "cost": "0", "costUnit": "run", "resourcePool": "local"
}
```

`resourcePool: "local"` — как у `transcribeVA`: модель ест процессор/GPU, два таких прогона
одновременно только мешают друг другу.

### Настройки (`ui.json`)

| id | контрол | по умолчанию | смысл |
|---|---|---|---|
| `inputFile` | link | — | аудио или видео (видео → достаём дорожку через ffmpeg) |
| `targetPath` | autocomplete | `$localFolder/OUT/$clearName` | куда положить `diarization.json` |
| `speakersMode` | ddm | `auto` | `auto` / `exact` / `range` |
| `numSpeakers` | slider 1–12 | `2` | при `exact` |
| `minSpeakers` / `maxSpeakers` | slider 1–12 | `1` / `6` | при `range` |
| `clusterThreshold` | slider 0.1–1.0 | `0.5` | порог кластеризации эмбеддингов; в режиме `auto` именно он решает, сколько спикеров получится |
| `minSegmentMs` | slider 100–2000 | `250` | сегменты короче выбрасываем: почти всегда шум |
| `mergeGapMs` | slider 0–1000 | `250` | склеивать соседние сегменты одного спикера, если пауза меньше |
| `speakerOrder` | ddm | `firstAppearance` | `firstAppearance` / `totalDuration` — как нумеровать спикеров (§4) |
| `speakerNames` | textedit | пусто | имена по порядку нумерации: `Anna, Bob` |
| `device` | ddm | `cpu` | `cpu` / `cuda` / `coreml` |
| `modelSegmentation` | textedit | из `copyAssets` | путь к модели сегментации |
| `modelEmbedding` | textedit | из `copyAssets` | путь к модели эмбеддингов |

| `saveToFile` | checkbox | `true` | как в `speech2signal`: `false` — отдать JSON строкой дальше по графу |

### Выход: `diarization.json`

Промежуточный файл. Сайт его **не читает** — он нужен `dialogDocBuild` и полезен для разбора
ошибок.

```jsonc
{
  "format": "diarization",
  "version": 1,
  "source": { "file": "audio.wav", "durationMs": 718400, "sampleRate": 16000 },
  "engine": {
    "name": "sherpa-onnx",
    "version": "1.10.0",
    "segmentation": "pyannote-segmentation-3.0",
    "embedding": "3dspeaker-eres2net"
  },
  "params": {                          // чем считали — чтобы прогон был воспроизводим
    "speakersMode": "auto",
    "clusterThreshold": 0.5,
    "minSegmentMs": 250,
    "mergeGapMs": 250,
    "speakerOrder": "firstAppearance"
  },
  "speakers": [
    { "id": "s0", "label": "SPEAKER_00", "name": "Anna",
      "no": 1, "firstAtMs": 26270, "totalMs": 214300, "segmentCount": 42 }
  ],
  "segments": [
    { "startMs": 26270, "endMs": 29190, "speaker": "s0", "confidence": 0.86 }
  ],
  "overlaps": [
    { "startMs": 31000, "endMs": 31240, "speakers": ["s0", "s1"] }
  ]
}
```

**Правила файла** — те же, что у документа (единицы и порядок должны совпадать во всей цепочке):

1. время — **целые миллисекунды**, `endMs` эксклюзивен;
2. `segments` отсортированы по `startMs`, при равенстве по `speaker`;
3. сегменты **одного** спикера не пересекаются (пересеклись — склеены или обрезаны);
4. сегменты **разных** спикеров пересекаться могут: люди говорят одновременно. Такие участки
   дополнительно перечислены в `overlaps` — редактору есть что подсветить;
5. `params` и `engine` записываются всегда: без них непонятно, почему прогон дал другой
   результат;
6. неизвестные поля при чтении сохраняются — правило то же, что в контракте документа.

## 4. Нумерация спикеров — по первому появлению

`speakerOrder: "firstAppearance"` стоит по умолчанию не из вкусовщины. Номер спикера
становится **номером дорожки**, а номер дорожки — её папкой (`01`) и идентификатором в
`dialog.json`, на который ссылаются `movedFrom` и документы следующего шага.

Сортировка «по суммарной длительности» меняется от прогона к прогону: перегнали аудио с другим
порогом — главный герой стал вторым, и все ссылки поехали. Порядок первого появления
устойчив к таким правкам.

Отсюда же правило для повторных прогонов: **номера не переиспользуются.** Появился новый
спикер — он получает следующий свободный номер, даже если номер удалённого свободен.

## 5. Что делает `dialogDocBuild` со словами и сегментами

Нода уже спроектирована (план сайта §V.5) для входа «SRT-файлы». Основной режим — **`cues.json`
(§1.1) + `diarization.json`**. Алгоритм:

1. **слово → спикер** по максимальному перекрытию с сегментами (слова берутся из `cues.json`,
   слой `words`);
2. слово, не пересекающееся ни с одним сегментом, отдаётся ближайшему сегменту, если тот
   ближе `assignWindowMs` (по умолчанию 300 мс);
3. слово, которому спикера так и не нашлось, попадает на дорожку **`no: 0` «не распознано»** —
   текст не теряется никогда, человек разнесёт его в редакторе;
4. **слова → реплики**: блоки из `cues.json` уже нарезаны `buildSentences`, но границу спикера
   они не знают, поэтому блок, внутри которого спикер меняется, **разрезается** по этой границе.
   Дальше реплика закрывается, когда выполняется любое условие:
   - сменился спикер,
   - пауза между словами больше `cueGapMs` (по умолчанию 500 мс),
   - слово заканчивается на `.` `?` `!` `…`,
   - реплика достигла `maxCueChars` (по умолчанию 90) или `maxCueMs` (7000);
5. границы реплики = начало первого слова и конец последнего, потом расширение до
   `minDurationMs` из правил документа, если реплика вышла короче;
6. `origin` каждой реплики получает `speaker` и `confidence` (среднее по сегментам, из которых
   она собрана) — по этому полю редактор строит фильтр «требует внимания»;
7. `tracks[].diar` заполняется движком, спикером и средней уверенностью.

Все пороги из пунктов 2–4 — свойства ноды, потому что материал разный: у интервью паузы
длинные, у мультфильма реплики короткие и рваные.

## 6. Нода `splitBySpeaker` ⬜ — стемы, необязательный шаг

**Редактору стемы не нужны:** дорожка персонажа — это его титры, звук нужен один, общий. Эта
нода делается тогда, когда стемы понадобятся дальше по конвейеру — например инструменту
озвучки как референс голоса. Спека здесь, чтобы не проектировать её заново в тот момент.

Простая ffmpeg-нода: вход — исходное аудио плюс `diarization.json` (или `dialog.json`), выход —
по файлу на дорожку.

```jsonc
{
  "id": "splitBySpeaker", "name": "Split By Speaker", "version": "0.1",
  "apiVersion": 1, "type": ["nodeui", "processing"],
  "description": "Режет аудио на дорожки по персонажам: речь спикера, тишина вместо остальных.",
  "main": "splitBySpeaker.js", "ui": "ui.json", "external": [],
  "cost": "0", "costUnit": "run", "resourcePool": "ffmpeg"
}
```

**Главное правило: длительность стема равна длительности исходника.** Стем — это исходное
аудио, где всё, кроме речи этого спикера, заглушено; паузы **не вырезаются**. Если вырезать,
тайминги перестанут совпадать с видео, и таймлиния, и озвучка, и весь документ разъедутся.
Поэтому режим `mute` — по умолчанию, а `cut` (склейка только речи) — отдельная опция для тех,
кому нужен компактный файл под озвучку, и она **не** идёт в дорожку документа.

Участки перекрытия попадают в стемы **всех** говорящих там спикеров: иначе речь просто
исчезнет из обоих.

Настройки: `stemMode` (`mute` / `cut`), `format` (`wav 16 bit` / `flac`), `fadeMs` (короткий
фейд на границах, чтобы не щёлкало, по умолчанию 10), `padMs` (расширить сегмент на пару
десятков мс, чтобы не срезать начало слова, по умолчанию 30).

## 7. Этапы

| Этап | Объём |
|---|---|
| **D1** | Проверка способов (§2) на своём материале: сначала A и C (разделение в ComfyUI — плагин уже есть), затем B. Мерить не «красиво ли», а долю правильной атрибуции и попадание таймингов |
| **D2** | По итогам D1: либо нода `diarizeSpeakers` + `diarization.json` (путь B/C), либо граф ComfyUI и `cues` из дорожек (путь A) |
| **D3** | Режим «слова + диаризация» в `dialogDocBuild` (§5) — с этого момента появляется настоящий `dialog.json` с дорожками |
| **D4** | `audioPeaks` для общего звука — появляется волна на таймлинии |
| **D5** | `splitBySpeaker` — только если стемы понадобятся озвучке (§6) |
| **D6** | Воспроизведение эталона нодами по карте §2.4: сначала минимальный набор (2 → 3 → 4 → 6 → 9 → 11), потом стадии качества |

До D3 оба редактора могут разрабатываться на документе, собранном руками, и на дорожках,
созданных человеком в интерфейсе. Диаризация — ускоритель, а не условие запуска.

Тестовый комплект для редакторов собирается скриптом
`innovation-hub/scripts/make-dialog-fixture.mjs`: по умолчанию — общий звук плюс титры по
персонажам (то, что нужно), с флагом `--stems` — вариант со стемами, с `--no-media` — совсем без
видео и звука.

## 8. Чего не делать

- **Не транскрибировать стемы по отдельности** (§1) — дороже и хуже, плюс галлюцинации на тишине.
- **Не вырезать паузы** в стемах дорожек (§6): тайминги — общий язык всей цепочки.
- **Не делать разделение аудио обязательным шагом** ради редактора: ему нужны титры, а не стемы.
- **Не терять неатрибутированный текст**: для него есть дорожка `no: 0` (§5.3).
- **Не сортировать спикеров по длительности** (§4) — номер это идентификатор.
- **Не переиспользовать номера** спикеров и дорожек между прогонами.
- **Не отправлять материал во внешний сервис ради диаризации**, если папка в контуре NDA.
- **Не считать диаризацию источником правды**: правда — `dialog.json` после человека.
- **Не складывать промежуточные файлы в `OUT`** (§2.8): там только финал, а `words.json` и
  `diarization.json` вычищаются вместе с локальной рабочей папкой.
- **Не ссылаться из документа на промежуточные файлы** — к моменту правки их может не быть.
- **Не гнаться за точностью выше рабочей** (§2.7): видимая ошибка дешевле незаметной.
