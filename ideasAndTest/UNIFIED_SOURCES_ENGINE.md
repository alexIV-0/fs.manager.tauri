# Единый источнико-ориентированный движок (обработка + постинг + сбор)

**Статус:** спека согласована 2026-06-30. Северная звезда для рефакторинга.
История поэтапной реализации постинга — `+AUTOPOST_DECOUPLED_PLAN.md` (этот документ её заменяет
как целевую архитектуру).

## Принцип

Любая автоматизация = **Источник → Граф → Уборка источника**, и всё это гоняет ОДИН движок
(`processItem` + `createProcessQueue`). Различается только **корневая нода-источник** и **граф
после неё**. Триггеры (часы) — РАЗНЫЕ и независимые; движок — ОДИН.

```
Источник-нода      Драйвер (часы)            Граф после неё        Уборка источника
──────────────────────────────────────────────────────────────────────────────────
mainSearch (IN)    обработка, scan schedule  convert/keying/…      OUT / delete (галочка)
Finder (любая)     постинг, свой scan timer  Poster → copyFile?    delete (галочка)
TG-source (буд.)   сбор, свой timer          (скачать)             в IN
                        ↑                         ↑                      ↑
                 свои кнопка+часы          разные ноды          deleteAfter на источнике
                 ── ОДИН processItem прогоняет всё это ──
```

## Источник истины и сайдкары

- **`options/options.json`** — весь флоу (все ноды-источники + графы). ЕДИНСТВЕННЫЙ источник
  истины. Всегда присутствует. Правится ТОЛЬКО через редактор флоу + сохранение.
- **`options/vkPost.json`, `options/tgSearch.json`** — автогенерируемые при сохранении флоу
  build-артефакты (НЕ вторая правда). Наличие файла = забота активна; нет файла = выключена.

**Сайдкар компилируется при сохранении и самодостаточен** (решение 2026-06-30): драйвер в
рантайме НЕ читает options.json. `processItem` исполняет не граф, а уже построенную очередь
(`createProcessQueue` выдаёт сериализуемые execution-объекты) — поэтому при сохранении гоним
`createProcessQueue(flow, <sourceNodeId>)` и кладём очередь прямо в сайдкар. Двухслойно:
```jsonc
{
  // шапка — дешёвый частый скан (драйвер решает что/когда сканировать/постить)
  "folder": "VK_post", "interval": 180, "order": "by Time", "deleteAfter": true,
  // скомпилированный пайплайн — исполнение, когда файл созрел
  "pipeline": { "processingQueue": [...], "<stepId>": {/*execution-objects*/} }
}
```
- Рантайм: драйвер читает сайдкар → подставляет выбранный файл + description (пути) → `processItem`.
- Оговорки: сайдкар = машинный блоб (руками не править), это КЭШ → обязателен перегенер при
  КАЖДОМ сохранении; версии/cost плагинов замораживаются на момент сохранения (для постинга
  неважно — cost=0). Источник истины всё равно options.json.

## Нода Poster (на сервис; пример VK)

Настоящий плагин (исполняется через processItem). IO:
- **вход** `inputFile` (видео) — от Finder по edge;
- **вход** `description` — `textedit` + `isInput:true`, acceptedTypes `['text','string']`: поле для текста
  И вход-связь одновременно. Если связь подключена — **import главнее** напечатанного текста
  (паттерн как у AIparser/txt2string; решает плагин: `_item.import.description ?? поле`);
- **конфиг** `account`, `target` (сообщество, `#vkGroups`);
- **выход** `inputFile` (запощенный файл) → дальше в copyFile/любую ноду.
Постинг через плагинный `_publisher.ts`; пишет `_post`-лог (дедуп + тайминг). un-stub из текущей
config-only `autoPostVK`.

## Ноды-источники

- **`mainSearch`** — источник IN. Делаем **удаляемым** и **≤1 на флоу**. Нет mainSearch → проект
  не сканируется на обработку, **папка IN не нужна**.
- **`Finder`** — источник произвольной папки (постинг). **0..N** на флоу. Config: folder, order,
  дедуп, интервал/расписание, **deleteAfter** (галочка «удалить после»).
- **`TG-source`** (будущее) — источник из Telegram/иного API.
- Item источника может быть **папкой** (движок уже умеет `isDir`) → мульти-файловый пост
  (картинка+видео+текст) ложится бесплатно. Конвенция `-` в начале имени = пропустить — общая.

## Драйверы (часы) — независимы

- **Обработка**: непрерывный скан IN, своя scan schedule. Кнопка 1.
- **Постинг**: свой проход по папкам с **отдельным таймером в опциях** (по принципу scan
  schedule обработки — это про «как часто искать материал», НЕ про интервал поста). Кнопка 2.
- Два прохода НАМЕРЕННО раздельны: обработка может молотить долго, постинг капает параллельно;
  постинг работает даже когда обработка выключена. Плата — двойной листинг (дёшево).
- Постинг-проход делает **чистый листинг** папок (НЕ `reloadFolders` обработки — та чистит
  off-список и шлёт UI-события; это работа сканера обработки, не постинга).

## Уборка — две разные

1. **Источник после графа** — мгновенно, часть конвейера: `deleteAfter` на ноде-источнике
   (удалить запощенный/обработанный исходник). Перенос «дальше» = отдельная нода (copyFile).
2. **Старый темп-мусор / логи (через N дней)** — отдельный **дневной** процесс (низкий
   приоритет). Сейчас едет внутри цикла обработки (`triggerCleanup`); вынести в раз-в-день.
   Условие безопасности — не трогать пути, что прямо сейчас в обработке (старьё и так не активно).

## Что УДАЛЯЕТСЯ при переходе на единый движок

Текущая Фаза A/постинг-машинерия — временная. Уходит:
- `runAutoPost` + `postOneForRoute` (адаптерное исполнение) → заменяется `processItem`.
- `afterPost` (move/delete внутри ноды) → заменяется `deleteAfter` на источнике + нода copyFile.
- свой эмит в log_win (`logWin.ts`) → логи пойдут автоматом от `processItem`.
- Poster становится обычной нодой-плагином (un-stub autoPostVK), чей выход течёт в граф.
ОСТАЁТСЯ: планировщик/драйвер постинга (кнопка/часы/перечисление источников/выбор файла),
сайдкары как индекс, дедуп.

## Фазы реализации

1. **Ноды-источники**: `mainSearch` удаляемый + валидация ≤1; новый `Finder` (источник папки).
   Граф без mainSearch валиден (постинг-only флоу), IN не обязателен.
2. **Сборка work-item для не-IN корня**: вынести из `findFilesForSingleFolder` переиспользуемый
   строитель item'а; драйвер постинга строит item с корнем на Finder + выбранный файл → `processItem`.
   Главный технический риск (но `createProcessQueue` уже берёт произвольный корень).
3. **Poster = плагин** (un-stub), выход в граф; `deleteAfter` на Finder; copyFile downstream.
   Удалить afterPost/adapter/собственный logWin.
4. **Таймер постинг-скана в опциях** (рядом со scan schedule); чистый листинг в драйвере.
5. **Статусбар постинга** (отдельный): N к постингу · следующий через MM:SS · последний ✅.
6. **Дневная уборка** темп-мусора — отдельный процесс (низкий приоритет).
7. **TG-source** как ещё одна нода-источник (позже).

## Инварианты (чтобы не смешать)
- Каждая забота = свой тип ноды-источника + своё имя сайдкара + свой драйвер.
- Связь между заботами — только через ПАПКИ (продюсер→папка→консьюмер), не через общий конфиг.
- options.json — единственная правда; сайдкары — производные, генерятся при сохранении.
