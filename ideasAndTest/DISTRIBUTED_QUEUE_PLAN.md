# Распределённая обработка: очередь, воркеры, разделение хранилищ

> Статус: **модель / направление** (не пошаговый план реализации). Продолжение
> [`ARCHITECTURE_DISTRIBUTED.md`](./ARCHITECTURE_DISTRIBUTED.md): та дока фиксирует направление
> (сайт = control plane, машина = worker), эта — конкретную механику, до которой договорились
> в обсуждении 2026-07-31.

---

## Одна фраза, которую надо держать в голове

> **Папка-проект = адрес и артефакты. БД = кто-что-делает-прямо-сейчас.**
> Спутать их → конфликт-файлы и потерянные обновления. Развести → система корректна.

---

## Сдвиг №1: не «толкать на машину», а «машина сама берёт» (pull, не push)

Наивная модель (push): оркестратор держит список свободных компов и **шлёт** каждому задачу.
Порождает вопросы «как узнать кто свободен», «что если занят/умер», «как не послать двоим одно».

Профессиональная модель (pull): оркестратор **не знает про машины**. Он кладёт задачи в очередь.
Свободная машина сама приходит: «дай следующую». Взяла — ушла работать. Освободилась — пришла снова.

Что рассыпается само собой:

- **«Свободен/занят?»** — не сообщать. Свободен = пришёл за задачей. Занят = не приходишь. Состояние *неявное*.
- **«Как послать на конкретный комп?»** — никак. Кто первый освободился — тот и взял. 5 машин разгребают одну очередь = параллелизм на 5 проектов без «раздавания».
- **«Как не отдать одно двоим?»** — очередь выдаёт задачу атомарно (см. Сдвиг №3).

Push (affinity — «папка прибита к машине») оставляем только там, где данные физически привязаны:
**AE / MOHO на лицензированной машине** — тег на задаче/воркере, а не общая логика.

---

## Сдвиг №2: задача не содержит локальных путей — только логику + адреса

В задаче не может быть ни `/Users/...`, ни `D:\...` — у другой машины их нет. Задача несёт:

1. **Ссылку на папку-проект в онлайн-хранилище** (корень) + **манифест** (логическое дерево + ID/URL файлов).
2. Саму job-спеку (node-граф).

Маски (`$`-переменные, `../`) **не выбрасываются** — остаются слоем *имён*. Меняется лишь то, во что
маска резолвится: не в локальный путь на диске случайного воркера, а в **адрес относительно
ссылки-корня в хранилище**. (Ср. текущую логику: относительный путь резолвится от `projectPathGD`,
корня проекта — а не от `mainWorkFolder`.)

**Обработка идёт в локальном scratch, не по сети:**

1. Оркестратор **один раз** обходит дерево и кладёт в задачу манифест (плоский список ID + дерево).
   Воркер не переобходит хранилище папка-за-папкой по сети.
2. Воркер качает нужные входы в `/tmp/job-XXXX/`, резолвит маски **там**, гоняет AE/ffmpeg/whisper локально.
3. Заливает результат обратно в папку-проект, возвращает ID выходов.

Онлайн-папка = *истина и адрес*. Локальный scratch = *рабочий стол*. **AE по сетевому монтированию
хранилища не гонять** — медленно и нестабильно.

## Сдвиг №3: «взять задачу» — это атомарный захват, а не чтение массива

Нельзя: `прочитать все pending → взять первую → обрабатывать` (две машины возьмут одно и то же).
Можно только: **одна неделимая операция «пометь-как-мою-и-верни-мне»**.

```sql
UPDATE jobs SET status='claimed', worker='m3', lease_until = now() + interval '15 min'
WHERE id = (SELECT id FROM jobs WHERE status='pending'
            ORDER BY created LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING *;
```

`SKIP LOCKED` = «эту строку уже забрали — пропусти, дай следующую». Из 10 машин, дёрнувших это
одновременно, ровно одна получит строку.

**«Кто решает — оркестратор или плагин?» → Ни тот, ни другой. Решает атомарный запрос в БД.**
В этом весь смысл — он убирает необходимость в судье.

- **Вариант A (рекомендую): pull, судья — БД.** Воркер зовёт тонкий эндпоинт сайта `POST /claim`,
  тот выполняет запрос на сервере и возвращает задачу. Нет узкого горлышка, нет SPOF в момент раздачи.
  Воркеру не нужны прямые креды к БД — только HTTP.
- **Вариант B: оркестратор раздаёт сам.** Он становится судьёй → бутылочное горлышко + SPOF, и
  атомарность всё равно нужна внутри него. Больше движущихся частей ни за чем.

**Аренда (`lease_until`) + heartbeat:** воркер периодически продлевает аренду. Умер — аренда протухла →
задача возвращается в `pending`, её берёт другая машина. Задача не теряется.

## Два хранилища: горячая БД / холодный архив-папка

Стандартный паттерн **hot store → cold archive**.

| | БД (горячее) | Папка-проект в онлайн-хранилище (холодное) |
|---|---|---|
| Что | очередь задач, статус, «кто взял», журнал дедупа постинга | входы, статичные материалы, настройки, описание, **финальный результат + архив статистики** |
| Когда пишется | постоянно, пока идёт обработка | **один раз, после окончания обработки проекта** |
| Писателей | много (воркеры, оркестратор, постинг) | один — воркер этого проекта, единожды |
| Роль | «кто-что-делает-прямо-сейчас» | источник правды, переносится куда угодно без потерь |

Правило разделения — **сколько писателей и когда**:
пиши-раз/один-писатель (артефакты, финальная статистика) → в папку;
спорное состояние/много-писателей/часто (статус, дедуп) → в БД (она транзакционная, для этого и есть).
**Не делать из папки-правды базу данных, обновляемую по любому чиху.**

## Идемпотентность: «один раз» надо обеспечить, а не декларировать

В распределённой системе ничто не происходит ровно один раз. Опасный сценарий:

```
воркер обработал → залил результат → дописал статистику в папку
        ↓ упал ЗДЕСЬ, до отметки "done" в БД
аренда протухла → задачу перезабрали → обработали снова → снова дописали статистику
        → в архиве ДВА хвоста от одного проекта
```

Фикс — сделать повтор **безвредным**, а не бороться с ним:

1. **Каждая запись статистики несёт стабильный `job_id`/`run_id`** (добавить в атомарный факт —
   см. [`+STATS_SCHEMA_PLAN.md`](./+STATS_SCHEMA_PLAN.md)).
2. **Дедуп на чтении.** Схема статистики уже «атомарные факты + агрегаты на чтении» → повтор с тем же
   `job_id` при подсчёте берётся один раз. Готовая лазейка, героизма не нужно.

**Финализацию вести через сайт, по ключу `job_id`:**

1. Воркер заливает финальный артефакт в папку (пиши-раз; ретрай перезальёт тем же — безвредно).
2. Воркер зовёт `POST /complete {job_id, run_id, stats}`.
3. Сайт в одном решении: `job_id` уже `done`? → игнор (это повторный заход, идемпотентно).
   Нет? → дописывает статистику в папку **и** помечает `done` в БД, под одним ключом.

Почему через сайт, а не «сразу из программы»: две записи (статистика в папку + статус в БД) должны быть
связаны одним решением по `job_id`, иначе воркер запишет одно и не запишет другое.

## Постинг: та же очередь, но строже

Механически — тот же массив задач, переиспользуем очередь. Два отличия нельзя проглотить:

1. **Цена повтора другая.** Перерендерить = перезаписать, безвредно. Перепостить = дубль в паблике.
   Задача постинга обязана: проверить журнал дедупа **в БД** *перед* постом и записать факт атомарно.
   Журнал дедупа (`file+platform`) переносится из локального `append_file` **в центральную БД** —
   иначе воркер B не видит, что воркер A уже запостил (ср. [`+AUTOPOST_DECOUPLED_PLAN.md`](./+AUTOPOST_DECOUPLED_PLAN.md)).
2. **Привязка к кредам.** Пост можно сделать только на воркере с токеном нужного аккаунта. Задача несёт
   *ссылку на аккаунт*, воркер добирает секрет в момент запуска с TTL
   (см. [`SECRETS_VAULT_SITE_PLAN.md`](./SECRETS_VAULT_SITE_PLAN.md)). Рендер поолится свободно, постинг — нет.

## Версии AE / MOHO

Принятая позиция: результат от версии почти не зависит, важно «не ниже определённой». Дешёвая страховка:
**задача несёт минимальную версию, воркер отказывается, если у него ниже.** Одна проверка вместо
«иногда ломается на какой-то машине». Не горит — на потом.

## Что строить (порядок) и что НЕ строить сейчас

**Строить по порядку:**

1. **Объектное/файловое онлайн-хранилище** с адресацией по ID/URL (у пользователя это ссылка на
   папку-проект). Без стабильных адресов распределёнка невозможна, не желательна.
2. **Таблицы в уже прописанной онлайн-БД:** `jobs` (очередь) + `logs`/`status` + `post_ledger` (дедуп).
   Одна БД, три роли.
3. **Тонкие эндпоинты сайта:** `POST /claim`, `POST /complete`, `POST /heartbeat`. Захват через `SKIP LOCKED`, аренда с таймаутом.
4. **Режим воркера** (не плагин *внутри* пайплайна, а **режим запуска** «оболочка с плагинами, без папок»):
   pull-цикл `claim → скачать в scratch → пайплайн → залить → complete`, heartbeat.
5. **Манифест задачи** строит оркестратор; воркер материализует дерево локально.
6. **Теги** `can_ae` / `can_moho` / `gpu` на задачах и воркерах — гибридный роутинг.
   ⏸ Отложено 2026-08-14: парк машин однородный, роутить не по чему. Вернуться, когда
   появится машина, отличающаяся от остальных.

**НЕ строить сейчас:** свой сетевой брокер поверх сокетов; iroh для очереди (это транспорт, не очередь);
GDrive-sentinel как фундамент (воскрешает push + конфликт-файлы + латентность синка — годится «дёрнуть
разок», не как основа); эфемерные облачные воркеры; realtime-вебсокеты для статуса (поллинг сайта хватит);
красивый дашборд.

## Аналогия для интуиции

Сайт-БД = вынесенное в сеть **окно логирования (logwin)**, только постоянное и двустороннее: не просто
принимает логи от плагинов, но и раздаёт им задачи. Новой сущности нет — это logwin, ставший общим и
двусторонним.

## Резюме решений

- ✅ **pull, не push** — машина сама берёт; free/busy неявное.
- ✅ **задача без локальных путей** — ссылка-корень + манифест; маски резолвятся от корня; обработка в scratch.
- ✅ **атомарный захват** — решает БД (`SKIP LOCKED`), не оркестратор и не код воркера; аренда + heartbeat.
- ✅ **горячая БД / холодная папка** — спорное состояние в БД, артефакты и финальная статистика в папку (пиши-раз).
- ✅ **идемпотентность** — `job_id` в атомарный факт + дедуп на чтении; финализация через сайт по ключу.
- ✅ **постинг** — та же очередь, но дедуп в БД + привязка к аккаунту-сейфу.
- ✅ **версии AE/MOHO** — мин-версия на задаче, воркер отказывается если ниже (на потом).

## Пересмотрено 2026-08-20: локальный прогон и воркер работают ОДНОВРЕМЕННО

Взаимоисключение отменено: машина простаивала половину времени зря — локальное расписание
ждёт скана, очередь ждёт свободной машины, а работать разрешено только одному из двух.
Разведены ровно те две вещи, из-за которых запрет и стоял:

- ✅ **Полоса воркеру всё-таки своя** (`worker` в `src/PROCESSING/runLanes.ts`). Полоса
  отвечает на вопрос «чей стоп меня убивает»: с общей полосой Stop локальной обработки
  прибивал бы ffmpeg взятой задачи, а аварийный стоп воркера — чужой рендер. Сигналов на
  полосу два и оба разъехались по ключу: `AbortController` в `processingAbort.ts` (был
  один на модуль — старт воркера подменял объект под идущей обработкой) и `AtomicBool` в
  Rust (там полосы были заложены изначально, менять нечего).
- ✅ **Семафоры пулов, наоборот, ОБЩИЕ с локальным прогоном** (`poolScopeOf`). Лимит
  `local: 1` — про железо («один After Effects за раз»), и два набора семафоров означали
  бы два рендера сразу. Набор теперь принадлежит области и живёт, пока в ней есть хоть
  одна активная полоса; конец волны локальной обработки его больше не выбрасывает.
  Постинг остаётся при своём наборе: он почти целиком `online`.
- ✅ **Аренда переживает ожидание слота.** Общие семафоры означают, что шаг воркера может
  честно стоять в очереди за AE десятки минут. `processItem` шлёт `node:wait` перед
  захватом слота, пульс аренды считает такой шаг текущим — иначе задачу забрала бы другая
  машина, пока эта ждёт.
- ✅ **Области работ не пересекались и раньше:** локальный скан пропускает зеркальные
  папки (`findAllFilesForProcess`, `isInMirror`), воркер берёт только задачи очереди. Так
  что «локальный результат уедет в онлайн-очередь» невозможно: отчёты фильтруются по
  `itemId` задачи.
- ✅ **Play в окне нод остаётся вне схемы.** Он гоняет одну локальную папку в своём
  JS-realm'е, семафоры того прогона воркеру не видны, и `local: 1` между ними не
  держится. Так и задумано: Play — ручной локальный запуск, общего замка в Rust под него
  заводить не нужно.
- ✅ **Две кнопки остановки.** Мягкая: не брать новых, текущую доработать, залить,
  отчитаться, отключиться. Аварийная: убить процессы сейчас и **явно вернуть задачу в
  очередь** (`releaseTask`), а не ждать протухания аренды.
- ✅ **Идентичность машины — UUID**, сгенерированный один раз при первом запуске и лежащий в
  настройках программы. Hostname остаётся подписью: дефолтные имена маков совпадают, а на
  совпадении ломается не очередь, а архив статистики (две машины пишут в один объект, и
  заливка затирает строки целиком).
- ✅ **Настроек у воркера нет и пока не нужно.** Включает и выключает человек кнопкой,
  автостарта нет; парк однородный, поэтому теги возможностей не нужны; задача на машине
  всегда одна, независимо от тяжести; интервал опроса — 10 секунд константой. Ручка,
  которую нельзя объяснить, хуже её отсутствия. Первый кандидат на настройку, когда
  появится живая очередь, — автостарт при запуске программы.
- ✅ **Манифест для папки-источника.** Снятие `-` с имени папки = момент, когда содержимое
  заморожено, поэтому перечисление в этот момент не устаревает. Для файла манифест не нужен
  вовсе — достаточно идентичности.
- ✅ **Скачивать в зеркало, а не в scratch.** Разбирали `/tmp/job-XXXX/` из раздела «Сдвиг
  №2» и отказались: половина этой работы уже сделана. Гидрация по требованию — шов
  `hydrate` в host-сервисах (`fs.read`/`fs.copy` сами тянут байты), заливка результата —
  watcher зеркала плюс демон, вытеснение скачанного — TTL и лимит размера. Со scratch
  пришлось бы писать заливку, чистку и вытеснение заново. Воркер только доводит каталог
  проекта до свежего состояния (`catch_up`) и превращает идентичность файла в путь зеркала.
  Следствие: `taskDone` зовём **после** того, как заливка по проекту опустела, иначе сайт
  узнает «готово» раньше, чем увидит результат.
- ✅ **Области видимости двух запусков не пересекаются.** Локальный прогон обходит только
  локально подключённые папки; облачные (в зеркале) он пропускает — их задачи выдаёт сайт,
  и берёт их режим воркера. Иначе облачный проект обрабатывали бы сразу двое: эта машина по
  своему расписанию и любая другая, взявшая ту же задачу. Первая колонка при этом остаётся
  общей — разделены запуски, а не интерфейс, и синхронизатор продолжает связывать папки при
  ручной работе. Запуск одной папки из окна нод — ручная операция и под это правило не
  попадает.

## Найдено при первом живом прогоне через очередь (2026-08-18)

Прогон прошёл целиком и правильно: сайт создал задачу по `123.mp4`, воркер её захватил, обработал
цепочку (`copyFile` → `ffSwitch` → `saveFileOnGD`), результат уехал в `OUT/08 August/`. Не сработала
только **отчётность**: в окне «Очередь задач» на сайте задача навсегда осталась «в работе», шаги
показывали 0%, и из живой очереди она не ушла.

Смотрели с двух сторон. Со стороны сайта в базе на момент разбора:

```
tasks:  status=running  claimed_by=alekseys-imac  attempts=1
        claimed_at 08:29:57   lease_expires_at 08:49:58

task_progress:
  step_id="start"    status=running  "начата обработка 123.mp4"   08:29:58
  step_id="running"  status=running  "обработка идёт"             08:34:58

payload.processingQueue: ["mainSearch","MQx1_","W4eDu","WShPP"]
```

То есть канал рабочий: авторизация проходит, `claim` отработал, `progress` доходит и аренда честно
продлевается. Причин ровно две, обе у нас.

### Причина 1: `stepId` синтетический, а не из задачи

Мы шлём `start` и `running`. Сайт сопоставляет отчёты с шагами **по тем же id, которые сам положил в
`payload.processingQueue`** — `mainSearch`, `MQx1_`, `W4eDu`, `WShPP`. `start` не совпадает ни с чем,
поэтому все четыре шага остаются `queued`, а полоса прогресса показывает 0%.

Настоящие id у нас в руках: в лог-окне они и печатаются (`→ MQx1_ (copyFile@0.1)`). Надо просто
передавать их в отчёт.

Отчёты с неизвестным `stepId` сайт принимает молча — не ошибка, но и не видно. Ровно поэтому
выглядело, будто мы с сайтом вообще не разговариваем.

### Причина 2: `taskDone` не зовётся вообще

Обработка кончилась в 08:30:01, а в 08:34:58 ушёл очередной пульс «обработка идёт». Задача не «ждёт
окончания» — она ждёт отчёта.

Отдельный побочный эффект: **пульс через `progress` продлевает аренду**. Каждый такой отчёт сдвигает
`lease_expires_at` на 15 минут вперёд, поэтому сборщик протухших аренд задачу не подберёт никогда —
с точки зрения сайта машина жива и работает. Умри воркер посреди работы, задача повисла бы так же.
Для «я жив» есть `ping`, он двигает контакт машины, но аренду не трогает.

### Контракт, который надо закрыть

Один роут `POST /api/storage/v1/queue` под нашим токеном `mch_…`, поле `action`. Те же операции —
экшенами на `POST /api/v1` для токена `rc_…` (имена в скобках). В каждом запросе — `machineUuid` и
`hostname` как сейчас.

| action | поля | что делает на сайте |
|---|---|---|
| `claim` (`claimTask`) | `capabilities?` | атомарно выдаёт задачу, аренда 15 мин, `attempts += 1` |
| `progress` (`taskProgress`) | `taskId`, `stepId`, `status`: `running`/`done`/`error`, `message?` (≤2000) | пишет шаг; первый отчёт переводит `claimed → running`; **продлевает аренду** на 15 мин |
| `done` (`taskDone`) | `taskId`, `outFiles?` (≤500), `totalCost?` | статус `done`, строки прогресса удаляются, машина освобождается. Идемпотентно — повтор безопасен |
| `failed` (`taskFailed`) | `taskId`, `error` (≤4000) | статус `failed`, `payload` сохраняется — есть что переретраить и в чём разбираться |
| `release` (`releaseTask`) | `taskId` | вернуть в очередь при аварийной остановке; попытка **не** засчитывается (`attempts -= 1`) |
| `ping` (`machinePing`) | — | «я на связи» без запроса задачи и **без** продления аренды |

Схемы — `lib/pipeline/queue-endpoint.ts` в репозитории сайта, описание — `docs/PIPELINE.md` §11–12.

### Что делаем у себя — СДЕЛАНО 2026-08-18

- [x] **`progress` по каждому шагу, `stepId` из `payload.processingQueue`.** Мост
      `reportSteps` в `runTask.ts` слушает локальную шину `processing:event`, куда
      `processItem` и так рассылает `node:start`/`node:done`/`node:error`, и переводит их в
      отчёты. Отдельный колбэк в движок не заводили: это был бы второй способ узнать одно
      и то же. В очередь идёт `graphNodeId` — у саб-шагов `loop` `nodeId` суффиксирован
      (`X#3`), а сайт знает только исходные id. Свои события отбираем по `itemId`: у
      элемента воркера он равен `taskId` (`description.dbItemId`).
- [x] **Шаг `mainSearch` закрываем сами.** `processItem` идёт по очереди со ВТОРОГО
      элемента — выход `mainSearch` подставляется до входа в движок. Без явного отчёта этот
      шаг оставался бы `queued` навсегда, и полоса не доходила бы до конца даже у успешной
      задачи. Отчёт правдив: идентичность разобрана, байты на диске — это вся работа
      `mainSearch` на машине.
- [x] **`taskDone` / `taskFailed`** — уже вызывались в `runner.ts`, но до них не доходило:
      см. следующий пункт.
- [x] **Найдена настоящая причина «задача навсегда в работе»: `waitUploads`.** Он ждал, пока
      опустеет список неотправленного, а `storageNotUploaded` отдаёт **весь список зеркала**.
      В нём висел файл из прошлого прогона, который не заливается вовсе (имя с двоеточиями,
      `/notify` → 400). Поэтому каждая задача проедала весь таймаут (10 минут) и только потом
      отчитывалась. Теперь фильтр по пути проекта, а файлы с `reason: 'stopped'` не ждём
      вообще (остановленная вручную заливка сама не возобновится) — но пишем их в лог, чтобы
      «отчитались, а файла в облаке нет» не было загадкой.
- [x] **Пульс аренды привязан к ТЕКУЩЕМУ ШАГУ, а не к таймеру.** Здесь отступили от
      формулировки выше — «перевести пульс на `ping`» — и вот почему: `ping` аренду не
      двигает, а рендер AE идёт сорок минут при аренде пятнадцать, то есть на одном `ping`
      задачу забрала бы другая машина посреди работы. Продлеваем настоящим `progress` по
      идущему шагу («шаг идёт 12 мин»), а когда шаг не идёт — между шагами и на ожидании
      заливки — не двигаем ничего. Дефект, который просили закрыть, закрыт именно этим: пульс
      больше не идёт после конца обработки, и застрявшая задача теперь протухает по аренде.
      Отдельный `ping` для «машина жива» не нужен — его шлёт демон синхронизации сам, раз в
      пульс, независимо от режима воркера (`storage/daemon.rs`).
- [x] **`release` на аварийной остановке** — проверено, реализовано в `stopWorkerNow`
      (`runner.ts`), плюс возврат при срыве до отчёта.

- [x] **`outFiles` в `taskDone` — логические, а не машинные.** Слали абсолютные пути этой
      машины (`/Users/…/r2cloud/…`), сайт кладёт их в `tasks.payload` как есть, и сделать с
      ними ничего не может: сопоставить с каталогом можно только по `folder_path` + `name`.
      Теперь отдаём путь от корня проекта (`OUT/08 August/18.08-01.30_123.mp4`). Файлы вне
      папки проекта в отчёт не попадают вовсе — их нет в облаке (промежуточное в локальной
      рабочей папке), и ссылаться сайту не на что; список таких пишем в лог.

**Что осталось открытым по этому разбору:** шаг длиннее аренды всё ещё держится нашими
отчётами о том же шаге. Если сайт захочет отличать «работа идёт» от «машина зависла на шаге»,
нужен либо предел числа продлений на один шаг, либо отдельное поле «сколько уже идёт» — это
решение сайта, у нас данные есть.

### Ещё два следствия, замеченные сайтом в тот же вечер

**Не удалять источник, пока по нему стоит задача.** В прогоне до этого файл был обработан и удалён
нашим прежним путём (`deleteAfter`) в 23:43, а в 23:45 воркер взял по нему задачу из очереди и вернул
её через `releaseTask`. Задача при этом не падает и не уходит: `release` уменьшает `attempts`, поэтому
`max_attempts` не достигается никогда — цикл «взял → отдал» может идти вечно. Пока конвейер включён,
`IN` облачного проекта трогать своим путём нельзя.

**Сайт теперь такие задачи гасит сам.** Если строка файла ушла из каталога, задача в `queued`
помечается `failed` с «источник удалён» — на нашей стороне это выглядит как задача, которая исчезла из
выдачи `claim`. Это норма, а не потеря работы.
