# Диалоговый документ `dialog.json`: контракт со стороны клиента

> Составлено 2026-08-24. Документ **для обеих сторон**: локального клиента (`fs.manager.tauri`,
> Tauri 2 + React 19 + MUI/emotion) и сайта (`innovation-hub`, Next 16 + React 19 + Tailwind).
>
> **Канонический текст правил — `innovation-hub/docs/DIALOG_FORMAT.md`.** Здесь он намеренно
> **не дублируется**: два полных текста разъезжаются молча, а формат — единственное, что
> связывает две независимые реализации редактора. Один текст, ссылка из второго репозитория.
> Эталонный файл — `innovation-hub/docs/dialog.example.json`.
>
> Ниже — только то, что специфично для нашей стороны.
>
> Наш план: [`DIALOG_EDITOR_PLAN.md`](./DIALOG_EDITOR_PLAN.md).
> План сайта: `innovation-hub/docs/TOOLS_SRT_EDITOR_PLAN.md` (там же спека нод графа §V.4–V.5).

## 1. Что нужно прочитать в каноническом тексте

| § | Про что | Почему обязательно |
|---|---|---|
| §2 | девять правил (мс, эксклюзивный `endMs`, детерминированный порядок, сохранение неизвестных полей, only-additive версии, относительные пути, UI-состояние вне документа, экспорт — производная) | нарушение любого = молчаливое расхождение двух реализаций |
| §3 | структура и порядок ключей | порядок ключей — часть контракта, иначе diff бесполезен |
| §6 | порядок валидации | ругаться обе стороны должны на одно и то же |
| §7 | профили экспорта | имена файлов и правила пересоздания |
| §8 | слияние при одновременной правке | алгоритм обязан совпадать до деталей |
| §9 | что делает нода графа и чего не делает | дописывать, а не перезаписывать |
| §10 | проверка «открыл → сохранил → файл побайтово тот же» | дешёвый тест на расхождение |

## 2. Наша специфика

| что | у нас |
|---|---|
| транспорт | файл на диске. Никакого HTTP: ни `storage/*`, ни `ensureLocal` — контур NDA |
| конкурентность | ETag нет. Перед перезаписью сверяем `mtime` + `size` с теми, что были при чтении; разошлись — слияние по канону §8 |
| запись | `fs_commands.rs` (атомарность и безопасность путей там же, где у остальных файловых операций) |
| относительные пути (§2.7) | резолвятся от папки документа; проверку `..` / абсолютного пути делать **и** в TS, **и** в Rust — как в остальных файловых командах |
| журнал незаписанных правок | файл рядом с документом, в сам документ не попадает |
| подхват изменений | `fs_watch_start` (`watch_commands.rs`) — вотчер, а не поллинг; у сайта наоборот, поллинг дельты |
| пики (`tracks[].peaks`) | необязательны: ffmpeg локально, считаем `parseAstatsEnvelope` на месте и кэшируем рядом |
| UI-состояние (§2.8) | LocalStorage окна редактора по ключу «id документа + id дорожки» |

## 3. Порядок согласования правок

1. Правка формата обсуждается и вносится **в канонический текст** (`innovation-hub/docs/DIALOG_FORMAT.md`).
2. Если правка ломающая — новый `version`, обе реализации отказываются открывать неизвестный
   major (правило §2.6), а не пытаются угадать.
3. Если меняется поведение только нашей стороны — правится этот файл, канон не трогается.
4. Эталонный `dialog.example.json` обновляется вместе с форматом, и обе стороны прогоняют по
   нему тест из §10.
